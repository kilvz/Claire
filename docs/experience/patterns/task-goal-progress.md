# Many operations performed, but the goal count never changes

Signal: the task card is stuck at 0/N, but verifiable results already appear in the action timeline. First compare the `criteria`, the parse-error event (`RunEvent.State.name == "task_progress_invalid"`) and the model replies of the same run. Having only the initial `criteria` and no parse error means no subsequent valid update was received; you cannot infer completed goals from the number of actions. The collapsed "N steps before this" on the chat page refers to actions that have already happened.

In one cross-app store-lookup task, the replies reported the confirmed address and store name one after another, yet the count stayed at the opening 0/3. The old protocol stripped the progress block from the conversation history and did not bring the checklist back in subsequent regular requests. Now `TaskProgressTracker` brings back the pending-confirmation IDs and deduplicates reports that carry evidence; `RunEvent.Criteria.confirmedIds` can be used for review. The counter does not verify the evidence content, nor does it fill in unreported results as completed.

Regression entry point: `AgentLoopTest.coffeeTaskConfirmsGoalsWithoutCountingClicksOrClosingOnFiveNotes` checks the to-dos the model actually receives, 1/3 → 2/3 → 3/3, and that operations can continue when the sub-quantity is reached; `completedQuantityClosesOutInsteadOfRecheckingForever` preserves the wrap-up behavior of pure counting tasks. Both are script replays and cannot prove that every model reports on time.

Another signal is **not a single checklist event at all**: when the same coffee-shop task ran again, it ended normally after 30 rounds, with no checklist and no parse error. The original to-do reminder only looked at multi-goal checklists that had already been established, so it would never prompt a backfill. Now, if the first tool call carries no checklist, one reminder is sent within the next regular request; the already observed results can be used to backfill confirmations at the same time. Check `RunEvent.State.name == "task_progress_plan_reminder"` to distinguish "a backfill reminder was sent" from "the model actually backfilled". If there is still no checklist, keep the action state and do not invent a denominator. The script cases `missingChecklistCanBeBackfilledOnTheNextCoffeeTaskReply` and `ignoredChecklistReminderDoesNotRepeatOrInventProgress` verify backfilling and ignoring respectively; the real model's responses still need to be measured.

The backfill rule is written in the system guidelines, and the runtime only emits a short marker. Repeatedly stuffing the whole example into the context after the tool results triggers compaction in the small-window case of `longTaskStaysUnderBudget`, which instead leaves the model unable to see the full screen it just read. That case also checks the retention of the first long screen read and the budget of the whole request.
