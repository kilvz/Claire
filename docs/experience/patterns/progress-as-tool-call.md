# Progress checklist treated by the model as a tool call

In two device runs of the same coffee-shop task, the model put the three acceptance goals into the arguments of a tool call named `task_progress`, and only called the tool to view installed apps in the next round. The upstream progress convention is written in the `<task_progress>` block of the reply body; see commit `13f34294`. The `unknown_tool` in the records and the missing first checklist event point to the difference between these two message formats. A similar progress stall can also happen when the model never generates a checklist, so check the raw reply type and tool name first.

`ProgressToolCallTest` replays this shape at the entry of the run loop. It checks whether `RunEvent.Criteria` receives the checklist, whether the actual operation runs exactly once, and whether the next model request returns a result for each call ID in the original order. Misplaced fields still go through the argument and state validation of `CompletionPlanBlock`, and other unknown tools still raise an error. Device acceptance should start a new instance of the same task; historical runs keep their original results.

Device joint-test review (2026-11-18): among 52 captured replies there were 4 function calls with the same name. One submitted three goals, and the other three each confirmed one. The run record wrote 4 checklist events in sequence, with no failure record for this tool and no progress validation errors, and the final state was `succeeded`. The joint test includes per-goal confirmation; when the compatibility fix is applied on its own, progress field validation still follows what that version originally had.
