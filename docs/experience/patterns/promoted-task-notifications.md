# Task notification qualifies but no live capsule appears

On an Android 16 device (OnePlus 13T, ColorOS 17), Claire Dev was already allowed to post ordinary notifications, but the system 「实时通知」 (Live notifications) switch was still off (this vendor displays Android 16 live notifications as 「流体云」 (Fluid Cloud)). Run `TaskLiveUpdateDeviceTest`: with the switch off, the task notification's `hasPromotableCharacteristics()` is true but `NotificationManager.canPostPromotedNotifications()` is false, and only an ordinary icon appears on the home screen. Use `Settings.ACTION_APP_NOTIFICATION_PROMOTION_SETTINGS` and `Settings.EXTRA_APP_PACKAGE` to open this app's system page, enable it and rerun the same test case: 「正在执行」 (Running) appears at the top of the home screen and then changes in place to 「等你回答」 (Waiting for your answer).

When diagnosing, look at three things separately: whether the notification posted by the app meets the [live update conditions](https://developer.android.com/develop/ui/views/notifications/live-update), whether the system permits this app to promote notifications, and whether the system UI actually shows it after you leave the app. Looking only at the notification shade, the permission declaration or a single system flag cannot replace the last step.

Verification scope: a Dev over-install on one Android 16 device. From this you cannot infer the default switch state or entry name on other models, or the vendor interfaces on Android 15 and earlier.

Another case is that the capsule has appeared but keeps showing only 「正在执行」 (Running) for a long time. In that case first check the mapping from `TaskState.Running` to the short text. While waiting for the model, `tool` is empty but `note` may still be the action from the previous step; showing `note` directly not only reports the wrong phase but may also expose task content. `RunProgress.Replay` has the current step and the total number of steps, while `RunProgress.Batch` only has the batch length, so the model round count must not be paired with that length as progress. Older short-text versions used this to distinguish operation, quantity and waiting states.

After the multi-state build `16e61108` was over-installed on the same device, the official `TaskLiveUpdateDeviceTest` cases passed for "leave to the home screen while thinking" and "leave to the home screen after progress is reported" respectively. The home-screen capture confirmed 「正在思考」 (Thinking), 「进度2/5」 (Progress 2/5) and 「等你回答」 (Waiting for your answer), and their removal after it ended; these phases use the same notification. During the first observation it had stopped at 「正在思考」, the cause was not determined, and the system switch was not changed on that basis. This time the screen-reader, phone-operation and web-browsing texts were not observed one by one on the device.

**When the chat-page count does not move, first distinguish missed reporting from missed refresh.** In one cross-app task, round 1 gave three acceptance conditions and 0/3, the text in rounds 18 and 23 confirmed two results respectively, but as of round 31 the run record still only had the initial `criteria` event, and there was no `RunEvent.State.name == "task_progress_invalid"`. In this case there was no new structured count to display in the UI. When diagnosing, compare these two kinds of events and the corresponding `model_reply` within the same run ID; if 1/3 already appears in the record, then check the UI's subscription and priority. `CompletionPlan.apply` keeps fields that were not updated; reporting a passage of text on its own or changing the list of acceptance conditions does not automatically increase `done`. This and whether the system permits notification promotion are two independent problems.

**Which segment the task has reached** can be judged from the package name that the task tool actually opened, or from the page read through the phone port. Advance only one segment according to the app order the user gave; unrelated packages, failed opens and looking back at the previous app do not affect the stage number. This number must not be written into the chat page's completed-goal count. Different goals within the same app have no package-name switch, so use the stage planned by the AI and the structured report it gives when it starts the next goal. With the coffee-shop task in `TaskStagesTest` it is reproducible that three segments still appear even though reporting was missed throughout; currently this version is only verified on the simulated port, and the system capsule width awaits device retesting.

In the device joint test at `558b4a6`, the user could already see 小红书 (Xiaohongshu), yet the capsule still showed 「1/3 查址」 (1/3 Address lookup). 「查址」 (Address lookup) comes from the AI plan; when planning in the named order, the first segment of that original sentence showed 「高德」 (Amap). This 36-step run ended successfully; only another record, cancelled after 5 steps, had the first-round unknown-tool error. Diagnosis should match screenshots by run ID. The old regression case ran with an empty app list; after adding test apps named 「搜索」 (Search) and 「笔记」 (Notes), the same coffee-shop request could not establish an order, and the AI segmentation again ignored the actual app switching — both phenomena were reproduced in the JVM. The phone connection was interrupted, so the actually conflicting app names have not been confirmed. The regression case `TaskStagesTest` now uses a launcher directory containing same-name words plus built-in knowledge, and checks that when the AI labels a stage with an app, successfully entering the next app can advance it; two goals within the same app still need explicit reporting. The system display of the new package awaits retesting.
