## 1. Bug analysis

### 1.1 Systemic bugs (same root cause, highest priority)

#### 1.1.1 The "back failure" family — the most urgent fix right now

**Issues involved**: #622, #642, #469, #450, #299, #225, #221, #220, #209 (and the A12 variant of #80)

**Common symptom**: in `actions`, item 7 of the self-check, `tap ok / type ASCII ok / type Chinese ok / scroll ok / back failed`, while the other 11 items all pass. On the task side it shows up as the `no_progress` circuit breaker (#622 provided complete records for two real run_ids).

**Key evidence (the inference from #622, most likely right in direction)**: back and tap/type/scroll go through **different injection channels**. tap/type/scroll are coordinate/text injection, while back is a **global key event (KEYCODE_BACK)**; on a virtual display with `displayId != 0`, the key event may be dropped by the system or not routed to the foreground task. Hence "the tap does nothing → the frame does not change → no_progress".

**Why you cannot reproduce it**: almost all of these reports are Xiaomi/Redmi + HyperOS (Android 15/16/17), and the test device you have is not in that combination. `#211` (setting the display to full screen after creating it) may have alleviated part of it, but reports still came in on 0.1.42/0.1.43, so it is not fixed at the root.

**Suggested fix (by root-cause class, not per-device special cases)**:
1. First confirm the back implementation path (`phone_back` / item 7 of the self-check) and see whether it actually sends `KEYCODE_BACK` or the accessibility `performGlobalAction(GLOBAL_ACTION_BACK)`; the two have different routing semantics on a virtual display.
2. Make the "back has no effect" determination a general "frame did not change after injection" check (reusing the re-tap detection idea already done in #461).
3. **Degradation chain**: when back has no effect, fall back to "tap the visible back control at the top-left of the current page" → then to "tap the navigation bar/gesture back area" → only if that still has no effect does it count as no_progress.
4. Once this degradation lands, it will simultaneously fix the task-side circuit breaker in #622 and all self-check items with back failures.

> Per the project's "fix by root-cause class" principle, do this family **in a single fix**; do not chase it on each machine.

#### 1.1.2 The "empty accessibility on custom-drawn UIs + ineffective injection" family

**Issues involved**: #237 (WeChat main screen), #92 (sending a WeChat message), #421 (taps ineffective in the GitHub client), #471 (OCR cannot read WeChat mini programs), #201 (WeChat input), #225 (the GitHub page cannot be tapped or read)

**Common root cause**: the target app's page is custom-drawn/Flutter or has anti-automation handling, exposing no accessibility nodes (`treeQuality: unusable`, `elements: []`), and the injected pointer events are not consumed. Right now Claire "can see the text but cannot tap and cannot read the controls".

**This must be split into two different problems; do not conflate them**:
- **A. Injected taps are dropped** (#237/#421/#92/#201/#225): you need to distinguish "not delivered" from "delivered but dropped". #237's proposal is good: 2–3 consecutive taps with `no_effect` + an empty accessibility tree ⇒ conclude "this app does not respond to injected taps", tell the user explicitly, and stop retrying infinitely.
- **B. Local OCR reads nothing although the frame has content** (#471): the screenshot has content and a vision model can read it all, but local OCR returns empty. This is an OCR engine recognition problem for a certain class of fonts/forms, not the same thing as A, and must be investigated separately (the reporter needs to add screenshots + diagnostics).

**Suggestions**:
1. Land an explicit failure type for "injection ineffective" plus a degradation path (#237 points 1 and 2); this is a general mechanism, not specific to WeChat.
2. Handle #471's empty OCR separately through the "ask for a screenshot to locate it" path (you have already replied asking for evidence).
3. Scenarios where an app like WeChat can be tapped (the list page works, the conversation page does not) show that it is not "WeChat as a whole is unusable" but "the conversation page is custom-drawn". At the **knowledge** layer, one could capture an APP knowledge entry along the lines of "WeChat conversation pages have empty accessibility and need screenshot-based locating".

#### 1.1.3 The audio focus/mute family

**Issues involved**: #483 (no sound from Douyin/Bilibili in the foreground while a task runs on the background virtual display), #228 (running a background task causes global mute), #588 (the small-window sound switch can only be turned on, not off)

**Root cause (already located by you)**: during a task, `appops PLAY_AUDIO ignore` on the virtual-display app only makes it "silent", but **does not stop it from requestAudioFocus**; as soon as the app in the virtual display makes a sound it takes audio focus away from the foreground player. It recovers after the task ends and releases it.

**Suggestions**:
1. #483/#228 are two manifestations of the same mechanism: keep the virtual-display app from seizing focus (or route virtual-display audio to a dummy device). The focus stack from `dumpsys audio` can confirm which uid takes focus; you have already replied with that diagnostic request, so wait for the data.
2. #588 is another layer: toggle state management for the small-window sound switch. You have already added diagnostic logs (`togglePipSound` / `could not mute again`), and **locating it requires a log from a device reproduction**; leave it parked awaiting data and do not guess hard from reading the code.

## 4. Appendix: a few cross-cutting reminders

1. **A device-side bottleneck ≠ a code bug**: for cases like #695, #307 and #570 that are "vendor ROM behavior", the right posture for the app is "capability detection + explicit error + graceful degradation", not digging into vendor private implementations (project rule).
2. **Fix by root-cause class**, do not patch issue by issue: the back family, the audio focus family, the unlock family and the ineffective-injection family are each one root cause, each fixed once.
3. **Never close an issue that is "fixed but not verified on a device"**; put it uniformly on the retest list after the next release (your existing process — keep it).
4. **Judge UI bugs with the perf build** (the debug build is 7–10x slower); do not draw conclusions about "lag"-type problems from the debug build.
5. **Every new string in a new feature needs 10 languages + RTL** (note this for #646 Turkish).
