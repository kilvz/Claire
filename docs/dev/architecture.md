# Claire architecture

This document describes Claire's overall structure as the code stands today, to make it easier to find code. Work not yet done or only half done is written up in [`roadmap.md`](roadmap.md).

Path abbreviations: `core/…` = `core/src/main/kotlin/com/wangzan101/mika/core/`, `app/…` = `app/src/main/java/com/wangzan101/mika/`.

## 1. Modules and layering

The repository has two Gradle modules:

- `:core`: pure Kotlin (JVM), with no Android dependency. The main loop, tools, the platform-independent parts of capabilities, context, verification, memory, knowledge, triggers and run records all live here, and can be run on a computer with unit tests and a fake model. Prompts, built-in knowledge and skills are its resources (`core/src/main/resources/`).
- `:app`: the Android host. UI, foreground services, virtual screens, accessibility, the built-in phone assistant, WebView, sandbox, file storage, and the Android implementations of the interfaces in `:core`.

There is also an optional standalone Go gateway `companions/relay/`, used for single-user, single-device public-network remote CLI / MCP. It is not part of the APK; the phone connects through outbound WSS; see [remote-mcp.md](remote-mcp.md) for deployment and phone authentication.

```
 Source   chat UI │ timed/conditional trigger │ parent task (child task) │ computer (CLI / MCP)
          └──────────┬──────────┘
          TaskService (foreground service, Android host)
          TaskCenter (one Run per conversation, parallel limit, queue) · RunStore · Outbox
                     │
          TaskRun ── one run: install capabilities, build AgentLoop, wrap up
                     │
          AgentLoop (scheduling only) ← RunInbox (interjections, answers, confirmations, hand-backs, cancel)
            ModelCaller · ContextBuilder/ContextCompressor · TurnPolicy/StopRules
            ToolDispatcher → ActionExecutor (the only execution entry)
                     │  CapabilityProvider (the core does not know concrete capabilities)
          phone      web       sandbox      (mcp client)
```

Dependency direction between packages in `:core` (checked by `PackageDependencyTest`):

- Capabilities (`core/cap/<capability>/`) depend on the core; the core references no capability, and capabilities do not reference each other; only the assembly layer (`core/assembly/`) knows several capabilities at once. In the App, the directories of the various capabilities under `cap/` likewise do not reference each other.
- The tool engine (`core/tool/`: `ToolDispatcher`, `ToolContext`, `AgentTool`, etc.) does not reference UI state (`core/screen/uistate/`). The engine only uses the layer that has a screen through `SurfaceLayer` (`core/tool/SurfaceLayer.kt`); the interface contains only the screen id, the tool, the parameters and the result; the implementation is `Interfaces`, created by the assembly layer at startup and put into the tool context, and tools that have a screen get the screen-reading state from the context through the extension in `core/screen/uistate/ScreenContext.kt`.

`:core` (`core/…`) is grouped by responsibility, with packages nested under each group:

|---|---|

| `screen/` | Screen reading: `uistate/`, `observation/`, `map/` (UI map), `user/` (screens the user sends), `vision/`, `visual/` |
| `safety/` | `gate/` (confirmation gate, irreversibility decision), `guard/`, `verify/` (verification and sources) |
| `learn/` | `memory/`, `knowledge/`, `skills/`, `teach/`, `replay/` |
| `model/` | Model calls; `chatgpt/`, `oauth/` (account sign-in), `decision/`, `usage/` (token usage) |
| `device/` | Device access; `adb/`, `shell/` (built-in phone assistant), `access/` (the App access list) |
| Others | `proactive/`, `trigger/`, `mcp/`, `remote/`, `calls/`, `frontdesk/` (front desk), `search/`, `net/`, `export/`, `eval/`, `prompt/`, `self/`, `selfcheck/`, `workspace/` and other single-responsibility packages |

`:app` (`app/…`) has one package per feature at the top level (`chat/`, `task/`, `calls/`, `voice/`, `browser/`, `mcp/`, `settings/`, `files/`, …), and the feature's pages live in its own `ui/` subpackage (e.g. `chat/ui/`, `settings/ui/models/`). `ui/` holds only global shared items: `MainActivity`, `Navigation`, `components/`, `theme/`, `viewer/`, `terminal/`, Markdown rendering. `cap/` contains the Android implementations of each capability.

Components registered in the manifest (Activity, Service, Receiver, Provider) keep their original fully qualified names: the system stores these names (accessibility authorization, notification listener access, Quick Settings tiles, alarms), and changing the package name would invalidate the user's authorizations and scheduled alarms. The small packages `a11y/`, `sandbox/`, `shell/` and `setup/` exist as entry points for this reason.

## 2. Tasks and runs

### Run

A run is described by `RunSpec` (`core/run/RunContracts.kt`): `id`, `goal`, `threadId` (conversation), `priorTurns`, `provenance`, the capability subset `capabilities`, `readOnly`, `parent`, `stepBudget`.

- `RunProvenance` (`core/run/RunProvenance.kt`) records where this run came from and whether the user is present: `RunOrigin` = Ui / Channel / Trigger / Mcp / Child; `Attendance` = Present / Reachable / Unattended.
- Run phases `RunPhase`: Queued, Preparing, Running, WaitingUser, Parked, Paused, Finishing, Aftercare, Ended, Interrupted.
- "Who started this step" is another matter; see `Origin` in §4.

### Task center

`TaskCenter` (`app/task/TaskRegistry.kt`, held by `TaskService`) manages starting, queueing and finishing runs:

- Each conversation has only one Run at a time. If the user sends another message while a task is in progress in the same conversation, by default it is handed to the running Run as an interjection (`TaskService.begin`); the user can also choose 「排队」 (Queue) on the input field, and that message goes into this conversation's persistent queue (`FollowUpQueue`), becoming the next item when the current task ends.
- Tasks in different conversations can run in parallel, with the limit in §8; tasks over the limit go into a first-in-first-out queue and are filled in as Runs end (skipping conversations that already have a Run). When the parallel switch is off (the default), the UI cannot switch conversations while a task is in progress (`ChatViewModel.canSwitch`; other conversations in the sidebar `ChatDrawer` are not tappable and show a hint), and tasks handed to the service for another conversation (conversation page, floating capsule, browser page, schedule, computer) all go into the queue and are not lost (`TaskService.begin`). The conversation page first waits for the service to become idle before handing over (at this time that message shows 「等前一个任务做完再开始」 (Wait until the previous task finishes) underneath, `ChatViewModel.begin`), to prevent a new message from being treated as an interjection while the previous task in the same conversation is still wrapping up; if another task started somewhere else between the check and the handover, it is still queued, and starts after that task finishes. Tapping stop at this point only stops this conversation's task (`TaskActions.cancelIn`) and does not touch the one that is running.
- When a scheduled task is due and the original conversation has a task running, it queues in that conversation and waits for it to end (`queueInConversation`); it is not treated as an interjection and is not lost.
- Run state is written to `runs-v3.json` (`app/task/FileRunStateStore.kt`, atomic replace write).
- `app/task/TaskCenterState.kt` is only the state the UI needs to display (run list, parallel limit, interjection state, etc.).

### Inbox and interjections

Everything that comes in from outside during a run goes through `RunInbox` (`core/run/RunInbox.kt`); the kinds are `RunInput`: Steer (interjection), Redirect, Answer, Confirm, HandBack, Cancel.

- **Interjections add to the work**: everything already done is kept. Each interjection cancels the model request currently being waited on (`AgentLoop.routedOrRedirect`), and the question is asked again after the existing history; messages already sent are not changed by a single character, and the request prefix still only grows. Tool calls that have already entered the execution entry finish as usual and their results are recorded as usual, and the interjection is attached before the next model question (`AgentLoop.appendSteers`). Steer and Redirect take the same path.
- **Text already displayed when interrupted is kept**: if the cancelled request had already streamed out some text (the UI's `TaskState.Running.preview`), `AgentLoop.keepInterrupted` records that text in the history as a text-only reply, placed before the interjection, so that what the model sees when it asks again is the same as what the user saw; thinking content and half-written tool calls were never displayed anyway and are not recorded. Nothing is recorded if no text was displayed (streaming display was off, text had not appeared, or a retry cleared it) or if this batch has no interjections. The live text on the UI is cleared on the spot, and text that arrives late from the network thread after the cancellation is no longer displayed. This text also emits a run event `reply_interrupted` (after truncation and redaction), and `TaskRun` attaches it to the interjection that is handed to the model right after (`SteerNote.interrupted`); the conversation page shows it above that interjection in a light color, with a small line underneath 「被你的新消息打断」 (Interrupted by your new message); it is stored with this turn in the conversation (`Turn.interruptedReplies`, one-to-one with `steers`, with an empty string where there was no interruption) and is still displayed when the conversation is reopened. It is for the UI only and does not enter the context given to the model in later turns.
- **Replies already finished before the interjection are kept**: when a reply without a tool call has already been displayed and recorded in history, and only then an interjection is picked up (the reply just happened to finish first and the interjection arrived afterwards, or an interjection arrived while tidying up sources before handing over), `AgentLoop.keepFinished` turns that UI text into a run event `reply_finished_before_steer` (after redaction, not shortened: the UI needs the full text), clears the live text on the spot, and then attaches the interjection. `TaskRun` likewise attaches it to the first interjection in this batch (`SteerNote.finished`), and the conversation page shows it above the interjection in the same way as an answer (without marking it as an interruption), stores it with this turn (`Turn.finishedReplies`, one-to-one with `steers`); nothing is attached if no text was displayed. Interjections on the conversation page that have not yet been handed to the model are placed after the answer that is still growing (`steersAroundDraft`): that answer was being written before the interjection arrived, so when it finishes or is interrupted it stays in place and does not jump from below the interjection to above it.
- **When interjections enter the context**: `AgentLoop.appendSteers` takes the inbox before each model call at every step; when the model gives an answer without tools it first takes a look, and continues working if there is a new interjection. Before the answer is handed over (after checking and tidying sources), `RunInbox.closeUnlessSteered` looks and closes under the same lock: if there are still interjections it does not wrap up and continues with them; only when there are none does it close the inbox, and only then do later messages become the next item. When the model calls end_not_done itself, an interjection that just arrived likewise makes it continue; a guard stop or an error still ends the run.
- **Waiting ends early**: the inbox emits a signal that "there is an interjection not yet handed to the model" (`core/run/SteerSignal.kt`), installed in the coroutine context of the whole run. Calls that lose nothing when cancelled are wrapped in `waitOrSteer` and end early as soon as an interjection arrives: pure waits and tools that only ask a vision model (declaring `AgentTool.yieldsToSteer`: wait, phone_wait, phone_event, web_wait_for, describe, find_visually, wrapped uniformly by the dispatcher), waiting for text in `phone_run`, each segment of `do_steps` that waits for the UI by condition, the dwell before a web page change (`PageDwell`), and the interval between two outward actions on the same website or in the same App (`ActionExecutor`). A cancelled call reports `skipped_for_new_message` and did nothing this time; inside `do_steps` this step is skipped together with the following sub-steps. The moment after an action completes that waits for the UI to settle and judges the effect is not cancelled (it gives the action's result). The retry wait of a model call is already inside the model request and is cancelled with it.
- **Pacing protection is not lost**: when a dwell or interval is cancelled, the action itself is not performed (the tool result explains why, and it can be called again if needed). Both are measured by instants (the interval from when the previous outward action finished, the dwell from when this page arrived), the part that was not waited out does not count as waited, and the remaining time is made up before the next page change or outward action; an interjection only lets the model think now, and does not make the next action come sooner.
- **In the middle of a multi-step batch**: when `do_steps` finds an interjection between two steps, it stops there, the result states 「为处理新消息而跳过」 (Skipped to handle the new message) (`skipped_for_new_message`), and it does not count as a failure (`core/agent/BatchRunner.kt`). If an interjection arrives while a step has finished and is waiting for the UI by condition, the wait also stops immediately (that step's `wait.stopped` is `new_message`), and the following sub-steps are likewise skipped.
- **Immediate feedback on the UI**: when `TaskRun.steer` is successfully put into the inbox, the message is marked 「已收到，下一步调整当前任务」 (Received; the current task will be adjusted at the next step) (`SteerState.Received`); while the task is paused/taken over it shows 「已收到，任务继续后处理」 (Received; it will be handled when the task continues); when handed to the model it changes to 「已加入当前任务」 (Added to the current task); if it missed the wrap-up and was queued as the next item it is 「当前任务已结束，已排到下一件」 (The current task has ended; queued as the next item). The conversation page and the conversation card in the floating capsule both write this small line under the message (`steerLabel`).
- **Withdrawing and editing interjections**: by default a message is still inserted directly into the current task. Long-pressing a message on the conversation page that has not yet been handed to the model allows withdrawing it or taking it back for editing; `RunInbox.withdrawSteer` shares one lock with `takeSteers` and the wrap-up, and returns failure if it has already been handed to the model or the task has wrapped up. On success it is marked `SteerState.Withdrawn`, the conversation page and the capsule no longer show it, and it does not count as an added interjection. If the task has not yet been handed to the service, it is withdrawn from `ChatViewModel.held`. Editing restores the body and quotations; editing is not offered when the input field already has a draft, a quotation or an attachment; editing is not offered for interjections inserted by the floating capsule with a screen or by the browser page with page notes (`editableSteer`): when taken back, the start of the input field is the screen marker or several lines of the page note's original text, deleting it loses the screen and the page, and damaging it makes the page unrecognizable. Interjections appended by the computer (`SteerNote.remote`) are also displayed in the conversation, but withdrawal and editing are not offered, and the inbox also refuses withdrawal (editing would turn words that belong only to the current task into a phone interjection, possibly converting it into the next item; whether to withdraw is decided by the computer); `remoteSteers` reports `Withdrawn` as `not_applied` and does not add an outward-facing state.
- **Interjections that were not handled in time**: interjections not yet consumed when the run ends become this conversation's next item if the user did not press stop; if the user pressed stop they are dropped (`TaskRun.handoffUnconsumed` only handles those unconsumed at wrap-up). An interjection that arrives after the run has closed is queued as the next item when `TaskRun.steer` cannot put it into the inbox, or when `TaskService.begin` finds that the task has already wrapped up.
- **Queueing (`FollowUpQueue`, `app/task/FollowUpQueue.kt`)**: messages the user explicitly chose to 「排队」 (Queue) and steers that missed the wrap-up all go into the same FIFO, separated by conversation, persisted in `files/followups-v1.json` (temp file + flush + atomic rename; a corrupt file is moved to `.corrupt-<timestamp>`). All additions and removals write to disk first and then publish the in-memory state; if writing fails, the UI never shows a "queued" state; the segment where the main conversation first waits for the service to become idle also only writes to disk and does not start early. Attachments are first copied into the conversation workspace, and their paths are then queued together with the original words; capsule screenshots are also saved first. The service calls `TaskCenter.tryStart(..., followUp)` to decide under the same lock whether to start or put it back in the queue; `onRunEnded` takes only **this conversation's** next item, one at a time via `claimNext`; after `cancelQueued` it also takes the next item, so that items queued behind are not stranded. Items in the capacity queue are likewise kept until the actual `markRunning` before removal, and cancelling while capacity-queued removes them at the same time. `claimed` lives only in memory: if the process is killed between taking an item and registering the run, after restart the item is still pending; after registration, the `followUpId` in the run record handles deduplication and reconciliation, so it will not be executed twice. Stopping the current task does not cancel items explicitly queued; the queue file is kept after the process is killed or exits, and is not automatically started at launch; the next time a conversation is opened, `ChatViewModel.openConversation/switchTo/refresh` calls `TaskService.drainFollowUps`. The UI uses `app.followUpQueue.changes` to show the queue bar above the input field; the steer fallback is shown by the `SteerState.Next` line on the interjection line and is not displayed twice.
- **Stop**: Cancel is a control signal and is not queued behind interjections. `TaskRun.cancel` cancels child tasks at the same time; if a takeover is in progress it ends the takeover; items in the queue are removed directly.
- **Account after stopping**: the UI immediately shows stopped and the input field becomes free; then a few lines of account are added as this turn's answer (what was done, what was seen, how many times batched actions were sent and which ones, which were not finished), and the outcome is still cancelled (evaluation, result classification and learning all count it as cancelled). When `TaskService` wraps up, it first registers the run number in `TaskCenterState.summarizing` (the UI uses this to write 「正在整理已做的事…」 (Organizing what was done…) under "stopped"), records the "cancelled" turn, then writes in a process-level scope via `TaskRun.stopSummary`, and when done uses `ConversationStore.updateTurn` to update that turn; whether writing succeeds or fails, the registration is removed; it does not block the wrap-up, the next item, or another stop tap. The writing is in `StopSummary` (`core/agent/StopSummary.kt`): it only reads this run's record (activities, the intent of each step, the two most recent passages read, the half-written text when stopped, all bounded, without images), asks a model once (preferring a lightweight model, falling back to the main model on error, no tools, 12 seconds total), and if there is no model, an error or a timeout, it assembles directly from the record (`StopSummary.plain`). Outward actions (send, submit) are counted by the `outward` flag on the activity (`ActionExecutor` marks it according to the irreversibility decision). If nothing was done and no text was written, it just says it was stopped. In the next turn's context it is written as "the user stopped this task partway; before the stop: …" (`Conversation.context`), so that "continue" knows where to pick up. The original text read in earlier turns does not enter the context; when it is needed the model looks it up itself (`history_read`, see "Records of earlier turns").

### Delivery

Results, questions and notifications are sent through `Outbox` (`core/run/Outbox.kt`): first record what is to be sent, then send. States Pending → Attempting → Delivered / Failed / Uncertain; the same delivery id is sent only once; one whose result is unknown halfway is marked Uncertain and not retried automatically. Records are in `outbox-v3.json` (`app/task/FileOutboxStore.kt`).

Channel tasks only send one acceptance confirmation, and do not forward run phases or step counts. After a task is persistently registered, it enters `Outbox` as a `Notice` with `accepted:<run key>`, and sending does not block task execution; a redelivery with the same channel message id does not create a task and does not confirm again; different ids are registered separately even if the text is the same, and are executed in order in the same conversation. Questions, confirmations and takeover still only go through `ChannelInteraction`. The result chain separately records the milliseconds of each segment — main loop completion to sending, Outbox plus sending, WeChat HTTP — without recording message content.

The local channel is `LocalChannel` (`app/task/LocalChannel.kt`): the local UI plus system notifications. `WechatChannel` (`app/wechat/`) is the second channel: a single account, the owner's private chat text and images, credentials stored encrypted on the device, an independent foreground service long-polling, no relay server built, and no separate task state machine. Inbound messages are first written to the pending ledger and then the sync cursor is advanced; `TaskCenter` confirms only after deduplicating persistently by channel message id; after a process restart, unregistered messages are submitted first. Task records save the source `ChannelPeer`, and questions, results and `RunRecovery` are all routed by source. The channel interfaces `Channel` and `ChannelGateway` (owner identity, question id correspondence, payment confirmation only on a channel that can confirm, `Channel.confirms`) are in `core/run/`; WeChat has `confirms=false`, and payment confirmation and phone takeover still go through the phone.

WeChat image sending and receiving reuse the existing workspace attachments and task export files: inbound images are downloaded in a batch, decrypted and imported, then the attachment paths and the original words are first recorded in pending, and then handed to the task; outbound sends only images explicitly exported by this task, and each image and its text has its own Outbox record. The screenshot tool can save to the workspace with `savePath`, and then deliver it via `share_file`. For image limits, failure and recovery semantics, and verification entry points, see [WeChat image sending and receiving](wechat-images.md).

Automatic screen wake and unlock for WeChat tasks is separately authorized by `WechatStore.allowUnlock`, off by default; the authorization is stored independently in `unlock.json`, bound to the current owner and bot, and a missing, corrupt or mismatched account is treated as off. Revocation only deletes the authorization file and does not change the message ledger; when turning off receiving, a failure to write to disk also revokes the authorization, to avoid restoring an unlockable state after a restart. Unlocking is not possible while receiving is off; unbinding or rebinding by scanning the code each time revokes the authorization, while rebinding the same account still keeps the message ledger. `canUnlock` checks the current binding, WeChat channel, owner and thread mapping every time. `taskUnlockAuthorization` (`app/task/TaskUnlockPolicy.kt`) provides the `TaskGate` unlock callback only for scheduled tasks and for the owner's WeChat tasks that were already authorized when they started running; other sources or unauthorized tasks still wait for a manual unlock. The WeChat callback re-checks the authorization dynamically at the moment of actual unlocking and does not carry over a revoked permission. This switch does not modify `DeviceAccessSettings.enabled` or lock-screen credentials, still requires the existing local device access permission, and does not change `RunOrigin.Channel` or the payment and takeover rules.

### After a process restart

- `RunRecovery` (`app/task/RunRecovery.kt`) is the single entry point for run aftercare, for runs that were "interrupted and the user has not been told yet". Two occasions: after a process restart, `MikaApp.onCreate` calls `recover` as soon as it starts (`TaskService.onCreate` also calls it, but only the first one in the process takes effect, and later ones do nothing); when the task service is destroyed while the process is still alive, `TaskService.onDestroy` marks the interruption and then calls `settleInterrupted` on the spot, without waiting for the next launch (aftercare uses an App-level scope, so it finishes even after the service is gone; the startup scan then picks up those that were killed before finishing on the spot). Marking is done synchronously inside the call (`RunStore.interruptUnfinished()` marks unfinished runs as Interrupted, excluding runs that are running at that moment via `live`), and aftercare is done in the background: a reply that was stored but not delivered is delivered once more (noted as recovered); an unknown delivery state is not resent, only 「上次结果可能已送达」 (The previous result may have been delivered) is shown; when there is no reply, a system notification 「运行中断,可在对话里重新发起」 (The run was interrupted; you can start it again in the conversation) is sent, and a failure-state record 「任务中断了,可以重新发起」 (The task was interrupted; you can start it again) is written into the conversation (the same set as other failure results, displayed in the UI as an unfinished turn). **"Already told" does not get a separate field; it is read from the delivery ledger**: if there is any one of `interrupted:<run>`, `uncertain:<delivery>` or `failed:<delivery>` notice record, it is not processed again; a run whose reply was delivered becomes Ended. So repeated calls, or both occasions colliding, only notify once. **Never resume from the middle**: the screen state cannot be restored.
- `TaskRecovery` (`app/task/TaskRecovery.kt`, run when the App starts) restores system state rather than runs: an App muted during the task gets its sound back, and a clipboard borrowed during the task is returned to the user.
- Child run records have Running changed to Unknown when loaded and are not re-run (`app/task/FileChildRunStore.kt`).
- Handling of scheduled task windows is in §10.

## 3. Main loop

`AgentLoop` (`core/agent/AgentLoop.kt`) only does scheduling; the specific decisions each live in one class:

| Class | What it does |
|---|---|
| `ModelCaller` | Assembles requests, calls the model, streams output; compression and backfill, retries for temporary errors, retries for oversized context, routing between large and small models |
| `RetryPolicy` | Bounded retries for 429, 5xx and network loss (at most 3 times, exponential backoff, with an overall wait cap per task) |
| `ToolDispatcher` | Finds tools by name, holds the evidence ledger, assembles each capability's prompt section |
| `TurnPolicy` | Progress checks (only when there is a step limit), a reminder once on an empty or truncated reply, one fallback when a tool call leaks into text, one reminder when follow-up is due, one fallback when the answer's language changed, and only `end_not_done` on the last turn (only when there is a step limit) |
| `StopRules` | When to end: giving up, a guard stop (repeating the same action, no progress, repeated reading, too many failures, going in circles in the sandbox), model failure, steps exhausted (only when there is a step limit) |
| `BatchRunner` | `do_steps`: give 1–20 known actions at once, execute and verify them one by one; a step can carry wait conditions (`expect` appears, `expect_gone` disappears, `expect_app` foreground App or page address, `wait_stable: true` UI stable, `timeout_s` default 8 seconds, at most 20 seconds), and after doing it, code reads the screen until the condition holds before the next step, no longer asking the model about "still loading"; stops early on a dialog, a window from another package covering the screen, or an App change, and writes `wait` (`met`, `stopped`, `waited_ms`) into the result. The waiting itself is in `core/screen/uistate/UntilWait.kt`, shared by phone and web, waking through the port's `awaitChange` (accessibility event / page change); waiting time counts as waiting in the run summary, not as operation |
| `IntentGate` | When a task started from the conversation UI first wants to use a non-lookup tool, judges whether the user is chatting, looking up information or asking for something to be done; if it is chat, answers again without tools. When it cannot tell (the call failed, or the reply is not one of the three words), it follows the main model's original decision; judged only once per run (`AgentLoop.assessIntent`) |
| `StuckAdvice` | Adds advice to the tool result when stuck; on the second time stuck, suggests giving up |
| `NoticePolicy` | After looking at a screen, decides whether to supply the model with knowledge about the corresponding App/website |
| `GuideRecommender` | The opening index: picks at most 3 pieces of App/website knowledge based on the task text, and separately lists all skills (built-in ones and personal skills in use or on trial); the model reads the full text itself with `skill_read` |
| `RouteReplay` | When "do it the way I did last time" is turned on, replays a matching successful route before the first model call (see §9) |
| `UserExchange` | The three interactions that need user participation: follow-up questions, confirmations and takeover |

Step limits are not set by default: Settings › Task runs › Step limit per task (`FeatureFlags.taskStepLimit`, 1–500, storing 0 means unlimited). `TaskRun` reads it once when starting, puts it into `RunSpec.stepBudget`, and then as `AgentLoop`'s `maxSteps` (the evaluation's `EvalHooks.maxSteps` takes precedence; when neither exists it is `AgentLoop.UNLIMITED_STEPS`); changing the setting midway only affects tasks started afterwards, and a task that was interrupted does not resume, so it does not pick up the new value either. When there is a limit: guards are graded by it (`OperationGuards(maxSteps)`; the thresholds for the three kinds of stop — returning to the same state, going in circles, and never reaching a new state — are computed as a fraction of the limit, see `GuardRules.lateStop`; when unlimited these levels of stop never arrive), progress is reminded at the halfway and three-quarter points (when the limit is at least 10 steps), and after the steps are used up there is one final wrap-up turn (only `end_not_done` is offered, counted as step limit plus one), and if the wrap-up does not answer either, the run ends with `FailKind.StepLimit`. The start event records this limit (`RunEvent.TaskStarted.stepLimit`, not written when unlimited, also present in the summary), and the run details page displays 「用了几步 / 上限」 (steps used / limit) from it (the wrap-up turn is not counted and does not exceed the limit); when unlimited this line is not shown.

What the setting currently covers (all through `TaskRun.execute`): the conversation UI (including the floating capsule and asking on the browser page), schedule-triggered tasks, and tasks handed over by the computer via CLI / MCP all follow the setting; a schedule's condition check (the read-only check) is not governed by it and is always unlimited; child tasks do not look at the setting, and their step count is decided by `spawn_agent` itself (15 steps by default, the model may ask for up to 40, `SpawnAgent`), and is not counted toward the parent task's steps.

### Result judgement

- **There is no "done" tool**: a reply from the model without any tool call is the answer; text attached to a tool call is displayed as process explanation. The text recorded when a reply is interrupted by an interjection is not an answer, it only lets the model know what the user has already seen (see "Inbox and interjections").
- **`end_not_done`** (`core/general/OutcomeTools.kt`): when something cannot be done or only partly done, use it to finish; `message` states clearly what was confirmed done, where it got stuck, and what is on screen now; `subtype` is one of `blocked`, `login_incomplete`, `captcha_incomplete`, `route_failed`, `device_unavailable`, `interaction_failed`.
- **Before handing over the answer**: an empty or truncated reply gets one reminder; some inference services occasionally fail to parse the model's tool call and the call becomes the body text as-is (`LeakedToolCall`, `core/agent/LeakedToolCall.kt`: a common call marker followed by a Claire tool name), which is not an answer: it falls back once and lets the model call again through the tool interface, and records `tool_call_as_text` in the run record; if it leaks again immediately it ends with a model error (`StopRules.toolCallAsText`), never handing the raw marker to the user, and the count restarts after a normal tool call; if the user just answered something and the Agent did nothing, one reminder; if the last action that changed the UI did not read back its result, one reminder. If the answer's body is clearly not in the language of the user's most recent message (`ReplyLanguage` counts by the script each letter belongs to, Han characters by character and the rest by word, not counting original text inside quotation marks and brackets or lines that only list names; the user's message counts only what they typed this time, not the screen, the browser page's page notes, the quoted passage, attachment lines and interjection markers it carries (`UserWords.typed`); not checked when the opening only sent a screen, only selected text or only carried an attachment, and for an interjection that only sent a screen or only selected text, judged by the previous message), it falls back once and has the model rewrite the whole thing in the user's language, and if it is still wrong after the rewrite it is handed over anyway.
- **Sources are generated by the system**: `AnswerSources` (`core/safety/verify/AnswerSources.kt`) picks the observations that support the answer from the evidence ledger `EvidenceLedger` (at most 6), as the "sources" below the answer; the model does not write them itself.
- **Background result classification**: after the answer is delivered, `TaskRun.settleOutcome` uses `OutcomeJudge` (`core/agent/OutcomeJudge.kt`, preferring a lightweight model, 30-second timeout) in the background to classify this run as one of `RunOutcome`'s Done / Partial / NotPossible / Unknown. It does not change the answer; the result is written to the run record and the conversation record; scheduled tasks use it to mark whether this run failed. Learning and replay only accept Done: admission is decided in exactly one place, `LearnGate.done` (`core/agent/LearnGate.kt`): an answer was handed over, it was judged Done, and there is no value that still does not match after a fallback; if verification ran, it must also have passed (running and failing still blocks, not running does not block). Drafting personal skills and App knowledge, moving a trial to formal, and recording experience routes and success counts all ask only it (see §9, §11); whether to record a route is decided in one place, `LearnGate.shouldSaveRoute` (routes are on, the task succeeded, there is a run id, and the goal does not carry the user's screen).
- **Independent verification**: `Grounding` (whether the numbers, ids and quotations in the answer appear in what was read, and whether the arithmetic is right) and `Verifier` (an independent verification model) are both in `core/safety/verify/`, controlled by the `reviewFinalAnswer` switch. The product currently has it off (`reviewFinalAnswer = false` in `TaskRun`), so all answers are recorded as "unverified", see "Known issues" in the roadmap; learning looks at the outcome judgement and is not affected by it.

## 4. The single execution entry point and tools

- **Single entry point**: every action that changes the outside world goes through `ActionExecutor` (`core/action/ActionExecutor.kt`). `ToolDispatcher.execute` requires an `ActionPass` (`core/tool/ActionPass.kt`), whose constructor is internal and which only `ActionExecutor` can create, ruling out bypasses at compile level; read-only calls go through `executeRead`, and anything not read-only is rejected. The order is fixed: guard → lock-screen check → irreversible action check and consent → execute → post-action verification → record.
- **Interval between outward actions** (`core/action/OutwardPacing.kt` pure logic, `ActionExecutor` waits according to it): when sends and submits recognized by the irreversibility decision (including buttons that contact someone or submit an application with one tap, such as 「立即沟通」 (Chat now), 「打招呼」 (Say hi), 「投递」 (Apply), 「Say hi」, 「Easy Apply」) are done in a row on the same website (by registrable domain) or in the same App (by package name), the first one does not wait, and afterwards each one is separated from the previous by a random 8–20 seconds; the more done in the last 30 minutes, the more the lower and upper bounds each increase by 0.5 / 1 second, up to 30 seconds; it counts from when the previous one finished, including the time spent reading pages and thinking about the next step in between, whether or not the page changed (the dwell on a page change is separately governed by the web pacing). Phone and web use the same decision and the same set of intervals; during autonomous execution the decision still runs to recognize outward actions (based on the screen the model currently holds, without reading the screen separately), but it does not block. The wait is after the decision and before the action starts, and the task can still be cancelled during it; how long it waited is recorded in this call's `waitMs` and is not counted in operation time. It is installed only by the App's tasks (`AgentLoop(outwardPacing = …)`); core tests do not wait by default.
- **Who started this step**: `Origin` (`core/action/Origin.kt`) = Model / Batch / Script / Replay / McpTool, each with its own policy (whether it can use the user's consent to let a payment through, whether it stops on a guard warning). Each action inside a composite tool (a multi-step batch, `mika phone` in the sandbox, web scripts) returns to the same entry point through `SubActions` (`core/tool/SubActions.kt`), on the same execution and recording path as single-step tools.
- **Tool declarations**: one class per tool, implementing `AgentTool` (`core/tool/AgentTool.kt`), declaring its verb, risk (Read / Write / External), capability, whether it can join a multi-step batch, whether it can join an experience route, its concurrency mode, etc.; code acts on these attributes and does not hard-code tool names. `ToolRegistry` filters the available tools by task, and a task's tool definitions are frozen once set.
- **Tools are in two layers, expanded only when used** (`core/tool/ToolGroups.kt`, `ToolDispatcher.offeredNow`): always present are the general tools (ask the user, end when not done, wait, knowledge and skills, memory, schedules, child tasks, …) and the capability that is never withdrawn (MCP); phone, web and sandbox are each a group (`Capability.folds`), and at the start only the entry tools are given (`AgentTool.entry`), with a short description from `prompts/entries/<tool name>.md`: after `phone_launch_app`, `web_navigate` or `run_command` is called, its group is expanded (`Entry.Opens`), while `phone_list_apps` and `web_read_page` (read the body of a URL) are enough on their own and do not expand (`Entry.Alone`). Takeover, reporting an obstacle, looking back at screens and multi-step batches are only given after a group with screens is expanded (`AgentTool.withScreens`, counted as the `screens` group). After expansion, the whole group's full text is given from the next request, the entry switches to the full text, and the capability's description section (`capabilities/<capability>.md`) is also spliced into the system prompt and kept for the rest of the task; `moreTools` in the result says a word about it. If the model calls a withheld tool from memory, it still executes as usual and likewise expands its group (it expands even with wrong parameters, so the full text can be seen and corrected next time). The order is fixed: always present → `screens` → phone → web → sandbox; expanding a group only changes the part from that group onward, and the request prefix is invalidated at most once because of expansion. Pre-expansion at the start: groups actually used in the previous turn (`Turn.groups`, recorded by `AgentLoop.usedGroups` and stored in the conversation file; entry tools that are enough on their own do not count as used), and capabilities deemed certainly needed by this message (the sandbox when carrying files from the workspace, `Capability.preload`). In a read-only task commands are not offered, and the sandbox group has no entry, so it is expanded from the start. Child tasks, schedule triggers and other sources are all the same. The run record records expansion as `tools_opened` and pre-expansion as `tools_preloaded`; `PromptVersion` is computed as if every group were expanded, so the same prompt version does not differ because of which groups were expanded this time.
- **Approval**: `ApprovalPolicy` (`core/action/Approval.kt`) asks about only one kind of action: the step that spends money (`Risk.payment`: a payment or order recognized by the irreversibility decision, or, when the screen has an amount due with a currency (¥, yuan, $), an outward or irreversible action that matches the decision, see `ClassifiedRisk`; characters on a Traditional Chinese UI are first converted to Simplified and judged with the same word list, `core/screen/uistate/Hant.kt`). Everything else is done directly: sending, posting, submitting, deleting, contacting others, changing account or security settings, typing into password fields, taps found by looking at an image but whose nature cannot be told, and taps whose target cannot be read are never asked about. The money-spending step is asked about only when it was started on the phone with the user present (`Ask`); runs started from channels, schedules or MCP, child tasks and runs with nobody present cannot ask anyone, and are always rejected (`approval_unavailable`). There is only one kind of consent: it lets through only the immediately following matching operation (`ConfirmationGate`: same App, same kind of action, the object is on screen, the declared amount is on screen, within 3 steps, with no other write operation in between). Payment itself (judged as pay) does not go through consent and is handed to the user to pay personally (`hand_to_user`, reason=payment). All approval conclusions are recorded in the run record (`RunEvent.Approval`: outward ones, money-spending ones, and ones not let through), and verification uses this to know that the task did outward things. There are no approval levels, and no per-task or long-term grants.
- **Ask / autonomous**: one global switch, in the first group 「做事方式」 (Working style) in Settings › Task runs (「自主模式」 (Autonomous mode), test tag `work-autonomous`), off by default, which means ask; the value is stored in `ApprovalStore`'s JSON (`autonomous`). `ApprovalControl` (`settings/ApprovalControl.kt`) gives each task a `RunApproval` when it starts (whether it is autonomous comes from the global value), and `TaskRun` installs accordingly: when asking, `confirmations = ConfirmationGate()` and `autonomous = false`, the money-spending step is blocked as `confirmation_required`, and for orders and the like the model calls `request_confirmation` (it must write the amount on screen; an application that cannot write the amount is rejected directly and not given to the user), and the user answers on the card in the conversation page, the card in the floating capsule or the notification (agree only this time / do not agree), and the answer goes through `TaskService` → `TaskRun.confirm` → `RunInbox` to the loop; when autonomous, `confirmations = null`, `autonomous = true` and `request_confirmation` is not offered, the decision still runs (and outward action intervals are still honored) but even payments are not blocked. Changing the switch (`ApprovalControl.setAutonomous`) saves it for later tasks, and running tasks switch along with it: a task that was asking at start and is switched to autonomous midway is no longer blocked from the next step (a confirmation already popped up still waits for an answer); a task that was autonomous at start and is switched to asking midway leaves it for the next task (tools and prompts do not change within a task). Tasks started in the floating capsule, tasks continued from a chat, child tasks and schedule triggers all follow this switch; tasks handed over by the computer via CLI / MCP are the exception: `ApprovalControl.start(remote = true)` always starts as asking and does not follow the switch, and the payment step is never done in such tasks (see the "Computer connection" section); child tasks are read-only anyway, and when asking they pass the gate, and any money-spending step is rejected. Runs with nobody present, such as scheduled tasks, do not pause and wait for someone when they hit a money-spending step in ask mode: the execution entry rejects it directly (`approval_unavailable`), the model truthfully says which step was not done, the rest is finished as usual, and the result is notified as usual. In autonomous mode `ConfirmationGate` does not exist, and the early return for autonomous in `ConfirmDecision.judge` comes before the "do not act on Claire itself" (`ownApp`) check, so this protection does not take effect in autonomous mode; when asking, Claire does not operate itself.
- **Old tool names after renaming**: `LegacyNames` (`core/tool/LegacyNames.kt`) maps old names to current tools, and is used only to read old routes, run records and personal skills; when the model calls an old name, it is only told the new name and the call is not executed for it.

## 5. Observation, action, place

- **Observation** is the only unit the core consumes: `Observation` (`core/screen/observation/Observation.kt`) carries kind `ObsKind` (Read / Output / Reply / UserSaid / Attachment / Fact), provenance (capability id), place, title, text, image, confidence, step, time and id. The evidence ledger, sources, verification and run records all read it.
- **Untrusted content** (web pages, child task results, etc.) is wrapped once in `<untrusted>…</untrusted>` when the observation is built (`core/screen/observation/Untrusted.kt`).
- **Place** `Place` (same file): App, Site, Page, Command, File. Knowledge is supplied to the model by place (§11).
- **UI state** (`core/screen/uistate/`): control tree, element ids and staleness detection, waiting for the UI to settle, action effect (`ActionEffect`: every action that changes the UI reports back the actual effect, and input is read back and verified; on the phone, when a tap or gesture shows no visible change but the tree for this screen cannot read that spot — the tree is unusable, or a part is missing and the tap is not on any element — the kind is still `no_effect`, additionally marked `treeBlind`, and the hint says instead "no visible change does not mean it was not tapped", and does not say it probably was not tapped; what is done by kind (consecutive no-effect reminders, multi-step early stop, statistics) is unchanged; in the UI after the action, short new text 「到上限了」 (limit reached) — such as use count exhausted, limit reached, come back tomorrow, too many operations, limit reached — in a hint bar, dialog or page popup does not count if it was already on screen before the action (`LimitNotice`) — the result writes `limitReached` and a stop hint, and a multi-step batch stops at this step). Phone and web share this. The dispatcher, before and after each call, uses `SurfaceLayer` to have it do the UI preparation and wrap-up (take a look before the action, compare out the effect, attach the UI after the action); the tool engine itself does not know it (see §1). The execution entry's irreversibility decision and approval, and replay when judging by screen reading, use it directly (`ActionTarget`, find a target by description).
- **Visualization** (`core/screen/visual/`): frame ids, `view_past_screens` look-back, frame differences. The image is only there so the user can see what Claire is doing and as supplementary observation when text cannot be read; getting things done relies on UI state.

## 6. Capability modules

Capabilities are assembled by `CapabilityProvider` according to `RunSpec` (`core/assembly/RunAssembler.kt`, `TaskTools.kt`), installed once at the start of each Run:

- Capabilities are chosen by `spec.capabilities`; runs with nobody present drop the tools for follow-up questions, confirmations, takeover, creating schedules and editing the profile; read-only runs keep only read-only tools (plus opening a URL on the web).
- General tools (`core/general/`) are always present: `ask_user`, `hand_to_user`, `handle_obstacle`, `end_not_done`, `wait`, `view_past_screens`, etc. Offered only when conditions are met: `request_confirmation` (ask the user for consent before spending money; only when there is a confirmation gate: ask mode, someone present), memory tools (only when 「使用记忆」 (Use memory) is on), knowledge and skill lookup (only when there is a knowledge catalog, `LookupTools`), `schedule_task`, `spawn_agent`, `history_read` (only when there are run records and earlier turns that recorded runs), `notices_read` (read the original notifications from the last two days, plus the stored daily, weekly and monthly summaries; only when the proactive capability's 「当日消息归纳」 (Same-day message summary) is on, the aggressiveness is not the most conservative level, and the task was started by the user on the phone), `web_search` (only when the user has configured a web search service in Settings; when not configured it goes through the browser).

### phone: phone Apps

- **Virtual screen**: the task operates Apps on a separate virtual screen while the user keeps using the phone as usual. The virtual screen is created by the built-in phone assistant (`app/cap/phone/display/AgentDisplay.kt`, `app/cap/phone/shell/ShellService.kt`), with the same size as the main screen; from Android 14 it has its own focus and does not affect main-screen input (on Android 12 and 13 the main screen's focus may be lost briefly, and Settings shows a hint; below Android 12 phone Apps cannot be operated, while chat, web and the sandbox remain available). It connects and creates the screen only the first time an App, a link, a system command or event listening is needed; tasks that use only the web or the sandbox do not touch it. The target App is muted on the virtual screen, and the sound is restored on takeover. Muting works by setting the App's `PLAY_AUDIO` to ignore, with the rules in `app/task/AppMuter.kt`: mute before Claire sends the launch (opening an App, opening another copy, sharing, opening a link that names an App or has only one App that can receive it, system actions that open a UI; alarms and timers set quietly are not muted), and the first few seconds are also silent; if the launch is refused, the early mute is reverted; afterwards, every new App that appears on Claire's screen (one opened from the target App, another copy coming to the top, rereading the top task on Claire's screen on accessibility window changes, `AndroidScreen.foregroundApps`) is muted the first time it is seen. Muting acts per "package + user" (`AppAudioKey`: the original copy is the package name, another copy is "package name@user number", and the built-in assistant's `*InUser` interfaces carry `--user`), so the copy in a clone or work profile is muted separately and does not affect the user's original copy. Not muted: Claire itself; system packages with no launcher entry (system UI, chooser, permission dialogs); whatever the user can currently see on the main screen (the assistant's `visibleOnMainScreen`, treated as in use when the main screen cannot be seen clearly) — muting acts per package, so muting the user's own copy would silence it too, and in that case the progress notification truthfully says 「该 App 可能会出声」 (This App may make sound), and likewise when the mute command fails. When muting is turned off in Settings, nothing is muted. At wrap-up, `AudioMute.restoreAll` restores everything muted during this task, including mutes applied midway; the original mode before muting is recorded in the assistant's ledger file (`app/cap/phone/shell/AudioMuteLedger.kt`), and the assistant restores on startup anything it did not get to restore last time. Restore rules: an explicitly set allow/ignore/deny etc. is written back as it was, an unset one is written as allow without writing default (Android only plays sound for allow), and only packages in the ledger are touched.
- **Orientation of the virtual screen**: after the virtual screen is created, it is first set to fullscreen windowing mode (`setFullscreenWindowingMode`; some systems give new screens freeform by default), and if the interface is unavailable it falls back to `wm set-display-windowing-mode`. To avoid stealing main-screen focus, the virtual screen carries STEAL_TOP_FOCUS_DISABLED, so some systems do not honor rotation requests from Activities on background screens, and landscape Apps end up shrunk into portrait with black bars. From Android 14, when there are Claire screens the built-in assistant starts an orientation watcher (`app/cap/phone/shell/DisplayOrientationWatch.kt`): it registers a task stack listener with the task manager (ITaskStackListener), and task changes are coalesced into one scan (`CoalescedScan`, events within 50 ms are scanned once); if registration fails it falls back to scanning every 500 ms, only while there are Claire screens, and stops after all screens are released. Each scan (`ShellService.syncDisplayOrientations`) takes one snapshot of Claire screens under the lock, and queries tasks, reads fields and changes orientation outside the lock, so it does not block creating or releasing screens; for each Claire screen it reads the top task's letterbox field (`appCompatTaskInfo`: `topActivityBoundsLetterboxed` from 15, and on 14 it reads the app window width/height from the task directly, but some letterbox modes do not fill in the width/height); when the size is valid it computes by the app window's landscape/portrait, otherwise it uses the Activity/Task requestedOrientation saved by the watcher to decide a fixed landscape/portrait request (the static `topActivityInfo` does not reflect runtime `setRequestedOrientation` and cannot replace the callback), then computes where it should rotate from the screen's current orientation (pure logic `DisplayOrientation.rotation`, and leaves it alone when consistent), and uses the hidden interface `IWindowManager.freezeDisplayRotation` to lock only this screen, falling back to `wm user-rotation -d <display> lock <rotation>` when the interface is unavailable; the main screen is not touched. Below Android 14 the watcher is not started and things are displayed as before. On the image side (`AgentDisplay`, `DisplayFrame`): the physical buffer is unchanged, each frame is turned upright according to the screen's current orientation (`DisplayFrameGeometry`), and the preview is limited to 360 pixels on the short side, so a landscape screen does not end up as just a low-resolution strip.
- **Apps when the task ends**: by default they are left in place and are not destroyed with the screen. At wrap-up (in `TaskRun`'s finally, before `AudioMute.restoreAll` restores muting) `AppsAfterTaskEnd` hands the keep/close decisions marked by the model (`phone_app_after_task`, stored in the phone port's `AfterTaskMarks`) to the built-in assistant's `finishDisplay`; the assistant decides each task's fate according to `app/cap/phone/shell/AppsAfterTask.kt`: marked ones follow the mark; unmarked ones that are making sound right now are closed (it first asks `AudioManager.getActivePlaybackConfigurations`, taking uids whose player state is started → package + user; when the uid is hidden it reads `dumpsys audio`; ones muted by Claire also count as playing; when none can be read, ones currently muted by Claire count as playing), otherwise they are left; Claire's own pages and anything that is not an ordinary App page is always closed. A left app is moved to the main screen and placed at the very back: `WindowContainerTransaction.setHidden(true)` → `moveRootTaskToDisplay(…, 0)` (the system always puts it on top, and while hidden it is not shown and does not take focus) → in the same transaction `reorder(…, false)` + unhide; after moving it looks again at ones making sound (one without a keep mark that makes sound is moved back to Claire's screen and closed with it), then waits for the TO_BACK transition to end (during this `TaskInfo.isVisible` is still true, so one reading of "visible" cannot be taken as failure): it checks every 100 ms, `reorder`s again every 750 ms while still visible, and waits at most 2 seconds, with the rules in the pure function `app/cap/phone/shell/SettleBehind.kt`. While waiting it does not hold the launch lock (moving and wrapping up are in the lock, with it released in between), and other tasks can open Apps as usual; a left task is recorded as "left" only at wrap-up, so a later open while waiting will not take it, and once another task takes over its screen it no longer counts as left. A task still visible at 2 seconds cannot be left in front of the user: it goes back under the lock and looks once more, and if still visible it is moved back to Claire's screen and closed with it (only if it cannot be moved is `removeTask` used, the same path as moving it over and it making sound), and the result records it as not left (reason `still_in_front`, with the diagnostic 「still visible on main, closed」); one that has already receded to the back is left. If unhiding after moving did not succeed (it stays hidden and cannot be seen in Recents), it is still left, with the diagnostic 「N left hidden on main」, and the next time the same copy is opened it is moved back to Claire's screen and unhidden; a cold start closes it first as usual. The screen still carries `FLAG_DESTROY_CONTENT_ON_REMOVAL`, so anything not moved is closed with it. If hiding or moving itself is unavailable on this system (interface missing, rejected), it no longer moves and closes with the screen as before, recording one line in the diagnostics 「apps after task: … move not supported」 (the run record has the `apps_after_task` details). The assistant remembers the ids of left tasks (only in memory); the next time `startApp` (including another copy) opens the same App, if that task is still behind the main screen and the user is not looking at it, it moves the whole thing back to Claire's screen and continues, without opening another; a cold start closes it first and starts from the beginning. When only releasing the screen (`releaseDisplay`, the assistant's `releaseAll` on unbind), everything is destroyed as before.
- **Built-in phone assistant**: a helper process running with shell identity, started through the phone's own 「无线调试」 (Wireless debugging) (`app/cap/phone/setup/BuiltinShellManager.kt`, `app/cap/phone/shell/HelperProcess.kt`; the ADB protocol is implemented itself, in `core/device/adb/`). Pairing once is enough: the pairing code can be read automatically by the accessibility service from the settings page, or entered from the notification or the setup wizard. The fill-code notification (`app/cap/phone/setup/PairingNotifier.kt`, sent by `PairingCoordinator` according to the assistant state and the progress in finding the pairing window) adds no screen recording or overlay permission and relies only on the notification itself: the 「配对」 (Pairing) channel is high priority, with sound and vibration, and can pop up above the system pairing window; a channel's importance cannot be changed by the App after creation, so `PairingChannel.plan` looks at existing channels — if there is none, create one; if an old version created it not high enough and the user has not changed it (`hasUserSetImportance`), rebuild with a new id; if the user turned it off or set it not to pop up, do not change it back; `SystemStatus.pairingChannel` gives it to the guide page (`SetupView.notifyIssue`): when notifications are not allowed or the channel is off, the pairing step's main button first goes to allow notifications / open this channel's settings page, and setting it not to pop up only shows a reminder and gives an entry. `PairingCoordinator.begin` starts watching for pairing (finding the pairing window, reading the code via accessibility, sending the fill-code notification), with a 10-minute deadline counted from the last `begin` (`SlidingDeadline`): tapping 「去无线调试」 (Go to wireless debugging), or leaving while the guide page is on the pairing step (`ON_STOP`, usually switching to system settings oneself), calls it again, and if already watching it only extends the deadline and does not pop the notification again from the start; the mDNS for finding the pairing window (`BuiltinShellEngine.startDiscovery`) is the same, and calling again while still searching restarts the timer. If the guide page has been open for a long time, or the user switches to system settings from Recents, the code can still be read and the notification can still pop up. When the pairing window is found it sends 「输入配对码」 (Enter pairing code) (accessibility is 5 seconds later, only when reading the code), and the action 「填配对码」 (Fill pairing code) carries RemoteInput (no unlock required, no generated reply); if nobody fills it, it pops up again after 8, 20 and 40 seconds, at most three times, ringing and popping each time, and it no longer pops up once it has been replaced by other content. A filled code is first normalized locally (spaces, various dashes, full-width digits) and checked to be 6 digits; if wrong it is pointed out in the same notification on the spot and not tried; if right it immediately changes to 「正在配对…」 (Pairing…; it stays this until pairing starts, and does not add another notification based on the state before the code was filled), and after success changes to 「配对成功」 (Paired successfully) and then disappears by itself; if the code is wrong, expired or the window closed, the same notification says to get a new code and fill it again, keeping the input field. When accessibility is off, the guide page uses three numbered small diagrams to explain these three steps, and the fallback of filling the code directly on the page still works. The state machine of the setup wizard (`app/settings/ui/PhoneSetupScreen.kt`) is the pure function `PhoneSetupFlow` (`core/device/shell/PhoneSetupFlow.kt`); the switches it reads are only used to tick automatically and give hints, and do not block hard: if developer options, USB debugging, accessibility and wireless debugging are read as on, it ticks them and moves on; if read as off it stops at that step, but the three steps that read switches all have 「我已经打开了,下一步」 (I have turned it on, next) (recorded in `SetupInputs.confirmed`), and accessibility can be skipped (recommended: after pairing Claire turns it on itself, and it will not be blocked by "restricted settings"); the pairing step, besides notification and automatic code reading, can also be filled in directly on the page, so no step gets stuck. A completed step can be tapped to go back and redo (`SetupInputs.revisit`; if the step gone back to is read as changed from off to on, it automatically returns to where it was). Success only looks at whether the assistant is running, regardless of what was read before. When pairing or connection fails (pairing window closed, cannot connect, unknown reason), it points out the step most likely to be the problem according to the developer options and wireless debugging that were read (`SetupView.suspect`: read as off, or this phone cannot be read), and gives a button back to that step; the same applies when the user confirms wireless debugging is on but the assistant reads it as off and does not connect, and it does not keep spinning. It retries automatically after a disconnect (exponential backoff). It tries the connection ports for wireless debugging (`core/device/adb/AdbConnectPort.kt`) in order and stops at whichever connects: the port that connected last time (stored in the App's private settings, rejected quickly when stale), the system property `service.adb.tls.port` (used only if readable), each local port obtained from mDNS lookups of `_adb-tls-connect._tcp` (`NsdAdbServiceFinder`), scanning local ports (`core/device/adb/LocalPortScan.kt`), and the port the user filled in on the guide page. Being rejected on TLS does not necessarily mean the key is wrong (some systems let another service take the first TLS handshake on the same port and reject any certificate, and only the next connection reaches adbd): it tries the same port again after a while, and if that fails it goes on to the remaining candidates; if an existing port was rejected this way it stops scanning local ports; only when all have been tried and some port rejected us does it report `BuiltinShellFailure.AuthorizationRevoked` (re-pairing needed, and the watchdog does not retry automatically). Scanning is the fallback when none of the above works (some networks block multicast, some systems do not let apps read properties): wireless debugging's adbd listens on a port the system assigns at random, so it only scans the ephemeral port range (using `/proc/sys/net/ipv4/ip_local_port_range` when readable, otherwise 30000–65535), and scans only the local machine's own addresses — first 127.0.0.1, and only if nothing looks like adbd, the IPv4 address on Wi-Fi, never other devices; `NioPortScanner` uses java.nio non-blocking connects, with at most 200 connecting at once and at most 150 ms each, skipping ports already tried and ports Claire itself is listening on (`OwnListeningPorts`, such as the sign-in callback); an open port must answer CNXN with STLS to look like adbd (connecting to itself, no other service answers STLS), then it completes the TLS handshake as usual with the paired key, and the first one to connect wins and is recorded as a cache; scanning and checking together take no more than 10 seconds and run on an IO thread, during the scan `BuiltinShellManager.scanningPorts` is true and the guide page shows 「正在本机查找无线调试端口…」 (Searching for the wireless debugging port on this device…). When it cannot connect, the connect step of the guide page has 「填无线调试的端口」 (Enter the wireless debugging port) (numeric keyboard, 1–65535; pasting a whole "IP address and port" takes what follows the colon), and if filled it retries once with it (`BuiltinShellManager.connectWithPort`, used only this once; this time it does not scan, and records the port as a cache when connected). Besides success, the guide page has 「稍后再说」 (Later) at the bottom at every stage (waiting for the user, connecting, failed), and back always leaves, never trapping the user on this page. Several capabilities — 「替我打开无障碍」 (Turn on accessibility for me), 「不受省电限制」 (Not restricted by battery optimization), 「重启后自动恢复」 (Restore automatically after reboot) and 「自动打开无线调试」 (Turn on wireless debugging automatically) — are on by default: they all need a paired connection to take effect, so every time the assistant becomes running (after pairing, reconnecting after a drop, already paired at App start, reconnected automatically at boot), `BuiltinShellRecovery.start` (`app/cap/phone/setup/BuiltinShellRecovery.kt`) watches the state and, through `RecoveryPermissions.applyPending` (`core/device/shell/RecoveryPermissions.kt`), fills in the items the user has not personally turned off that have not taken effect yet, without showing dialogs, and on failure only records it to be mentioned on the settings page. The record (`app/settings/RecoverySettings.kt`) keeps two things per item: "in effect" and "turned off by the user personally"; old versions had only the first, so anything never turned off is treated as on by default. Unpairing withdraws the items that took effect, without touching the user's choices, and they are turned on automatically again when pairing again, while ones turned off personally stay off; boot auto-restore depends on whether 「重启后自动恢复」 is in effect. Accessibility only adds Claire's own service and does not touch other services. Claire's accessibility service may stop for two reasons: after the process is killed by the system, the system treats it as crashed, so it is still on in Settings but is no longer bound; when force-stopped, the system removes it from the accessibility list directly. `BuiltinShellRecovery.start` also watches whether Claire's service is in the system list, whether the service instance is connected, and the assistant's state (all have callbacks, no polling); if the service has not been running for more than 3 seconds and there is a way to write system settings (if the App itself has permission to modify system settings it writes directly, without waiting for the assistant, and it can fix even with wireless debugging off; without permission it waits for the assistant to be running), `AccessibilityRepair` (`core/device/shell/AccessibilityRepair.kt`) turns it on through `RecoveryPermissions.restartAccessibility`: if it is not in the list, add it; if it is there but not bound, remove it, pause, and add it back, and the system rebinds it; it counts as fixed only after the service connects; if adding back fails, it writes the original list (together with the master switch) back and still counts it as failed. Right after boot, before the user has unlocked once (`UserManager.isUserUnlocked` is false), the service cannot be bound anyway; then it does not fix it, and the status card only says it will be restored after unlocking; after receiving `ACTION_USER_UNLOCKED` it judges again and fixes it as usual if still not connected. No matter who turned it off, it always turns it on automatically, and only if 「替我打开无障碍」 is turned off in Claire does it leave it alone; each stuck episode is tried at most twice, and if that fails it stops and leaves a hint for manual handling on the UI. After fixing, it only says the time under that item on the settings page. When a task connects to the phone it still waits 5 seconds for the accessibility service as usual; if a repair is about to start or is in progress (`AccessibilityRepair.phase`) it keeps waiting until the repair finishes (about half a minute at most), and only reports the phone unavailable after giving up. This is enabled only on Android 13 and above. After the assistant is up, wireless debugging is no longer needed, but restarting it (rebooting the phone, Claire updating, the assistant gone) depends on wireless debugging, and stock Android turns it off when Wi-Fi disconnects and after a reboot. 「自动打开无线调试」: when the watchdog wants to start the assistant but wireless debugging is off and Wi-Fi is connected, `WirelessDebuggingAutoOn` (`core/device/shell/WirelessDebuggingAutoOn.kt`) writes `adb_wifi_enabled` to 1 and then connects as usual; when Wi-Fi connects (network callback) and the assistant is not there, it also does this. It only turns it on, never off, and does not touch USB debugging or developer options. It is written only by the App itself (it requires permission to modify system settings, shared with 「重启后自动恢复」, and withdrawn only when both are turned off; when the assistant needs to start there is no other connection available), and if not authorized or the user turned this item off it does not write, and the UI still gives the manual way to turn it on. Stock Android on a Wi-Fi network that is not allowed immediately flips the switch back to 0 and pops up a dialog asking the user: if within 3 seconds after writing it reads it flipped back, it stops, and the status reports 「这个 Wi-Fi 还没允许无线调试」 (This Wi-Fi does not allow wireless debugging yet) (`BuiltinShellFailure.WifiNotAllowed`), asking the user to turn it on personally once and check 「始终允许」 (Always allow), and it does not write again until the Wi-Fi changes, the user turns it on personally, the user taps retry, or the assistant comes up, so it does not pop dialogs repeatedly; if the write is rejected, or it has written 3 times in a row and the assistant still has not come up, it also stops; the interval between two writes starts at 10 seconds and doubles.
- **Root startup and Root commands**: when the phone already has `su`, Settings › Advanced and other settings shows a separate Root page (`app/settings/ui/RootSection.kt`); capability detection only looks at the generic `su` path, does not execute authorization requests, and does not identify the specific root implementation. Assistant startup has no visible switch: only after the user personally taps authorization for the first time does `RootControl` request `su 2000` and persist the explicit shell UID authorization result; `RootStart.of` is always Off when there is no historical answer, so opening the App, a watchdog restart or a capability refresh never suddenly pops up an authorization request. After authorization, `BuiltinShellEngine` preferentially starts the assistant via root with the same restricted shell identity, and the handshake, token and signature checks are the same as with wireless debugging; after refusal, no response, wrong identity or `su` disappearing, it stops requesting automatically, and only retries when the user taps authorization again. If wireless debugging pairing still exists, a root failure can fall back, and the USB startup path is unchanged; unpairing clears the automatic startup request and invalidates unfinished authorization callbacks. Root commands are another high-risk setting, off by default, requesting UID 0 authorization separately; only when both the switch and the authorization are valid does the main task `TaskRun` assemble `RootCapability`, which is not given to child tasks or condition checks. `RootCommandClass` only lets definite read-only commands execute directly; commands that modify, delete or cannot be judged still go through the unified approval of `ActionExecutor`, and output is truncated uniformly.
- **adb identity (pairing key)**: Claire's own RSA-2048 key (public exponent F4) plus a self-signed certificate (`core/device/adb/AdbIdentity.kt`); during pairing the public key is given to the device, and every TLS connection afterwards presents the certificate, and the device only accepts the one from pairing. The key is stored as PKCS#8 in the App's private directory, wrapped with an AES key in the Android Keystore (`WrappedKeyFile`; when `AndroidAdb.keyStore` is cleared, the wrapping key is deleted along with it). Reading it back does not depend on the platform giving a private key with CRT parameters: as long as it is an RSA private key, take the modulus, and the public exponent first from the CRT form, or if absent from the RSAPrivateKey structure in PKCS#8, and only if the structure also has 0 does it fill in F4; before filling it in, it verifies a signature once, and if it does not match it treats it as unreadable rather than connecting with the wrong public key; the public key read from the same stored bytes is the same as before, so upgrades do not require re-pairing. "Never stored" and "stored but unreadable" are strictly separated: `AdbKeyStore.read` returns null for the former, and throws `AdbKeyUnreadableException` for the latter (cannot decrypt, empty or truncated file, cannot parse). There is only one `AdbIdentitySource` per process (`AndroidAdb.identities`), and pairing (`forPairing`) and connecting (`forConnect`) get the same key from the cache; if none has been stored, a new one is created and stored; if one is stored but unreadable, connecting throws, writes a log (tag MikaAdbKey), does not touch the file, and the engine reports `BuiltinShellFailure.KeyUnreadable` (「配对用的密钥读不出来了」 (The pairing key can no longer be read); the one-tap fix is to pair again, and it does not retry automatically), and only the pairing step deletes the unreadable key and stores a new one (pairing then gives the new key to the device); unpairing (`forget`) deletes the key and clears the cache. The `adb key status` line in diagnostics is the key's state in this process (NotLoaded / Loaded / Created / Unreadable and the reason), and it only looks at the state and does not read the key for diagnostics.
- **Starting the built-in assistant from a computer (USB)**: when wireless debugging pairing does not succeed, or when an Agent on the computer does the setup, the computer runs `adb shell sh /sdcard/Android/data/com.kilv.claire/files/usb-start.sh` over USB debugging, which starts the same assistant (the same `app_process` command and parameters), and handover also goes through the same `HelperHub.offer`, with the same checks of shell identity, APK, the process hosting the Binder, the token and the signature fingerprint. The script is written by `UsbStartScript` (`app/cap/phone/setup/UsbStartScript.kt`) into `Context.getExternalFilesDir(null)` (the App writes it without permission, shell can read it, other Apps cannot), and its text is the pure functions `HelperHandoff.usbScript` / `usbStub`. It is rewritten along with `HelperHub.shell`, and also when the token is invalidated as a whole (`HandoffNonces.resets`, e.g. unpairing) (`HelperHandoff.usbScriptWrites`; otherwise, while the assistant is absent, the script would keep an invalidated token and the handover would be rejected as BadNonce): when the assistant is absent (App start, someone wants to use the assistant but it is not there, the guide page is opened) it writes a script with a one-time token, and the token is `HandoffNonces.usbNonce` — stored together with the startup token and the continuation token, and if any one of them is used, all of them are invalidated; it expires after 24 hours by wall clock (it must survive a reboot), and while more than half its validity remains it is reused, so it is not swapped while the computer is running it; when the assistant is connected it is replaced with a note without a token ("already running"; if the process is gone, ask the user to open Claire first), so no usable token is left on disk. The script only starts if `id -u` is 2000; the assistant uses setsid to start a new session and put itself in a background subshell (after the subshell exits it belongs to init), the token goes through the built-in echo through a pipe into standard input, and output is discarded, so when the adb session ends and adbd kills its process group after unplugging, the assistant is not affected; the script waits 2 seconds and then uses `pidof` to see whether the assistant process is still there, and says either 「正在启动,打开 Claire 确认」 (Starting; open Claire to confirm) or 「没起来,先打开 Claire 再跑一次」 (It did not start; open Claire first and run it again). When not paired, the assistant is accepted and the engine records "started by the computer" (`BuiltinShellPlatform.usbStarted`), the state is running as usual, and the follow-up (filling in those capabilities, turning on accessibility) is the same as after pairing: `commandRunner` runs commands through the assistant's `runCommand` when the assistant is there, and only connects to the paired adbd when it is not. An assistant started this way is gone after a reboot; when there has never been pairing, Claire cannot start it itself, and a new process first waits a while (a still-living assistant will come to hand over), and if it does not come it reports `BuiltinShellFailure.UsbHelperStopped` (「手机助手已停止」 (The phone assistant has stopped): run the command on the computer again, or pair wireless debugging so it recovers automatically), and boot auto-restore also does not touch wireless debugging; unpairing clears this record too. The guide page normally does not offer this path, and only when needed (`SetupView.usbFallback`, computed by `PhoneSetupFlow`) puts a card in the current step: 「这台手机打不开无线调试?改用电脑启动」 (Cannot turn on wireless debugging on this phone? Start it from a computer instead), which is an explanation, the command and a copy button. When it is needed: the system has no `adb_wifi_enabled` setting (`SetupInputs.wirelessMissing`; stock Android from 11 always writes it to 0 or 1 at boot, and it can be read whether on or off, so if it cannot be read the system does not have wireless debugging, while a read error draws no conclusion); the user tapped 「找不到无线调试?」 (Cannot find wireless debugging?) on the wireless debugging step (the only hint line this step normally has); the pairing window is never found, cannot connect, the computer-started assistant stopped, or the user says wireless debugging is on but the assistant reads it as off; stopping at the wireless debugging step, the pairing step (pairing window not found yet) or automatic connection (`PhoneSetupFlow.stallPoint`) for 45 seconds without progress (`SetupInputs.stalledMs`, counted from the start after changing place). The first two are offered only after reaching the wireless debugging step (starting from a computer also requires finishing developer options and USB debugging first). Once the card has appeared it stays (recorded in `SetupInputs.usbAsked`) until success. It does not take "wrote 1 and it was flipped back to 0" as a signal: stock Android does this on a Wi-Fi network that is not allowed too (it pops up a dialog asking the user), which would be a false alarm on a normal phone; and the wireless debugging page has no separate public jump entry that could be used for judging.
- **Claire pulled back up by the assistant after being killed**: when the system or a cleaner ends Claire's process (on force-stop the system also removes Claire's accessibility service from `enabled_accessibility_services`), the floating capsule disappears with it. The built-in assistant does not die with it: it learns from the death notification of the Claire token it received at handover (`HelperProcess.onAppDied`), first waits `HelperRestorePolicy.GRACE_MS` (8 seconds), and if Claire comes back during this time (the uid importance listener reports it up, or it hands over again) it does nothing; if it does not come back, it decides according to Claire's last wish (`RestoreWish`, via `IMikaShell.setRestoreWish`): if the capsule is set to always show, or a task was running when it died, it pulls it up, otherwise (for example the user force-stopped it personally, or the capsule only shows during tasks) it leaves it stopped. When pulling it up it first appends Claire's accessibility service back to the list and turns on `accessibility_enabled` (`RestoreCommands.accessibility`, without touching any other service; it writes only when the user has not turned off 「替我打开无障碍」 in Claire and Claire's entry was really in the list while Claire was alive; one that the user turned off in system settings while Claire was alive is not turned on for them — it only counts 3 seconds after it is gone from the list, so that the force-stop moment does not change the wish), then hands over again as usual: when it fetches Claire's handover provider the system starts its process (shell can get any App's provider, which is the path the `content` command uses; providers are not restricted by background service starts and show no UI), `MikaApp.onCreate` runs as usual, and the capsule, watchdog and automatic accessibility turn-on come up with it. It pulls at most 3 times in 10 minutes, and if it dies again right after being pulled up it stops and waits for the window to pass; every step is recorded in the assistant's log (logcat tag MikaHelper). The wish is handed over by `RestoreWishSync` (`app/cap/phone/setup/`) when the capsule mode, a task running, 「替我打开无障碍」, the accessibility list, or the assistant changes (`RestoreWishSender` only hands it over when it changed or the Binder changed). At every handover the assistant reports to Claire "the last time it pulled it up, the most recent times, and the last time it gave up because it was too frequent" (`HelperRestoreReport`); every time Claire starts it looks to see whether the accessibility service was removed, or is in the list but not bound after 5 seconds (`A11yStartCheck`, counted only after the service has connected once), and records it in `RecoverySettings`; both are written into the Recovery section of "Copy diagnostics" (`restored by helper`, `accessibility on start`). When paired, the watchdog starts the assistant as soon as Claire starts (`BuiltinShellEngine.start`: if nobody comes to hand over, it starts one after 3 seconds through the paired connection, without waiting for a task to need it), so that it is present; when not paired it does not connect. Some systems additionally kill background Apps, so a line under Settings › Floating capsule asks the user to allow Claire to run in the background and auto-start in system settings.
- **Reading and operating**: the accessibility service (`app/a11y/MikaAccessibilityService.kt` → `app/cap/phone/a11y/ScreenAccessibility.kt`) reads the control tree per screen and performs gestures on the specified screen. Every screen read first judges from the control tree whether it is sufficient (`core/screen/uistate/TreeQuality.kt`): it counts as clearly sufficient only when there are enough named elements, most controls have names, and there is no large region inside the App window with not a single character, without recognizing text; when unsure it reads once with the text recognition bundled with the APK (`app/cap/phone/a11y/PhoneOcr.kt`), and if the text missing from the tree is filled in with three or more lines it counts as a missing part (partial); when the tree is missing a part or unreadable (unusable) it always recognizes text (the main model that cannot see images, answer sources and verification, and `phone_collect` all rely on it); screens protected against screenshots are not recognized. Filled-in text (`core/screen/uistate/VisibleText.kt`) first drops misrecognized lines (low confidence, all symbols, stray Western digit strings on a mostly-Chinese screen), and each line carries a position of 0–999 and a tap center; when the tree is insufficient the screen-read result writes `treeQuality` and a hint: tap the center of the text on screen, locate controls without text (icons, images, input fields) visually, to type into a field give the point to type at or say in the element which field it is, and use the whole-screen description only when you cannot tell what page it is (it is several times slower and is not used to find a single control). If the main model can see images and 「先读元素,必要时看图」 (Read elements first, look at images when necessary) is on, the image is also attached. Before recognizing text it first waits for the image to settle (self-drawn UIs hardly emit accessibility events, and when events are quiet the image may still be transitioning), and if the whole page changes during recognition it recognizes the new page once more, while local movement (animated avatars, cursor) is used as is (`app/cap/phone/a11y/StillFrameRead.kt`); if the tree changes during reading it still recognizes. When the tree is insufficient and not a single line of text was read, the screen-read result writes `ocr` (empty, illegible, timeout, unavailable, failed), and the hint changes to locating input fields and buttons visually. Input is generally written directly into the input field; web-style edit areas use clipboard paste, and the user's original clipboard is returned afterwards. When there is no focused input field in the tree (the App draws its own UI), it first selects all and then pastes via the clipboard, and Ctrl+A / Ctrl+V are sent by the built-in assistant only to Claire's screen (`injectCtrlKey`), then it verifies by comparing the text recognized on screen before and after typing (`core/screen/uistate/UnseenField.kt`: one more occurrence is consistent, no change at all means it was not typed, anything else is unverifiable; when the IME is showing, text on the keyboard does not count). It does not require the IME to be showing: key events go to the focused window on this screen, and a field receives them even without the IME; if the IME is not showing and nothing changed at all, the focus is most likely not on the field, so it reports `no_focus` and asks the model to tap the input field first, instead of blindly re-pasting. When nothing on screen has input focus (no input focus can be found in any window) and the IME is not showing, it does not paste at all and directly reports `no_focus`: there is no field to receive it, and pasting would make a change elsewhere in the UI be taken as "possibly typed" (same for clearing). Clearing likewise uses select-all plus the delete key, and when the IME is not showing and the UI did not change it likewise reports `no_focus`. Typing and clearing also accept a point (a coordinate, or a `@vN` found visually, checked the same way as a tap that the image has not changed): it first taps that point, waits for the UI to become quiet, and if an input field visible in the tree appeared it types into it as usual, otherwise it pastes as above, reading the on-screen text before pasting after the tap; if nothing changed at all before and after pasting it reports `point_not_typed` (that point is most likely not an input field), does not retry automatically, and does not press Enter when unverifiable (`ScreenPort.typeAt` / `clearAt`, `AndroidScreen.typeAt`). On screens where the tree cannot read the input field there is no need to tap before typing: tapping only gives the field focus, when neither the tree nor the image changes, and the verification of typing is the evidence that it was hit. When typing at a point, that tap also goes through the irreversibility decision (tapping a send-like button is judged as a tap). When an input field is pointed at by description (`element`) and there is no match in the tree, and this screen's tree is missing a part or unusable, the execution entry's element-substitution step finds the field visually (`Interfaces.bySight`, when a vision model is configured; the same verification as `find_visually`, marking ones without supporting evidence), substitutes the found `@vN`, and afterwards verifies the image, judges irreversibility and verifies after pasting just as when the model passes `@vN` itself; the result writes `foundBySight` and the text seen, saving the round of finding a point before typing.
- **Gesture pacing** (`core/cap/phone/GesturePacing.kt`, with random values, arcs, easing and the web mouse `InputPacing` sharing `core/screen/uistate/Pace.kt`): before each finger-down it waits 30–120 ms; a tap is held 50–120 ms, and a double tap is 40–90 ms per tap with 80–140 ms between (within the system's double-tap window); when tapping an element the touch point is slightly off the center (no more than one fifth of the width/height and at most 12 pixels; a direction narrower than 24 pixels is not offset; always inside the element), and tapping by coordinate is off by at most 3 pixels. For swipes (`phone_swipe`, the gesture that `phone_scroll` falls back to, single-finger `phone_gesture`) the start and end points are unchanged, but the path goes along a short arc between the two (deviation no more than 6% of the distance and at most 30 pixels; multi-point paths follow what was drawn), the duration varies by 8% around the given value, and the start is slow: a fast swipe shorter than 800 ms releases at a speed comparable to the previous constant-speed swipe (so the fling distance is unchanged), while a slow drag of 800 ms or more settles before lifting and does not fling; when the start and end almost coincide (holding in place) it only lengthens, never shortens. Fast and slow require each point to have its own timing, which accessibility gestures cannot do (the system moves along the path at constant speed), so a paced stroke is injected point by point by the built-in assistant according to the timings (`injectStroke`, only to Claire's screen), and when the assistant cannot inject it falls back to an accessibility gesture along the same arc; taps still use accessibility gestures, and only fall back to assistant injection if that fails. Two-finger gestures only vary the duration. The control's own click and scroll actions (`ACTION_CLICK`, `ACTION_SCROLL_*`) and input are unaffected. `GesturePacing.Instant` is exactly as before (for tests).
- **Operating pace** (Settings › Task runs › Operating pace, `core/cap/phone/OperatingPace.kt`, stored in `FeatureFlags.operatingPace`): gestures are human-like in all three modes, and three other things follow it — 「快」 (Fast) (`FAST`: no extra pause between actions, typing in one write, no screen cap, i.e. the previous behavior), 「标准」 (Standard) (`STANDARD`, the default), and 「像人」 (Human-like) (`HUMAN`: every App uses the slow set of dwells and typing). It is read once at the start of each task (`TaskRun`), the evaluation and real-device acceptance override it via `EvalHooks.operatingPace`, defaulting to 「快」 (`-e evalPace` / `-e livePace` switch to `standard` or `human`), without changing the setting; the core's `toolDispatcher` defaults to `AppPacing.Off` and `AndroidScreen` defaults to `TypingPacing.Instant`, so tests still run fast.
  - **Typing** (`core/cap/phone/TypingPacing.kt` pure logic): after `AndroidScreen.typeText` finds the input field, it first writes segment by segment into an ever-longer prefix according to the pace (`ACTION_SET_TEXT`, which works for any native input field, including CJK, and handles CJK text just the same), and the last segment's full text is handed to `typeAndVerify` as before to write in one go, read back and verify, and retry. Latin letters take 60–170 ms per character, CJK characters 160–380 ms per character, with 1–3 consecutive characters going on screen together (like IME word selection), and occasional extra pauses of 0.3–0.9 seconds after punctuation and spaces; with many characters it writes a few characters per segment, at most 40 segments, for at most 6 seconds total (for Apps that limit how fast one can act, and for Human-like: 90–230 / 220–520 ms, pauses 0.5–1.4 seconds, at most 60 segments, 12 seconds). A single character is never split (surrogate pairs, combining marks, variation selectors, zero-width-joiner emoji sequences). After writing the first segment it reads back: if the field does not accept a partial character (read-back does not match, cannot read) or cannot be written, it stops and writes the whole text as before. Password fields, web fields that only accept pasting (`TypingPacing.forField`) and fields that cannot be seen in the tree (paste) are still written in one go.
  - **Dwell between actions** (`core/cap/phone/AppPacing.kt` pure logic, `AppDwell.kt` wired to the phone capability): every action that changes the screen goes through the single execution entry `ActionExecutor`, which asks this screen's capability before executing (`Capability.beforeWrite`; the phone capability waits according to `AppDwell`) and tells it the result afterwards (`afterWrite`); single steps, each step in a `do_steps` batch, and replay are all the same, while composite actions (such as `phone_run`) do not dwell themselves and each step inside them dwells separately; the web still uses its own page-by-page dwell (`PageDwell`) and does not go through here. If the previous action's result has an effect of `done` or `place_changed` it counts as having moved to a new screen, otherwise it is the same screen: on Standard, the same screen dwells 0.5–1.2 seconds and a new screen 0.9–2 seconds, with a 5% chance of an extra 0.6–1.5 seconds, at most 3.5 seconds at a time; for Apps that limit how fast one can act (App knowledge `pace: careful`, looked up by package name with `GuideCatalog.appPace`) and for Human-like, the same screen is 0.9–2.2 seconds and a new screen 2.5–5 seconds, plus reading time of 15 ms per character for the screen the model most recently read (at most 8 seconds), with a 10% chance of an extra 2–5 seconds, at most 15 seconds at a time. The dwell counts from when the previous action finished, including the time the model spends thinking and reading the screen, and only the shortfall is filled in; how long it dwelled is recorded together with the outward-action interval as this call's wait (run record `tool_result.waitMs`) and is not told to the model; if the user interjects during the dwell the action is not done and it reports `skipped_for_new_message`. On the slow set, when the dwell on a new screen is long enough and the next action is not done by screen position (back, key press, scroll by direction), during the dwell it slowly swipes a short distance in the middle of the scrollable content that occupies most of the screen, per the `IdleScroll` arrangement (`AndroidScreen.idleScroll`, a slow drag that settles before lifting; it does not swipe when the IME is showing, the input field has focus, another app window is covering it, or there is no sufficiently large scrollable content), how many swipes it did only goes into the run record (`idleScrolls`), and the screen the model holds is marked stale (`ScreenSession.movedByClaire`).
  - **Screen cap** (not set by default: `AppPacing.screenCap` is null. Stopping hard to ask a person would leave reading/summarizing tasks and unattended tasks like schedule and proactive ones unfinished, and the risk of being blocked is pressed down by longer dwells): when `screenCap` is given, an App that limits how fast one can act may move to a new screen at most this many times in one task (scrolling down to read the same page does not count), and after that, actions that change screens inside the App (tap, swipe, back, key press, gesture) are not done and report the same `page_limit` as the web (`core/screen/uistate/DwellStop.kt`, with an explanation telling the model to answer with what it has already read, and to ask via `ask_user` if it needs to keep looking); typing, clearing, scrolling, turning wheels and opening other Apps still work. The count restarts after the user answers (`Capability.onUserAnswered`); outward actions themselves are not blocked, and once one has succeeded in this App the cap is no longer set for this task (via `Capability.onOutwardEnd`). Ordinary Apps have no cap.

The default vertical `phone_scroll` prefers a scrollable control, and falls back to a gesture only when none is found.
  - Query and composite: `phone_query` (find by text, resource ID or control type in the complete control tree, reading text only), `phone_run` (a series of ordered commands, each step relocating on the current page and optionally deciding whether to continue by a text condition; stops and hands back to the model when the target is missing, cannot be distinguished, or the App switches), `phone_collect` (read a long list or chat screen by screen and merge by overlap), `phone_find` (scroll to find a target), `phone_extract` (visible text, list rows, form fields; passwords are not returned), `phone_dialog` (read a dialog, tapping only when a unique button text is given), `phone_wait`, `phone_event` (wait for or collect window, content and notification events), `phone_gesture` (single-finger path or two fingers), `phone_set_wheel` (turn a wheel to a value, see below).
  - System actions: `phone_set_alarm`, `phone_set_timer`, `phone_show_alarms`, `phone_add_calendar_event` (see below).
  - Other: `phone_system_command` (execute a system command through the built-in assistant, separate from the Linux sandbox; 10-second timeout; when the command does things that the dedicated tools for tapping, swiping, typing, key presses and opening Apps do, or fails twice in a row, the result reminds it to switch back to the dedicated tools; after a reminder in this task, commands that do those kinds of things are not executed (`use_phone_tool`, only replying with which tool to use), and sharing text via shell (`am start` with SEND, without files) is never executed and points to `phone_share_text`; commands that check status or read settings are unaffected, `core/cap/phone/CommandSteer.kt`); for vision tools see below.
- **Sharing text to an App**: `phone_share_text` starts a text share of a piece of text according to Android's text sharing (ACTION_SEND text/plain, EXTRA_TEXT, only to the specified package) onto Claire's screen (the built-in assistant's `startShare`, which, like opening an App, checks whether the user is using it on the main screen and whether another task holds it), then, like `phone_launch_app`, waits for it to come to the foreground, recognizes the system asking which one to open (when two copies are installed; when this App has several pages that receive shares the system asks which one, and a system-package window coming to the top also counts), and records the task. It only opens the share page and does not send: the recipient and the send button are tapped by the model on that page, and sending still goes through the irreversible action confirmation. When this App does not accept text shares it reports `cannot_share`. For sending messages and taking notes in Apps whose text cannot be read or typed into, go through it first (`core/cap/phone/AppTools.kt`, `AndroidScreen.shareText`).
- **System actions (alarms, timers, calendar)**: `phone_set_alarm` (hour, minute, label, days of the week to repeat, vibrate), `phone_set_timer` (seconds, label), `phone_show_alarms`, `phone_add_calendar_event` (title, start/end, all day, location, notes) are handed to the phone's clock and calendar Apps through Android's standard interfaces (`AlarmClock.ACTION_SET_ALARM` / `ACTION_SET_TIMER` with `EXTRA_SKIP_UI`, `ACTION_SHOW_ALARMS`, the calendar's `ACTION_INSERT`, with the type given explicitly as `vnd.android.cursor.dir/event`; no calendar permission is needed, and `SET_ALARM` for setting an alarm is a normal permission), without operating their UIs cell by cell (`core/cap/phone/SystemActionTools.kt`; the intent is first written by `app/cap/phone/shell/SystemIntents.kt` as an Android-independent Spec and then converted to an Intent). On Claire's side it first asks the package manager who can receive it (the manifest's `<queries>` lists these kinds): if no App receives it, it reports `not_supported` and the model goes back to operating the clock or calendar UI; if there are several, it uses the one the user has set as default, otherwise it picks the system one first, specifying that page directly, so no "which one" chooser is left on screen. Then it hands it to the built-in assistant to start on Claire's screen (`startSystemAction`, which allows only these intents and, like opening a link, checks whether the receiving App is being used on the main screen and whether another task holds it; before and after the action it watches the main screen as usual and moves back anything that opens on the main screen). When the receiving page requires a permission the shell does not have (the clock's set-alarm page requires `SET_ALARM`), the assistant instead sends a PendingIntent made by Claire: started as Claire, with permissions checked as Claire, screen and background start checked as the sending assistant, and it still lands on Claire's screen (from Android 14 the sender explicitly allows a background start). Alarms and timers are supposed to be set quietly: before and after setting an alarm it reads the system's next alarm (`AlarmManager.getNextAlarmClock`, waiting at most 3 seconds), and the result's `check` is verified (the next one is it), earlier_alarm_first (an earlier alarm is in front and it cannot be seen), not_seen or unknown; for the latter two and for the blocked case it hints that the user should confirm with `phone_show_alarms`; if the App opens its own UI instead, it reports `screenOpened` and asks the model to confirm on that page. For the alarm list and a new calendar event it waits for that App to come to the top and records the task; a new calendar event is not saved for the user, and the save button is tapped by the model on that page. Setting alarms and timers are entry tools that are enough on their own in the withheld phone group (`Entry.Alone`, without expanding the whole group), a new calendar event is an entry that expands the whole group, and the alarm list is in the group; the risk is the same as opening an App (it only changes things on the phone and spends no money, so no confirmation is needed).
- **Wheel pickers**: for wheels that turn cell by cell, such as time, date and region, `phone_set_wheel` (the wheel or the id of the item it currently shows, and the value to show) turns to the value in one call in the port, without the model looking and swiping one cell at a time (`core/cap/phone/SetWheel.kt`, `app/cap/phone/a11y/WheelDriver.kt`). The id given can be the wheel, or one of the items it shows (self-drawn wheels are often the selected item): in that case the wheel is the column found upward that is horizontally aligned with this item (at least three items, with roughly even spacing, `WheelMath.column`), and other wheels side by side in the same block (the minutes next to the hour) are not read or dragged; the scrollable container found upward is used for accessibility scrolling only if it horizontally covers the exact center of this item (a whole-page scroll area does not count). It tries what the control can do in order: if the wheel contains an input field (stock number wheels do), it writes the value into it, defocuses it to confirm (so that a popped-up IME is dismissed), and reads it back; if it can "scroll forward / backward" via accessibility (stock number wheels one cell at a time), it reads the current value and scrolls in batches of at most 5 via `WheelSteps`, reading back and recomputing after each batch, deciding the direction from the numeric difference, and when a wrap is visible (…58 59 00 01…) it takes the nearer side, calibrates on the first read-back whether "forward" increases or decreases, and when the value stops changing: if no wrap is visible, this side has reached the end or the target is out of range (`at_end`); if a wrap is visible (there is no end), this step had no effect and it hands over to dragging (`not_moving`); if one step turns more than one cell, or it overshoots the target several times back and forth, it hands over to dragging, at most 80 steps; for text lists it goes by the position difference when the target is in sight, otherwise scans to one side and reverses at the end; if none of these works (the App draws the wheel itself), it reads the visible items in this column (or recognizes the on-screen text if accessibility cannot read them), estimates the height of one cell and the current value, puts the finger at the horizontal center of this column and drags upward starting from a lower item (downward starting from an upper one, allowed to drag beyond the column), a slow drag by the number of cells (at least 1 second; when pacing, settle before lifting at the end and do not fling, to avoid overshooting), and after reading back calibrates the height of one cell by the actual number of cells turned and drags the rest, at most 5 rounds (`WheelDrags`); if dragging does not change the value it does not count as the end: only when no wrap is visible and there are no more items toward the direction to go is it `at_end`, otherwise it switches to a quick flick (0.4 seconds) and tries again, drags a bit farther when only one cell remains, and if it does not move 3 times in a row it reports `not_moving` and suggests the model swipe this column itself with phone_swipe. The pure algorithms for recognizing the value, the direction, the wrap, the cell count and the cell height are in `core/cap/phone/WheelMath.kt` (`"09"` is `"9"`, `"40分"` is `"40"`; a selected item's accessibility name often carries a state word, so `"已选中，21"` or `"Selected, 21"` is `"21"`, and when the whole string has only one number it takes that one; text values are also compared by segments split at punctuation; a stateDescription reported separately by the system is removed first when it is concatenated into the name; when only one item is marked isSelected it is the selected one, otherwise it is the item whose own upper/lower range covers the middle line, and if none covers it (some wheels only report the upper and lower cells) it infers the middle cell from the two adjacent numbers above and below (39 and 41 give 40, 59 and 01 give 00, 11 and 1 give 12, `WheelMath.between`), and only if that fails does it fall back to the one nearest the middle line; after every scroll, drag or input it waits for it to settle (reading twice 0.35 seconds apart with the same value) before reading, and after reaching the target it verifies once more after settling, and turns on if it is wrong; only when the settled value matches does it report that it arrived; the `value` and `from` reported to the model keep only the value segment). The result gives `value` (currently displayed), `from`, `attempts` and `method` (text, actions, drag); when it did not reach the target it reports `wheel_at_end`, `wheel_unreadable`, `wheel_not_moving` or `wheel_not_reached` and truthfully gives the currently displayed value. Nodes that look like wheels in the screen-reading tree are marked `wheel: true` (stock number wheel controls, or ones that can scroll and have three to nine short values arranged vertically and evenly around the middle; it prefers to under-recognize, `WheelMath.looksLikeWheel`, `ScreenReader.isWheel`). It can be put in a multi-step batch, and several wheels (hour, minute) can be set in one batch.
- **Apps installed twice**: when the same App is installed in two users (clone, work profile), some systems first ask which one to open. If, after `phone_launch_app` opens it, the top window has changed to a system-package window and the tappable options in that window mention this App's name, it counts as opened, and the result carries `chooser` (the options and which one is the other copy) and a hint: choose as the user said, or the original copy if nothing was said, and do not open it again; that window being in the foreground does not count as being switched away, and the App's task is recorded once the chosen one reaches the foreground (`core/screen/uistate/LaunchChooser.kt`, `AndroidScreen.openApp`). The other user's name shown next to the options is still read by `pm list users`.
- **Opening another copy of an App**: many systems ask which one to open only on the launcher icon and do not ask on programmatic launch, so the other copy can never be opened. Therefore `phone_list_apps` lists each additional copy as a separate item (the same package name, with the name written as "App name (another copy: that user's name)", carrying `user`), and `phone_launch_app` with this `user` opens that copy; without it, it opens the original copy as before. Which users are usable is decided by the built-in assistant according to Android's multi-user concepts (`core/screen/uistate/AppCopies.kt`, reading UserManager's UserInfo and UserProperties, with flags taken from the system's own names: reflect `UserInfo.flagsToString`, or failing that read the names and parentId in the parentheses of `dumpsys user`, without hard-coded flag bits): types with private, flags with HIDDEN or PRIVATE, ones the system marks as hidden from other Apps (private space and the like), and guest/demo/ephemeral/disabled ones are never listed or opened; the rest must be running and unlocked, not in quiet mode, connected to the current user (same profile group, or whose parent user is the current user), and clearly a clone (type with clone, flags with CLONE, or sharing media with the parent) or an original work profile. If any item cannot be read it counts as not satisfied. Some systems make a clone a full user with a clone flag (the type is not the original clone type), recognized by the flag name. The built-in assistant's `appCopyUsers` gives the usable user numbers and a line for diagnostics (only the number, the flags and flag names, the type, the profile group, the parent), and `startAppInUser` checks once more before launching, returning 8 (`copy_not_found`) if it is not among them. In another user it first finds that user's launcher page (`queryIntentActivitiesAsUser`, or if that fails asks `cmd package query-activities --user N`), and first takes the route of opening the icon from the launcher: ILauncherApps.startActivityAsUser (the interface behind `LauncherApps.startMainActivity`; the system checks cross-user permission against the caller, shell has INTERACT_ACROSS_USERS_FULL, and the package name also matches the uid), with ActivityOptions that start onto Claire's screen — some systems always pop up "open with which one" for a programmatic launch of another copy, and this launcher route does not; if that fails it uses `startActivityAsUser` as that user, and finally falls back to `am start --user N --display D -n <component>`. If the system still asks on Claire's screen (the option names may be identical), `phone_launch_app` taps the options one by one itself and reads the user that owns the top task: if it is the wanted copy, it counts as opened; if not, it presses back once to send it to the background (not finishing it, since it may be the user's own copy) and opens again to tap the next one; if none is right it fails with `copy_not_opened`, saying which copy was opened, and does not treat the wrong one as success. When the target App is installed twice, every result carries `inProfile` and `profileUser` (the user that owns the copy currently on screen), and `requestedCopy` when a different copy was requested; when the original copy was opened it says explicitly that it is not the requested one. Occupancy is counted by "package name + user" (`ShellService.sameCopy`): the user using the original copy on the main screen does not block Claire from using the other copy, and vice versa; when the task's user cannot be read it counts as occupied. A cold start only does `am force-stop --user N` on that copy. The target App records the user the task belongs to (`TargetApp.userId`), and the same App switching to its other copy on Claire's screen also counts as being switched away; parallel tasks occupy the two copies separately; muting acts per "package + user", so when the target is the other copy only that copy is muted, without touching the user's own copy. Screen reading, tapping and typing go by screen, with no changes needed.
- **Apps opened onto the user's main screen**: when an App on Claire's screen opens another App not from its own page on this screen but from the background (a service, a redirect, a system chooser, a cross-user hand-off), Android by default puts it on the main screen (and when two copies are installed it first asks on the main screen which one to open), and Claire's screen shows no change. Before every tap, swipe, key press and the like (`AndroidScreen.verified`), it asks the built-in assistant to watch the main screen for 6 seconds (`watchMainScreen`): the assistant registers a task stack listener with the system (ITaskStackListener, used only as a "changed" signal, and it re-reads the task list when one arrives; if registration fails it checks every 100 ms during the watching period), records the task that came to the top of the main screen, which screen it was on before, and which user it belongs to (`app/cap/phone/shell/MainScreenWatch.kt`, `MainScreenLog.kt`), and looks once more on the spot when queried (`mainArrivals`). After the action it judges by the pure logic `MainScreenSpill`: an ordinary App page that appeared during this period (not the launcher, Recents and the like, and not Claire itself or the launcher App), was not moved over from another screen (takeover), is still on the main screen now, was not tapped by the user on the main screen during this period (accessibility tap events), and is not the original top task showing again — it is moved back to Claire's screen (the same task-moving call as takeover, `moveTask`). If what came to the main screen this time is a dialog that the user must handle personally, such as a login verification, account confirmation or payment confirmation, it is not moved: pages of the system account sign-in service (packages that have registered an account authenticator and have no launcher icon of their own; `AccountManager.authenticatorTypes` is read fresh each time, and it counts only when no LAUNCHER entry can be found; such a package only shows account-add, sign-in and verification pages when it comes to the main screen; authenticator packages that do have launcher icons, such as chat Apps or mail Apps registered for contact sync, do not count and are judged by the other criteria, `MainScreenSpill.authenticatorUi`; the manifest queries authenticator services so that such packages are visible to Claire), a top window that is not full-screen (a dialog, a bottom sheet, a window with a password field, or a page itself excluded from Recents (`excludeFromRecents`)) (`AndroidScreen.needsUserWindow`; a window counts as not full-screen when its width or height is less than 80% of the main screen, checked again after 300 ms so that an ordinary App still in its opening animation is not taken for a dialog) — all are left on the user's screen and reported as `onUserScreen`, `needsUser`, with a hint to ask the user to handle it there via `hand_to_user`; if the user has already tapped on the dialog after it appeared (the package of the accessibility tap event is it), it is no longer moved either (`MainScreenSpill.Tap`). **Claire never opens or reopens an App or system page on behalf of another App**: the opener must remain the original App (for example a shopping App opens a payment App, and the payment side needs to know who opened it); moving a task does not change the opener, while reopening would, so it only moves and never reopens. If the page in the top task on the main screen changed before the action, the App the user is using was opened, and it is left alone; nothing is moved during takeover. When the system asks on the main screen which one to open (a system-package window, either the system chooser or its options matching the names of an App installed twice; each system's chooser dialog is not necessarily the stock one, `MainScreenSpill.handling`), it is **not moved**: moving it would make it rebuild for the new screen, and some close themselves when rebuilding. It stays on the user's screen, and the action result carries `opened` (picker, onUserScreen), recognizable options `chooser` and a hint: the system is asking on the user's screen, do not tap again, do not choose for the user, and the next action will wait for the user to finish choosing. The task stops before the next screen-changing action (`TaskRun.awaitUserPick` is hooked in before `TaskGate`, `AndroidScreen.awaitUserPick`), the state is a needs-you wait (`GateReason.needsYou`; on the capsule it is `CapsuleKind.NeedStep`, 「需要你:「<App>」在问用哪个,请在屏幕上选一下」 (You are needed: "<App>" is asking which one to use; please choose on the screen)), and it keeps watching the main screen during this time; after the user has chosen (the chooser is gone) it looks at what was chosen (`MainScreenSpill.picked`): an ordinary page opened on the main screen is moved back to Claire's screen and continues, reported as inProfile; one opened on Claire's screen is counted as well; one that must be handled by the user personally (there is a password field in the window, or nothing can be read from the tree and the system reports a screenshot-protected window when the main screen is captured, like payment or password entry; an App whose tree merely cannot be read is moved back as usual, `MainScreenSpill.needsUser`) stays on the main screen and changes to a needs-you pause that can be continued by tapping (「「<App>」要你在屏幕上处理,处理好了点继续」 ("<App>" needs you to handle it on the screen; tap continue when done)); after the user taps continue, if it is still on the main screen it is moved back, and if it has closed it says so truthfully (`byUser`); if the user closed the question (`closed`) it says so truthfully, and the model decides the next step. These results are carried as `opened` in the next screen read, the next action is not done and reports `opened_elsewhere`. The `opened` in the result (package, app, pulledBack, onUserScreen, needsUser, inProfile, picker, closed, byUser) comes with a hint: if it was moved back, do not tap again and continue there; one moved back counts as opened by the target App and not as being switched away, so the effect is a place change rather than no effect; one left on the user's screen (the user is using it) says not to come again and to ask the user to handle it; a dialog that must be handled by the user personally says not to move it back and to ask the user to tap there (`needsUser`). For an App installed twice, after asking which one to open it reports which copy was opened (`inProfile` main/other, by the user the task belongs to), and for the other copy hints to go back and choose the other one if that was not what the user wanted. If it opens a while after the action, it is moved back before the next screen read and the screen read carries `opened`, and the next action is not done and reports `opened_elsewhere`. A batch of actions or a phone script stops when it encounters this.
- **Takeover**: when something must be handled by the user personally (sign-in, verification code and the like), `hand_to_user` sends a notification; the user taps 「我来处理」 (I'll handle it), and the App on the virtual screen is moved to the main screen; when done the user taps 「处理好了」 (Handled) or 「我自己做完了」 (I did it myself) and it is moved back, and the Agent first re-reads the UI to verify before continuing; 「跳过」 (Skip) does not count as done (`app/takeover/Takeover.kt`). Takeovers for multiple tasks are queued.

### web: built-in browser

- WebView renders on a private virtual display created by the App (`app/cap/web/WebHost.kt`), does not take up the phone screen, and does not need the built-in assistant; it uses desktop pages by default (`app/cap/web/cdp/DesktopProfile.kt`), and can remember desktop or mobile per website (`web_site_mode`). When the user has chosen an interface language in Claire (not following the system), web pages are requested in that language (`app/cap/web/cdp/PageLanguage.kt`): Accept-Language and navigator.language(s) are changed through `Emulation.setUserAgentOverride`'s acceptLanguage (e.g. English → `en-US,en`), added on top of the desktop identity for desktop mode, while mobile mode keeps the WebView default UA and UA-CH and only changes the language; if the first page was already sent before the session was set up, it reloads once after setup, and a tab whose language changed midway switches before the next main-document load; when following the system it does not override and sends the string the system gives.
- Pages are operated through the WebView DevTools protocol (`app/cap/web/cdp/WebDevtools.kt`); clicks and input are real input events; when it cannot connect it falls back to injected page scripts. It never opens the Runtime group (`Runtime.enable`): with it on, the page can tell a debugger is attached, and on real devices some websites therefore keep reloading forever; reading scripts and page scripts uses only the isolated world and evaluation (a page script's mika calls go through an outbox in that world and are handed back by an always-attached intake evaluation, without the binding that needs Runtime), and a lost world is recognized by the main frame replacing the document (`Page.frameNavigated`) and by evaluation reporting that the context is gone.
- In the element tree of the screen-reading script (`app/src/main/assets/web/page.js`), password fields, and text input fields and textareas whose autocomplete marks them as bank card number, security code, expiry or one-time code, only report how many characters were filled, without the value; text in such textareas also does not enter the body of page reads and summaries. Verification after typing still reads and compares the value inside the App as before, and is not handed to the model.
- Tab pool: at most 4 per task and at most 8 globally (`app/cap/web/WebTabPool.kt`, `TabBudget.kt`). Links that would jump to an external App are not followed.
- Downloads land in `downloads/` in the current conversation's workspace and are not opened or installed; uploads submit only files from the workspace (`WebDownloads.kt`, `UploadStaging.kt`).
- Read-only scripts: `web_evaluate_js` runs in the page's isolated environment; the page object is a read-only wrapper, writing, tapping and navigating are all blocked, and it cannot access the network either (fetch, XMLHttpRequest, sendBeacon, WebSocket, EventSource, new Image() and the like report blocked_network, and any request seen from it on DevTools also ends the run with an error; for data behind the page use `web_capture` to read the responses the page itself received); secret input fields such as password fields read out as `***` (the same for same-origin iframes, shadow roots and templates), while on their own interfaces only page-defined attributes such as type and name are read, innerHTML and the like, and the textContent of outer elements containing secret textareas, are masked on a copy that belongs to no window (without constructing the page's custom elements), and child text nodes of secret textareas and value attribute nodes of secret inputs also read out as `***`, even after being obtained and detached from the page; selecting elements by value attribute reports invalid_selector, selectors are first restored according to CSS rules (escapes, comments, namespaces) before judging, anything with `url(` is blocked, and `web_script`'s `mika.query` uses the same set (`core/cap/web/ReadScript.kt`, `SelectorPolicy.kt`). Site commands (scripts in website knowledge with a `/* mika-command` header, `core/learn/knowledge/SiteCommands.kt`) also run read-only through `web_run_site_command`; currently there are no site commands in the built-in knowledge, so this tool does not appear. Scripts run by `web_script` cannot reach the page and can only operate through Claire's action entry.
- Login state: the site registry `SiteRegistry` records visited sites, whether they have been signed in to, and whether they have been blocked by verification; Settings → Website sign-in can open sign-in, sign out of one site, or sign out of all (`app/cap/web/WebLogin.kt`). - The user's own browser (sidebar 「浏览器」 (Browser), UI in `app/browser/ui/BrowserScreen.kt`, `BrowserStart.kt`, `BrowserPageParts.kt`, tabs in `app/browser/UserBrowser.kt`): a visible `WebTab` that shares the same web configuration (cookies, web storage) as the Agent's tabs, so signing in here also means being signed in when Claire does tasks. The sandbox programs are arm64-only, other devices show 「此设备不支持(需要 arm64)」 (This device is not supported (arm64 required)) and the model is told not to use this group of tools. For the source and build see `tools/sandbox/README.md`.
- One workspace per conversation, `/workspace` in the sandbox, kept across messages; files attached in the chat are placed in `/workspace/inbox/`; `share_file` saves a file to the phone's 「下载/Claire」 (Downloads/Claire) and shows it in the conversation as a file card; when the card is tapped, web pages, Markdown, PDF, images and text-like files open in the App's viewer page (`FileViewerActivity`, see §15), and the rest are handed to an App in the system that can open them.
- Online by default; only after turning off 「允许脚本联网」 (Allow scripts to access the network) in Settings → Advanced → Files and compute environment does it go offline; when the device cannot isolate the network, it can only run with 「允许脚本联网」 on (`AndroidSandbox`, the hint in `AdvancedSection`). Each task has a cumulative runtime budget, and the same command failing repeatedly is stopped (`core/cap/sandbox/SandboxGuard.kt`).
- **Network proxy**: it uses Settings › Advanced and other settings' 「网络代理」 (Network proxy) (see §12 \"Network proxy\"); this page does not show it again. It is given only to commands allowed to access the network (`AndroidSandbox` passes empty when offline), and put into `http_proxy`/`https_proxy`/`all_proxy` (one each in upper and lower case) and `no_proxy` (`LocalHosts.NO_PROXY`: this machine, LAN subnets and suffixes go direct) through `ProcRunner.env`; `https://` proxies are only usable by commands here.
- **Space used**: a group further down the same page (`SandboxUsageReader`, `app/cap/sandbox/SandboxUsage.kt`): how much the total, the runtime environment, skills and conversation workspaces each take, then lists workspaces by conversation (by conversation title, with deleted conversations written as 「已删除的对话」 (Deleted conversation), largest first). Sizes are counted by ordinary files in the directory tree, without following links (`AndroidSandbox.treeBytes`). Tapping a row first confirms and then clears that workspace, and the last row clears all; like deleting a conversation it deletes by handle through the file gate, without following links, holding the tree lock's exclusive permit (`SandboxDirs.exclusiveWrite`, used for deleting and replacing a whole directory tree), mutually exclusive with commands, import and reset, and only after getting the permit does it check whether the conversation is busy (when clearing all it checks again before deleting each one); while a large directory is being deleted all conversations' sandbox commands wait; a conversation with a task running or queued states 「暂时不能清理」 (Cannot clear right now) and is skipped when clearing all. The runtime environment and skills come with the App and are not cleared here (to prepare from scratch use 「重置运行环境」 (Reset runtime environment)). The phone storage is not mounted in the container.
- Tools: `run_command`, `run_bundled_script` (runs scripts bundled with knowledge and skills, see `docs/dev/skill-scripts.md`), `read_file`, `write_file`, `search_files`, `share_file`.
- **User terminal**: the user can open a terminal of their own from the conversation's long-press menu or the workspace row in Settings, and run commands in the same conversation workspace. It goes through `SandboxPort.openShell` / `AndroidSandbox.openShell`: the launcher gives `/bin/sh` a pseudo-terminal with `--pty`, with no time limit, taking `SandboxTree.lease` (reclaimed when resetting or clearing the workspace, stopping the whole process tree); it does not connect the phone bridge, so the `mika` command is unavailable in the terminal. Sessions are managed per conversation by `app/terminal/TerminalHub.kt` (at most two globally), and `TerminalSession` keeps the latest 1 MiB of output for a reattached UI; the UI is a WebView + xterm.js (MIT, resources in `app/src/main/assets/terminal/`) in `app/ui/terminal/TerminalWebView.kt`: output is written into xterm in 64 KiB base64 chunks, and input goes back to `TerminalSession` through `Bridge`; xterm's `onResize` calls `SandboxShell.resize`, letting mikarun change the pty with `TIOCSWINSZ` through the `--pty-size` file (the kernel sends SIGWINCH), so rotating the screen or the IME popping up can re-lay it out. OSC 52/8 are swallowed, and page navigation is always blocked. The terminal does not go through `ActionExecutor`, does not write run records, the evidence ledger or the conversation, and does not provide any tools to the model; the network state is frozen when the session starts, with the same settings as `run_command`.
- Commands in the sandbox can call the current task's phone tools with `mika phone <operation> '<json args>'` (`app/cap/sandbox/SandboxBridge.kt`, `BridgeProtocol.kt`): each command run gets a randomly named local socket and a one-time token, and which are open is declared by the tools themselves (`ToolInfo.sandboxCallable`: phone capability tools are open by default, vision tools are not; new phone tools need no list change), and `<operation>` is the tool name without `phone_` (`type`, `clear`, `key`, `launch`, `dump` are shorthand for `phone_type_text`, `phone_clear_text`, `phone_press_key`, `phone_launch_app`, `phone_list_elements`). Each operation still goes back to the single entry point through `SubActions` and is written to the run record, with the same timeouts and limits as calling directly (`phone_wait` / `phone_event` at most 30 seconds, `phone_system_command` 10 seconds). There are also `mika share` and `mika progress`.

### Vision

With a model that can see images (§12), it provides `phone_describe`/`web_describe` (describe the interface) and `phone_find_visually`/`web_find_visually` (locate by looking at the image, `core/screen/vision/Locator.kt`: first find exactly in the control tree, and only when not found let the model frame it, then check the name; a model whose locating accuracy has not been verified needs supporting evidence, but when this screen's tree is unusable or is missing a part and what is sought is not in the tree, there is nothing to compare against, so the frame is handed over anyway, marked `unverified`, and after tapping the effect speaks). Describing the interface reads the whole screen and writes a large paragraph once, several times slower than locating: the prompt only lets it be used when you cannot tell what page it is, and the description requirement (`roles/describe.md`) also asks only for a brief four paragraphs—at most 15 lines of interactive elements, a few characters each, no text that is not a control, only the first few items of a long list, and at most two lines of hints. The screenshot tool is provided only when the main model can see images. Graphic captchas are not solved by itself; they are handed to the user.

### Child tasks

`spawn_agent` (`core/general/SpawnAgent.kt`, `core/run/ChildRuns.kt`) dispatches a child task to look into a bounded question: web and sandbox only, read-only, with nobody present, 15 steps by default (the model can pass `maxSteps`, 1–40), cannot ask follow-up questions, cannot send outward, cannot write memory, cannot create schedules, cannot dispatch further child tasks, and has no knowledge and skill lookup tools. The result has a length cap (4,000 characters by default, the model can pass `maxResultChars`, 500–8,000; out-of-range values are pulled back into range, and non-integers are rejected as a parameter error; when truncated the result writes `truncated` and the original length `fullLength`; the executor hands back the full text, and the persisted record separately stores a preview of at most 4,000 characters), and is handed back to the parent task as an untrusted observation; only one is dispatched at a time, and the parent task waits for it to finish; a child task finishing does not mean the user's goal is complete. It is offered only in runs started from the conversation UI and with web capability.

### Records of previous turns

The conversation's context carries only the outcomes of the most recent turns (`Conversation.context`: at most 5 turns, 2,500 tokens), and the original text read in previous turns is not carried. `history_read` (`core/general/HistoryRead.kt`) lets the model look it up itself: without `turn` it lists previous turns (newest first, at most 20: which turn, the user's original words, the outcome, the start time, and whether there is a detailed record); with `turn` (1 = the turn just past) it reads that turn's full outcome, what the user interjected midway, Claire's progress explanations (the text in replies that carried tool calls) and the original text read (the `observed` in the run record, with the same original text given only once), paginated by item (`offset` / `nextOffset`, about 8,000 characters per page, at most 2,000 characters per item), without screenshots. It only recognizes turns of the same conversation brought in at this run's start (`Turn.runId` in `RunSpec.priorTurns`); other conversations and other runs cannot be looked up; it is read-only. The original text comes from the run record (`core/run/record/RunRecords.kt`, on the App side `RunStore.reader()`, read on an IO thread), and was already redacted and truncated when persisted, and is given as-is when read; untrusted things such as web pages are still wrapped in `<untrusted>`. The original text read is handed to verification as an observation (the source is recorded as `history`), so values read earlier and used in the answer can be traced. The run record keeps only the most recent 30 runs, and an earlier turn has only its outcome left (`recorded=false`). It is provided only when there are run records and there are previous turns that recorded runs, and then the context ends with one extra hint line (the history_hint item in `feedback/loop.md`). Child tasks have no previous turns and are not offered it. It can also be called when discussing history (when the intent is judged as discussion).

### Computer connection: CLI and MCP

Two directions. **Claire as an MCP server** (computer connection) is already hooked up, with two ways to connect: over USB (the computer turns it on with adb, listening only on loopback) and over the LAN (the user turns it on in Settings, off by default); **Claire as an MCP client** connects to external servers (Settings › Advanced › MCP servers): `core/cap/mcp/HttpMcpClient.kt` uses Streamable HTTP (2025-03-26), `LegacySseMcpClient.kt` uses the old HTTP+SSE (2024-11-05), and `StdioMcpClient.kt` uses a local process in the sandbox; `McpOAuth.kt` supports OAuth 2.1 discovery, dynamic registration, PKCE and refresh, and a Bearer can also be filled in manually; tools set their risk by annotation and are frozen at run start, and resources/prompts are synthesized into read-only tools. External tool names are uniformly `mcp_<server-id>__<tool-name>`, with invalid characters replaced by underscores; tools longer than 64 characters or whose names collide after cleaning use a short name with a SHA-256 digest. `mcpToolNames` first keeps the declarations that need no renaming, then sorts by original tool name to assign short names; if a short name collides again with any final name, it increases the digest length and recomputes, so it is globally de-duplicated before registration, and a server reordering does not change the mapping. When the server lists the same original name repeatedly, only the first item is kept and the reason for degradation is recorded, while calls still use the uncleaned original name. The setting is in `app/settings/McpServerStore.kt`, with tokens stored encrypted. At the start of a task `McpServerStore.connectionsFor` connects all enabled items in parallel, waiting at most 15 seconds in total (`CONNECT_BUDGET_MS`, separate from a single server's own timeout for tool calls); ones not connected by the deadline are not connected this time and are closed, recorded in the health status (stating they were skipped after the timeout), with a hint on the task card, and it is not counted as a task failure; ones that connect are put into the task's `ResourceScope` on the spot and closed together at wrap-up (ending, cancelling, failing, or being stopped midway through connecting). The external endpoints handed to `toolDispatcher` are just one `mcpServers` list, assembled in one place by `TaskRun.mcpEndpoints()`, and when other sources also provide such endpoints later they will be assembled there. A stdio server's process, while alive, holds a lease of the sandbox tree (`SandboxTree.lease`), not an ordinary shared permit: things that need exclusivity (switching the root filesystem, resetting, clearing the workspace) first stop these processes and take back the permit before acting, without waiting for the task to end and without worrying about missing a close; afterwards calls to that server truthfully report that the connection is closed. The low-level tool session (`core/mcp/McpServer.kt`) is the other direction. For user docs see [mcp.md](../mcp.md) and [cli.md](../cli.md). The computer CLI uses the plain HTTP task API, alongside the MCP adapter, sharing one task service.
The MCP client passes each connected server's `instructions` to the model as bounded, untrusted guidance. The same interface covers Streamable HTTP, legacy SSE and stdio; guidance does not change tool risk or grant user approval.


The **server**'s layers are all in `:core`, and the whole set can be tested on a computer:

- `MiniHttpServer` (`core/remote/HttpServer.kt`): a shared minimal HTTP/1.1 listener. One thread per connection; the connection count, request headers and body all have limits; it understands Content-Length and chunked, and connections can be reused. It keeps the path and query parameters for the entry point to validate; it does no TLS, guarding instead by accepting only private addresses and the access token.
- `RemoteAccess` (`core/remote/RemoteAccess.kt`): the shared gateway for both entry points, in a fixed order: 403 for a request with an `Origin` header; an address that fails authentication 5 times within a minute is blocked for a minute (429, with `Retry-After`); the `Authorization: Bearer` token is compared in constant time, and a mismatch returns 401. Routing and the error format are decided by the adapter, and unknown paths also pass authentication first. `privateAddress` judges loopback, LAN, private-network and link-local addresses; if either end of the connection is not a private address it is disconnected on the spot. The LAN token recognizes all allowed connections, and the USB token recognizes only loopback; both are compared, without short-circuiting. Authentication failure counts are shared across the API and MCP.
- `RemoteTaskService` (`core/remote/RemoteTaskService.kt`): protocol-independent use cases for starting, querying, listing, waiting, answering and cancelling, which validate input and task state in one place and return typed results and business errors; it contains no HTTP, MCP tool names or JSON-RPC envelope. `RemoteTasks` / `RemoteTask` / `RemoteStatus` are in `core/remote/RemoteTasks.kt`; states are mapped only from the existing `TaskState`, and both entry points share fields and the same task index. Waiting returns on state change (a progress-explanation change does not count), at most 50 seconds; if the task in the index disappears it reports that it does not exist. The mcp- prefix is kept for compatibility with existing remote conversation ids and is isolated from local phone conversations.
- `RemoteTaskApi` (`core/remote/RemoteTaskApi.kt`): the plain HTTP/JSON entry point `/api/v1`, providing the version, the task lifecycle, read-only device status, and exporting redacted run records by task id or run record id (`GET /tasks/{id}/export`, with run_export in the capabilities only when there is a record export). No MCP handshake or tool discovery is needed. Business errors are mapped to HTTP status and code/message; unknown fields are rejected. For the detailed contract see [CLI docs](../cli.md#http-contract).
- `McpRpc` (`core/mcp/McpRpc.kt`): JSON-RPC over Streamable HTTP, returning only a single JSON and not opening an SSE stream (the spec allows it); GET / DELETE return 405, no session id is sent, and the server sends no requests. Both protocol generations are recognized: the new generation (2026-07-28) carries the version and client capabilities in `_meta` on every request, and the `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` in the HTTP headers must match the body (mismatch is -32020), an unrecognized version returns -32022 and lists the recognized versions, and `server/discover` is supported; the old generation (2025-03-26 to 2025-11-25) first does an `initialize` handshake and picks a version both sides recognize. Wrong tool arguments or a task that cannot be found are tool execution errors (`isError`), handed back to the model on the other side to see; an unrecognized tool name is a protocol error.
- `McpTaskTools` (`core/mcp/McpTaskTools.kt`): keeps the original tool names, schema, MCP prompt text and return format, and converts arguments into calls to the shared service. `mika_run_task` / `mika_task_status` / `mika_wait_task` / `mika_answer` / `mika_cancel_task` / `mika_list_tasks` all do not store task state separately. Payments, confirmations and phone takeover cannot be let through by an ordinary answer.
- `RemoteEndpoints` (`core/remote/RemoteEndpoints.kt`): the shared protocol routing after transport authentication, holding `RemoteTaskService`, handing `/api/v1` to the plain API and `/mcp` to MCP, and recording recent activity. It does not authenticate connections; the caller first completes the corresponding entry point's authentication.
- `CompanionApi` (`core/remote/CompanionApi.kt`): the three read-only Web console endpoints—conversation list, conversation turns (paginated, truncated) and running tasks; the data is read live by `RemoteCompanion` from the App's conversation storage and task center, without storing state separately or entering the execution path. The gateway side's `/app` page and sign-in session are in another change in `companions/relay`, see [anywhere.md](anywhere.md).
- `RemoteHost` (`core/remote/RemoteHost.kt`): the LAN/USB entry point, holding `RemoteAccess` and the HTTP listener, handing to the shared routing after authentication. `bindAddress` selects all network interfaces or IPv4 loopback 127.0.0.1, consistent with ADB forwarding. The private-address check is not relaxed because of the remote gateway.
- `RelayGateway` / `RelayClient` (`core/remote/`): HTTPS pairing and an active WSS channel, not following redirects, forwarding only fixed MCP POSTs. Requests have independent ids, bounded concurrency and body size; duplicate ids are not executed; cancellation and disconnects interrupt waiting; the connection is re-established with backoff but operations are not replayed. User authorization already verified by the gateway is not passed through as a USB token, and a loopback source is not forged. The tunnel and the local entry point share protocol routing, and tasks are still handled according to the existing remote origin.
- `McpUsb` (`core/mcp/McpUsb.kt`): the convention with the computer over USB. The connection info `mcp-usb.json` adds the plain API's api_url / api_version, and keeps the original content (the Streamable HTTP address, the `Authorization` header, the token, the port, the `adb forward` command, and this boot's number `boot`); 「connect-computer.sh」 (connect-computer.sh) on the computer: it does not run unless it is shell (uid 2000), first runs 「usb-start.sh」 (usb-start.sh) once to start the phone assistant, then `am start-foreground-service` to start `McpService` (action `USB_ON`, and `USB_OFF` when it carries the `off` parameter), waits until connection info whose `boot` matches `settings get global boot_count` is written (recognizing that it is not left over from the previous boot), and prints it; when turning it off it waits for the file to be deleted. The script carries no secrets.

**On the App side**:

- Self-hosted remote mode: `RelaySettings` (`settings/RelaySettings.kt`) atomically saves the whole pairing and switch encrypted, with a separate Keystore key; the state flow contains only non-secret fields. `McpRuntime` manages this path independently of the original listener, and when remote is on it reuses the `McpService` foreground service. The notification's close action also closes remote access. Pairing itself does not enable access; after closing, the pairing is kept, and unpairing first closes and then revokes at the gateway. `RelaySection` is the 「远程」 (Remote) item in the MCP guide, using existing components and resources in Chinese, English and Traditional Chinese, and does not display the stored token.

- The LAN kind: the switch and port are stored in `files/settings/mcp.json`, and the access token (a 32-byte random number) is stored encrypted via `KeyCipher` in `mcp-token.bin` like a service provider's Key (`settings/McpSettings.kt`), off by default.
- The USB kind (`settings/McpUsbSettings.kt`): another switch and another token, stored in `files/settings/mcp-usb.json` (together with this boot's number `Settings.Global.BOOT_COUNT` when turned on). Turning it on generates a token; turning it on again while already on reuses the old one; after listening starts it writes the connection info to `mcp-usb.json` in the external files directory (from Android 11 other Apps cannot read it, but shell can; the token has to be handed to the computer in plaintext anyway, so it is also stored in plaintext in the private directory); if it does not start, it deletes it. Turning it off forgets the token (a new one next time) and deletes both files. It does not survive a reboot: if the boot number changed it is treated as off, and last time's files are cleared along the way.
- `McpModes` (`app/mcp/McpModes.kt`): how the two switches combine. Only one port is opened: when LAN is on it binds all interfaces (loopback included, and USB can still connect), when only USB is on it binds loopback only, and when both are off it does not listen; the actions the service receives `USB_ON` / `USB_OFF` / `TURN_OFF` (「关闭」 (Close) on the notification, turning both off) change which switch.
- `McpRuntime` (`app/mcp/McpRuntime.kt`), one per process: when either is on it starts `McpService` (`app/mcp/McpService.kt`, a specialUse foreground service with one persistent low-priority notification that can close it directly), and it listens only while the service is running; each time the service receives a start it `sync`s once: if the listening mode changed (LAN turned on or off) it switches to another listener, and if USB is on it writes the connection info; when both are off it stops the service and closes the port. At App start it writes 「connect-computer.sh」 once.
- `McpService` is exposed externally and requires the caller to hold `INTERACT_ACROSS_USERS_FULL`: shell has it, an ordinary App cannot get it, and adb cannot grant it (the same gate as the provider for assistant handover), so `adb shell am start-foreground-service -n <package>/.mcp.McpService -a com.kilv.claire.mcp.USB_ON` can only be sent by a computer over USB debugging. It uses a foreground service instead of a broadcast: from Android 12 background Apps generally cannot start foreground services themselves, while a foreground-service start initiated by shell is allowed under the system uid class; if entering the foreground is refused the service exits instead of crashing. A manifest test (`ManifestProvidersTest`) guards this permission. The task service exits by itself when there are no tasks, so the listener is not put in `TaskService`. If the service is reclaimed by the system it is rebuilt (START_STICKY); at boot and when Claire's UI is opened, if the switch is on but it is not running it is started again.
- `RemoteTaskHub` (`app/task/RemoteTaskHub.kt`) implements `RemoteTasks`: `TaskService.startMcp` starts a task, on the same path as the conversation UI, and both CLI and MCP reuse the existing external-task origin `RunOrigin.Mcp`'s permission policy (here a historical name, not meaning CLI goes through the MCP protocol) and presence state `Reachable` (follow-up questions wait as usual, and are treated as unanswered at the deadline; the hand-to-user step has the same deadline, and if nobody handles it past the deadline the task stops). If there is still a task in the same conversation it queues behind it.
  - Receipt records (`app/task/RemoteTaskReceipts.kt`): the `receipts` table of the App-private SQLite database `remote-tasks.db`, one row per remote task: id, conversation, original words, receipt time, whether it opened a new conversation, whether it has been claimed by the task service, terminal state, and where an interjection went. The terminal state and interjection destination are stored as JSON in `RemoteTaskRecord`'s (`app/task/RemoteTaskRecord.kt`) own format, not by serializing `TaskState` / `FailKind` directly: failure categories have fixed names on disk (`gave_up`, `interrupted`, etc.); unreadable ones (bad data, a category written by a newer version) do not throw, an unrecognized category is treated as `environment`, and a wholly unreadable one is returned as a failed terminal state. The answer's evidence ledger is not stored.
  - request_id deduplication: the computer may first choose a lowercase UUID as the request field request_id, and it is the task id. The Hub checks the original request in the same critical section (the original words and conversation parameters must both match, otherwise 409), writes the receipt record, then sends the start Intent; the task service only claims ids not yet claimed (`claimStart`), so concurrent retries and old Intents delivered after the process is rebuilt only start once. Running progress is read from TaskRun, and the terminal state is written to disk before being returned to the computer; if writing to disk fails it is first kept in memory and rewritten on query, and if it still cannot be written it returns 503 to let the computer query later.
  - Interruption: when the database is opened (a new process) receipts that are not yet terminal are marked as failed with category `FailKind.Interrupted`; running remote tasks are recorded the same way when the task service is destroyed. `Interrupted` is like `Environment`: it counts as a runtime-environment matter for scoring, skill trials record it as unreviewed, and learning does not treat it as a failure to do the thing; the reason shown to people uses `task_interrupted` (available in 11 languages).
  - Deleting a conversation: this conversation's remote content is cleared, leaving the ids already used as placeholders (keeping the receipt time), and a late retry returns 410 and is not executed again.
  - Retention: cleared once when a receipt is received and once when the database is opened, clearing only finished ones and placeholders—those received more than 30 days ago, and those outside the most recent 1000 by receipt order; ones that are not finished are not cleared. After being cleared, the same id that comes again is treated as a new request, so deduplication holds only within this window. Ids that existed only in memory before the upgrade cannot be recovered.
  - Answers are handed directly to `TaskRun.answer`, stopping is handled through `TaskService`'s `ACTION_CANCEL_MCP`, and queued tasks are removed directly. Only remote tasks registered here can be queried and controlled from the computer. New conversations ask the model for a title as usual.
- Several security guarantees: payments and confirmations can never be let through from the computer—`mika_answer` only hands an answer to a task waiting for a follow-up question; `request_confirmation` rejects directly in runs not started from the phone (`declined_remote`), and `ApprovalPolicy` always Denies payments in runs not started from the phone; runs started by CLI or MCP start in asking mode regardless of the autonomous switch (`ApprovalControl.start(remote = true)`), so autonomous mode cannot let payments through either. On the phone, notifications for questions and takeover still pop up as usual. The run record's start event states the origin (`RunEvent.TaskStarted.origin` = `mcp`, not written for ones started on the phone), and it is also in the summary.
- Settings page (`mcp/ui/McpScreen.kt`): the top distinguishes access not enabled, waiting for a computer request, recently received requests and start failure; a listener or switch being on does not mean the computer is already connected. First choose CLI / Skill or MCP, then choose the USB or Wi-Fi / private network way shared by both. CLI has only the install and connect steps, and connect verifies the connection itself; the network way provides the HTTP root address, the token file command and token copy, while MCP provides the /mcp configuration. Switching the guide does not change permissions. The access switch, token management and remote wake are in the advanced settings collapsed by default; the network MCP configuration preview is also collapsed by default and hides the token, generating the full configuration only when copying. The address and request time refresh every two seconds within the page as before. `ComputerAccessScreenTest` verifies guide switching, explicit permission operations, status and configuration copying.

`mika_steer_task` and `POST /api/v1/tasks/ID/steer` (CLI `task steer`) append a requirement through the same `RemoteTaskService.steer`. It only accepts `running` remote tasks; `TaskRun.steerRemote` then checks the run, pause/wait and cancel states again, and `RunInbox.steerCurrent` is mutually exclusive with close/cancel. A message belongs only to the current task, and if the task ends before it is consumed it is marked as not used, without falling back to the next task the way UI interjections do. It returns the message id and the inbox receipt confirmation; the task state's `steers` lists only remote messages' `received`/`joined`/`not_applied`, without phone interjections or message bodies, and the terminal state keeps a snapshot.

The plain API provides only read-only device status for the CLI doctor; MCP additionally provides the main-screen preparation tools `mika_device_state`, `mika_wake_device`, `mika_unlock_device`. They belong to host device management (the same as pairing and recovery), and are not registered as the model's `AgentTool`, do not enter the model context, action history or credential logs. After MCP's original authentication, `McpDeviceTools` calls `core/device/DeviceAccess.kt`: main-screen state → wake up → request showing the credential page → enter the local credential if necessary → verify the system state. The core depends only on `DeviceAccessPort`, `DeviceAccessStore`; the Android adapter is in `app/device/`, the main-screen input's shell implementation is in `cap/phone/shell/DeviceUnlockInput.kt`, AIDL has a separate method, and the ordinary virtual-screen key whitelist stays unchanged.

`DeviceAccess` is one per process, serialized by a Mutex; remote permission is off by default, and credentials can only be set on the phone. `unlock(authorized)` rechecks the origin's authorization after acquiring the lock and before waking up, showing the credential page and submitting the credential, and it can only narrow the local master switch. `DeviceAccessSettings` encrypts and atomically writes the whole configuration with a separate Keystore key, caching only non-secret state. Before input it persists a failure placeholder, and clears it only after the system is already unlocked; after a failure or interruption the credential must be saved again on the phone. The Android adapter only enters on the main screen SystemUI's single, type-matching password field, and does not handle SIM PIN or unrecognizable vendor pages; when the input field does not declare an input type, it treats it as a PIN page if 0–9 digit keys are all present in the same window, otherwise as a password page; when the input field cannot get focus it first requests focus and then taps once, and if neither works but the SystemUI window it is in is the input-focus window it still counts as being able to input; credential keys are injected in a targeted way via `ShellService.injectTo`, only to the focus window owned by SystemUI (`injectInputEvent(event, mode, targetUid)` from Android 13), and the system refuses when there is another window above the lock screen or when it has been unlocked and returned to the App, so keys do not land elsewhere, and modifier keys are also released to SystemUI only after the key was sent; before Android 13 credentials are not entered (`unsupported_keyguard`). `TaskGate` continues only after the system has actually lit up and unlocked; if it is still locked after automatic unlock returns, it ends the task with the corresponding origin's text. The settings UI is a grouped card on the computer connection page, using the existing row/input/button components and Chinese and English resources; credentials do not enter restorable UI state, and screenshots are blocked while editing. This feature does not change the task origin or payment policy.

## 7. Context and compression

- **Cache partitions** (`core/agent/ContextBuilder.kt`, `ContextCompressor.kt`): partition 0 is the system prompt and tool definitions, which within a task changes only when a group of tools is expanded (each group at most once, and only the part from that group onward changes), and is otherwise unchanged character for character (except for two kinds of request: the final turn after steps are used up offers only the give-up tools, and the re-ask when judged as discussion offers no tools); partition 1 is the opening context, written once and not changed (previous conversations, memory and profile, the task's original words, available channels, App/website knowledge, and the knowledge and skill index; everything except the user's original words is wrapped in `<context kind=… source=… trust=…>`); partition 2 is history, append-only; partition 3 is this step's result, screen and runtime state (which interface, which step, local time, the beginning of the user's own typed text in their most recent message, appended to the end of the last message). Text the main loop writes to the model (the shell's source and trustworthiness, runtime state, reminders, explanations of confirmation and takeover, replay progress, tool results, folded summaries) is always in English, consistent with the system prompt and tool descriptions, so the model does not answer in Chinese; text shown to the user still follows the interface language.
- **Append-only**: normally messages already sent are not rewritten, and the full history is never modified; only during compression is it rewritten uniformly once on a copy. When `AnthropicModel` sends back assistant messages, blocks stay in the order received and thinking blocks are not moved. Models from Claude 5.1 on also verify the returned thinking blocks: the signature is bound to the system prompt, tools and preceding messages that produced it, and after expanding a group of tools or compressing (and also in the final turn after steps are used up, and the re-ask with no tools when judged as discussion) it no longer matches, and on some accounts and models it returns 400 directly. When rejected, `AnthropicModel` removes the thinking blocks carried this time and sends again, and subsequent requests from the same model instance (one per task, shared by child tasks) no longer carry them (they remain in the history), and anything received after the resend is returned as usual. What checks partition 0 and append-only by the online bytes is `PrefixStabilityTest` (OpenAI-compatible interface) and `PrefixStabilityAdaptersTest` (Responses, Anthropic, Gemini and caching-marking compatible interfaces), running the same 30-step fake task: partition 0 changes only on expansion, and history is rewritten only on compression; the latter also checks that replay's encrypted thinking, thinking signatures and thoughtSignature are carried completely on every step, and that Anthropic carries no more than 4 cache markers in one request.
- **Token budget**: the opening context, memory, previous turns and App/website knowledge are all counted in tokens (`TokenEstimate` rough estimate): total 8,000, Task 4,000, Knowledge 5,000, a single document 2,000; full memory 4,000, retrieval 800; previous turns 2,500 (when only one turn is left and it is still too long, the original words and outcome are truncated separately); previous turns carried by outcome judgement and intent judgement 800. Counting in tokens makes each language take up the same amount of context: compared with the old character-based quota, English can hold about twice as many characters and Chinese about a third fewer; the bundled App/website knowledge documents are all within 2,000 each. During compression the line for a "large result" is 1,000 tokens (the token count corresponding to the old 4,000 characters, with the handling of English and JSON results unchanged). Tools' and the UI's own limits (`maxChars`, `OutputClip`, web read and script results, summary fields, citations, skill docs, etc.) are still by character and have not changed.
- **When to compress**: always by the **whole request** (system prompt + tool definitions + messages, the same measure as the input tokens the provider reports). The size of the whole request is computed by `UsageMeter`: when there is a recent reply from the same model with real usage, = that request's input tokens (already including the prompt and tool definitions at the time) + this reply's output minus the thinking tokens the provider reports separately (`Usage.reasoningTokens`: compatible interfaces' `completion_tokens_details.reasoning_tokens`, Responses' `output_tokens_details.reasoning_tokens`, Gemini's `thoughtsTokenCount`; Anthropic does not report them separately, so all output counts) + the estimate for later messages + the change since then in fixed overhead; when there is no anchor (the first step, after switching models, just after compressing) the messages and fixed overhead are fully estimated. Fixed overhead is counted only once. Estimates always multiply by the same "real / rough estimate" ratio: calibrated smoothly once real usage exists, and previously a conservative 1.2. The trigger point is computed in exactly one place, `ContextLimits.of`: available = window − output reservation (at most 20K, and a quarter of the window for small windows); trigger point = available − margin (at most 13K, and a quarter of available for small windows), not below half the window; one compression compresses below "half of available, and one margin below the trigger point". Example: for a 32K window the trigger is 18K, for 128K it is 95K, for 1M it is 967K. After compressing it must grow by at least another margin before compressing again (hysteresis), but never beyond the available window; so history with very large fixed overhead that cannot be compressed is not compressed every step either, and only compresses every step when it truly reaches the edge of the available window. The window and absolute trigger point in Settings are stored per provider and model, assembled through `ProviderStore.modelFor`. An unspecified trigger point is computed automatically by `ContextLimits.of`, and a manually entered value uses the same range. When the provider reports the context too long, it resends once at a more aggressive tier. Three interfaces—OpenAI-compatible, Responses and Anthropic—all count as reporting too long when they return HTTP 400 and the content says the context's length, size, limit or window was exceeded ("exceed", "longer than", "larger than", "greater than", "max" followed in the same sentence by context length / size / limit / window or model length (the wording when a request with images is too long), plus the previously recognized `context_length`, "maximum context" and the old self-hosted service's "context length of only"; merely mentioning words like "context window" does not count, and the error may echo words from the request) (`ModelHttp.contextTooLong`); an OpenAI-compatible streaming request that returns 200 and gives one such error frame in the event stream also counts. Anthropic additionally recognizes 413 and "prompt is too long", and Gemini uses its own rules. When the window is left empty the selected model's context length is used.
- **How to compress** (without calling the model): first shorten old results before the most recent 12 turns (old screen reads are replaced with placeholders, and web, command and file content is truncated only when too long; placeholders keep observation ids), then fold old turns into "Earlier steps (compressed)"; if still not enough, tighten tier by tier. A structured summary (`StepSummary`) is implemented but off by default. When an action carries a screen, the most recent full screen read before the fold boundary is not folded, and the leftover diffs mostly attach after it (the diff reads in between were already replaced with placeholders in the shortening step); when the leftover round-trips' unshortened screens can be understood on their own (at least one, with the `base` of every diff among them), it folds as usual, and folds as usual even under heavy compression. The tier that only shortens and does not fold keeps it as before.
- **Never trimmed**: what the user said (the task's original words, interjections, answers) is never trimmed; the turns of follow-up questions, confirmations and takeover are not folded. After compression `ContextRecovery` puts the missing user messages and opening context (previous conversations, memory, knowledge, skills, channels) back in place.

## 8. Parallelism

Tasks in different conversations can run at the same time, with one virtual screen per task (`app/task/ParallelCapability.kt`): this requires Android 14 and above, with the speed switch 「不同对话同时进行」 (Run different conversations at the same time) turned on (off by default), and a limit of 1–3 (2 by default); on low-memory devices, or once creating a second screen has failed, only 1 is allowed. What is truly exclusive is the same App, main-screen takeover and the clipboard, coordinated in one place by `ResourceScheduler` (`app/task/ResourceScheduler.kt`): the same App belongs to only one task at a time, takeovers queue, the clipboard is locked, and web tabs have a global budget.

**Waiting for another task to release an App**: when opening an App that another task is using, the result is `app_in_use_by_other_task`, and the explanation tells the model it can do something else first, or pass `wait` (seconds, 1–180, `LaunchApp.MAX_WAIT_S`) and call `phone_launch_app` again. Whether to wait and how long is decided by the model per task, with no settings switch. When `wait` is passed and it is still occupied, the tool waits through `ScreenPort.awaitAppFree`: `AndroidScreen` treats "it is not on another screen and no other task holds it in the occupancy registry" as released, and hands it to `ResourceScheduler.awaitApp` (through `TaskCenter.awaitApp`)—which registers "who is waiting for which App", wakes waiters on the spot when a task releases an App (`releaseOwner`, at task end), rechecks every second for Apps on other screens that close themselves without notice, and when released opens it once more, returning `app_wait_timed_out` if it is still occupied at the deadline. Before waiting it follows "the task holding this App is waiting for an App held by ..." all the way; if it comes back to itself they are waiting on each other (the same for cycles of two or three tasks), and it does not wait, returning `app_wait_would_deadlock` (the check and registration are under the same lock, so when two tasks start waiting at the same time the later one sees the earlier one; the earlier one keeps waiting, the later one does not wait and releases the App in its hand when it finishes, and then the earlier one gets it). During the wait the task is still `Running`, with progress `RunProgress.WaitingForApp` (the conversation page, notification and capsule all say 「等另一个任务用完某 App」 (Waiting for another task to finish using an App)), not paused, and not counted as "needs you"; after waiting it is put back to the original line. This is two layers apart from the conversation page's task queue handed to the service (when parallelism is off, if a task elsewhere has started first, the new task queues behind it and starts after it finishes, with 「等前一个任务做完再开始」 (Wait for the previous task to finish before starting) written below the message): that one is the whole task queued behind another task before it starts, running one at a time, so it will not contend for an App; this one is a task already running in parallel waiting for an App midway.

## 9. Experience replay

Successful routes can be recorded, and similar tasks replay them directly, checking lightly at each step without calling the model, and handing back to the model when they do not match (`core/learn/replay/`, with replay actions executed as `Origin.Replay` through the single entry point). Routes are recorded only from runs that succeeded (`LearnGate`, taken from the persisted run events after `TaskRun.settleOutcome` judges the outcome, with `RouteRecorder` only concerned with whether the route itself can be recorded); when replay finishes and this time also counts as succeeded, the route's success count increases by one (`RouteReplay.noteResult`). The speed switch 「照着上次的做法做」 (Do it the way I did last time) is on by default: the old setting is upgraded once by `FeatureFlags` (`speed_defaults_applied_v3`), and after the user turns it off it stays off.

## 10. Scheduling and conditional triggers

- **Tools**: `schedule_task` (`core/general/ScheduleTask.kt`), with `op` = create (default) / list / edit / pause / resume / delete / run_now / reschedule. edit reuses PlanDraft/editedTrigger validation, keeps unspecified fields, and uses an empty string / empty list or 0 for explicit clearing; the host rechecks conversation ownership under the same lock, keeps the plan id and execution ledger, and returns the next three times. It is offered only in runs started from the conversation UI. When resuming a one-time plan that has been claimed (has run or is running) (`TriggerEngine.setEnabled`) it is not changed and reports `already_ran` (the plans page gives no switch for such a plan either); to run it again use reschedule or run_now.
- **Time rules** (`TriggerDefinition`, `core/trigger/Triggers.kt`): one-time (`at`); fixed interval (`intervalMinutes`, with multiple missed runs merged into one and how many were missed recorded); daily or on weekdays by local time (`repeatAt` or multiple times of day `repeatTimes` + `repeatZone` + `weekdays`), keeping the time of day fixed across daylight saving. Multiple times of day are uniformly sorted and de-duplicated, and preview and advancing share nextCalendarAt; when a daylight-saving jump makes two times of day land on the same instant it runs only once.
- **Three ways of doing it**: fixed reminders (`reminder`) are delivered directly at the time without calling the model; task runs execute at the time as a run with nobody present; ones with a `condition` first check the condition with the read-only web and sandbox, with the result structured as `ConditionOutcome` (`core/trigger/ConditionOutcome.kt`), and a check error does not count as "not met". The check goal is generated by `conditionCheckGoal` (`core/trigger/ConditionCheck.kt`): the condition's original text, the comparison baseline, and the requirement to output only `{"met","value","evidence"}`; `value` is the key value used for comparison next time (format characters removed, whitespace collapsed to one space, at most 80 characters); the baseline, when written into the check goal, is marked as untrusted content (`Untrusted`). The baseline (`baselineValue`) is the value at the last dispatched action, or the value seen at the first check if it has never been dispatched. Whether to execute is decided by `afterCheck`: when `notifyWhen` is `ConditionNotify.BecomesMet` (default) it executes only when the condition goes from not met to met, and with `ConditionNotify.EachTimeMet` it executes every time it is met; when `cooldownMs` is set, the cooldown counts from the scheduled time of the check that last executed the action (how fast or slow the check runs does not matter), and during the cooldown a fire that would execute is skipped and not made up (`lastConditionMet` is not moved), while a check after the cooldown ends that is met still executes. Skipped periods record the reason `condition_not_met`, `condition_unchanged` or `cooldown`. When starting the action fails synchronously, `revertFire` rolls the dispatch state back to before the check; if a baseline existed before the check it is rolled back too, and if not the one recorded this time is kept. After the action has been registered or started, the dispatch baseline is kept whether it succeeds, fails or is cancelled, and the same change is not replayed automatically. The check run's goal is the generated check instruction; the turn recorded into the conversation (a check error, cancellation while queued, clean-up after an interruption) and the progress notification use the condition text the user wrote (`StoredRun.userText`), without recording the check instruction as the user's words. `whenIdle` makes it wait until no task is running.
- **Scheduling** (`app/task/TriggerRuntime.kt`): the system alarm is only a wake-up signal, and `FileTriggerStore` is the real source. The main plan file keeps the old schema, and newly added observations, baselines, notification mode, cooldown and multiple times of day are put in a `.conditions` sidecar next to it; old versions can still read the main plans (multiple times of day degrade to the first), and a damaged sidecar only loses the extension state without clearing the whole plan file. Before dispatching it first writes the next time and this window (id = trigger + due time), and the same window is not dispatched twice. A plan whose window has already been recorded is not claimed again, and `rearm` does not schedule an alarm for it either (the condition for checking the ledger when judging the condition and when claiming is the same, see `slotTaken`): scheduling by an overdue due time means it rings immediately, and when it rings it cannot be claimed, so it spins forever. It uses exact alarms when possible; without permission the first time it sends a notification guiding the user to turn it on in system settings, and `schedule_task`'s result also tells the model 「可能不准时」 (May not be on time); the plans page shows a hint. It re-arranges on boot, time change, time zone change and exact-alarm permission change (`app/setup/BootRestoreReceiver.kt`), and also at App start. The device time zone is recorded in `triggers` (`TriggerRuntime.syncTimeZone`): when the time zone changes, at App start (also filled in when the time zone changed while off; the first time it only records the current one), and compared with the recorded one, and if changed, local-time plans that follow the old device time zone are recalculated in the new time zone (`TriggerEngine.rezone`), while ones explicitly pinned to another time zone are left alone.
- **Results go back to the original conversation**: a task at the due time runs in the conversation that created it, and its result, reminder and failure explanation are all written back to that conversation, and tapping the notification opens it.
- **Run duration and consecutive failures**: Settings › Task runs' 「定时任务最长运行时间」 (Maximum run time for scheduled tasks) (`FeatureFlags.triggerRunMinutes`, 15 / 30 / 60 / 120 minutes, unlimited by default): a run triggered by a schedule (including condition checks) stops after running this long, with the outcome recorded as `FailKind.TimeLimit`, and like running out of token budget it does not count toward whether a skill works. Before the result notification is sent it counts backward from this plan's own period records how many consecutive failures there have been (`failureStreakBefore`, stopping at a delivered or unknown result, and not counting skips where the condition was not met), and when this one brings it to 3 or more the notification title states 「已连续失败 N 次」 (Failed N times in a row), with the body ending with a reminder that the scheduled tasks page can pause or modify it.
- **Process killed midway**: reminders are delivered again (de-duplicated by id); other claimed windows are marked as an unknown result, explained in the original conversation and notified 「Claire 不会自动重复操作」 (Claire will not repeat the operation automatically).
- **Plans page** (`app/task/ui/PlansScreen.kt`): split into 「进行中」 (In progress) and 「已停用」 (Disabled) sections, each row with three lines (what it does, the repeat rule and next time or status, and the last result: skips are split into 「条件未满足」 (Condition not met), 「条件未变化」 (Condition unchanged) and 「冷却期内」 (Within cooldown), and when that check recorded a value, it is shown too), with the switch on the right being pause and resume; tapping a row raises an action panel: view conversation, run now, edit, delete; the top right can create directly. The editor's daily/weekly time of day supports comma separation, and previews the next three times.

## 11. Knowledge and skills

- **Built-in** (`core/src/main/resources/`): App knowledge (`knowledge/apps/<id>/APP.md`), website knowledge (`knowledge/sites/<domain>/SITE.md`), skills (`skills/<id>/SKILL.md`), one document per directory, so adding one means adding one directory; to see what exists look at these directories or the index generated at build time `knowledge/index.json`, and the list in the README is generated from the same index by `./gradlew updateReadme`. For the format see [`knowledge-format.md`](knowledge-format.md). At build time `KnowledgeIndex` scans the headers, validates and generates the index, and a validation failure fails the build.
- **Automatic supply**: matched by the task text at the start; when entering an App (having read its interface) or a website (opened or read successfully the first time), its knowledge body is added. Each document is given only once, at most 3 per task (`KnowledgeStore`, `NoticePolicy`).
- **Skills are given in two layers** (`GuideRecommender`, `ContextBuilder.start`): the opening index lists all skills, not selected by task text—built-in skills first and personal skills after, each sorted by name, one line each (id, display name, description; a trial description is prefixed to say it has not been verified), with disabled ones and pending drafts not listed. The index is written once in the opening context, and switching to the foreground midway does not add to or change it; it is given whole and not trimmed by the budget. Whether to use one and which one is decided by the model from the descriptions, and to use one it reads the full text with `skill_read`; no skill's full text is stuffed in at the start. Reading a personal skill records a `SkillUsed` (`how` = viewed; the old record's injected is still read and counts as used the same way), and the task outcome is recorded only into the skill that was actually followed this time (`SkillFollow`): after reading it, actions were successfully taken, and if the skill's header names an App / website (the knowledge name, with aliases replaced by registered package names and domains, and App and website knowledge that register each other counted together; unrecognizable ones that do not look like package names or domains count as not written, `GuideCatalog.skillPlaces`) it also must have entered one of them after reading (a screen-read record, or the `currentApp` / `currentSite` reported in a call result); merely reading does not record it, and when more than one was followed and the result cannot be attributed, it does not record either (`RunLearning.recordOutcomes`). Whether to draft also looks only at what was followed: something only read, not followed, but accomplished by itself this time is still drafted.
- **Lookup tools** (`core/general/LookupTools.kt`): `knowledge_search` / `knowledge_read` look up App and website knowledge, and `skill_search` / `skill_read` look up skills (built-in and personal together).
- **Writing a skill at the user's request** (`core/general/SkillSave.kt`, built-in skill `skills/skill-authoring`): when the user asks in a task to create, import or rewrite a skill, the model writes the whole document following the built-in 「写技能」 (Write a skill) skill and saves it as a personal skill with `skill_save`. Quotations must come from what the user said this time (text on pages and in files cannot make it write); it goes through the same validation as self-learned drafts (`SkillDrafter.validate`: name, description, five sections, length, tool names, sensitive content); a built-in skill's name cannot be taken, and one with the same name as a pending draft is not accepted; changing an existing one requires the version returned by `skill_read` (the first 12 characters of the original text fingerprint; a mismatch means it was changed midway). Once saved it goes straight into trial and is marked 「按你的要求写下」 (Written at your request) in 「记忆与技能」 (Memory and skills) (`source: user` in `meta.json`), and moves to formal after one success; renaming and deleting stay in Settings. A run that saved a skill this time does not start another self-learned draft (`Eligibility`). What the user said this time (`UserUtterances`) no longer follows the memory switch: it is kept only in memory and cleared at the start of each task, and when memory is off the memory_* tools are still not provided and it is not used to extract memory.
- **Sharing and importing skills** (`core/learn/skills/SkillImport.kt`, `app/skills/ui/SkillsSection.kt`): in 「记忆与技能」, tapping a personal skill offers 「分享技能」 (Share skill), which sends the full text through the system share sheet (`SkillImport.shareable` removes the lines that only make sense on this device: `source`, `learned_from`, `updates`). Full text shared by someone else is pasted in from the skill section's 「导入技能」 (Import skill), without going through the model: `SkillImport.prepare` writes the origin as `source: imported`, passes the same validation as self-learned drafts, cannot take a built-in skill's name, and is not accepted when a draft with the same name is pending confirmation; if a personal skill with the same name already exists it becomes that skill's update draft (with the original text fingerprint, and which lines changed can be seen before accepting). Imported ones always first go into 「待确认」 (Pending confirmation) marked 「导入的」 (Imported), and start from trial after being accepted. When accepting, an imported draft that has not been changed is validated once more (`MemoryViewModel.approveSkill`; a self-learned draft was already checked against that run's tools when drafted, so an unchanged one is not checked again).
- **Skill marketplace (fork test)**: Settings → Memory and data → Skills → Get skills. Only when the marketplace is opened does it read the `index.json` of the main branch from the selected public GitHub repository; only when an item is tapped does it download `skills/<name>/SKILL.md`. The test version presets `1122414/mika-market-test`, which can be changed in 「技能来源」 (Skill source). The index has `version: 1`, and each item provides `name/display/description/sha256`; the name, description and content digest must match. The preview shows only text and does not run scripts; adding it to pending confirmation uses the original text previewed this time and reuses the manual import validation.
- **Personal skill self-learning** (`core/learn/skills/`, `app/task/RunLearning.kt`): after a task succeeds (`LearnGate`, which does not require having run final verification), it drafts a personal skill under conditions (enough actions, no skipped takeover, the user did not finish it personally, no declined confirmation, not replayed, see `Eligibility`); when drafting it lists the existing personal skills (together with pending drafts) line by line for the model, and which of them this time's matter is the same kind of thing as is written by the model in the header as `updates: <name>`, with code only checking that it really exists: pointing at an accepted one drafts it as that skill's update (overwriting it when accepted, checked with the original text fingerprint), pointing at a pending draft replaces that draft, and an unmatched name is treated as a new one (a new one cannot take an existing name); the draft goes into trial only after the user accepts it in 「记忆与技能」, moves to formal when it succeeds during trial, and is disabled on failure; a formal skill is also disabled if it does badly 2 times out of the last 3 (`SkillOutcomes`, with outcomes not judged as done not counted). The switch 「从办成的任务里学技能」 (Learn skills from completed tasks) is on by default (the old setting is upgraded once when read in `MemorySettings`, and after the user turns it off it stays off).
- **Teaching Claire** (`core/learn/teach/`, `app/teach/`, [`teach-mika.md`](teach-mika.md)): can be entered from the conversation's 「＋」 and the idle capsule. Only after confirming a goal in one sentence and tapping 「开始示范」 (Start demonstration) does it record taps, long presses, input, scrolling and window switches from accessibility events; consecutive scrolls and inputs are merged. While collecting and while paused there is an accessibility overlay above the screen (`TeachChip`, the same kind of window as the floating capsule, without requesting notification or overlay permission), saying that it is learning or paused, and able to pause or end; if it cannot be added it does not start, and if it disappears midway or accessibility disconnects it stops and records no more. Notifications are only an additional hint. This is separate from `RunLearning` / `LearnGate` / experience routes, does not record Claire's own interface, and does not save whole screens, full text, passwords, verification codes or payment content. At the end the user can correct or delete steps, and it only asks about steps with insufficient information. The draft has `source: demonstrated` and goes into pending confirmation through `TeachPublish.toPending`, not through `skill_save`. Before being accepted it does not enter the skill directory; after being accepted it is still a trial, and when read it requires stopping the application if the interface does not match, and states that it has not yet been run successfully. Giving up, declining, deleting, or deleting after accepting removes the local trace. While collecting or paused it does not start new tasks; after a process restart it does not resume collecting by itself.
- **App knowledge self-learning** (`core/learn/knowledge/AppKnowledgeLearning.kt`, `app/knowledge/AppKnowledgeFiles.kt`): under the same switch, for runs started from the conversation UI that took actions in phone Apps, it judges once per App that had actions and has a built-in knowledge entry (an App without an entry has nowhere to attach the supplement, so it is not learned). There are three kinds worth learning (`AppKnowledgeDrafter.kind`): it succeeded and this App had enough effective actions; it succeeded but with stumbling (two or more actions that errored or caused no screen change, or two or more backs); or it did not succeed or only partly succeeded (judged Partial / NotPossible, or gave up, or ran out of steps) and took at least 3 steps in this App. Cancelled ones, ones that skipped takeover, ones the user finished personally and replayed ones are not learned. It asks the model once (preferring a lightweight model; role `prompts/roles/app_knowledge.md`, with the request format in `app_knowledge_input.md`; an already-verified supplement is not asked when the last run succeeded smoothly), giving it the App's built-in description, the supplement in use, the outcome and a condensed action list (with error codes and whether the screen changed, without screen text or typed characters), and asks for the full text after the supplement is revised: only fact lines starting with "- ", at most 12; if there is nothing worth adding, answer NONE and output nothing. The goal, the answer or the reason for not succeeding is given as-is in the request; the returned supplement is accepted as-is (the data is only on the phone, with no redaction), and only a whole one that writes things like passwords or verification codes is not accepted (`SensitiveFilter`). Each App has at most one pending revision, and it is not accepted if the one it revises against is not the one currently injected (another one was accepted first); after the one in use changes (accepted, archived, trial changed phase), a pending revision drafted against the other one is archived on the spot, and accepting a stale revision only archives it, without keeping it around to block this App's future drafts; after being accepted it goes into trial, and during trial it replaces the one it revises (the old one is neither injected nor deleted), and only when it goes formal is the old one archived, and if archived it switches back to the old one (`AppKnowledgeTrial.inUse`). When injected it is attached after the App's description, and a trial one is marked as not yet used by a successful task (the `knowledge.learned_trial` in `feedback/loop.md`; a verified one is `knowledge.learned`). A run that uses a trial draft and succeeds moves it to formal; one learned from a lesson is archived only after two consecutive bad results, while others are archived after one bad result (`AppKnowledgeTrial`); like personal skills, runs stopped by a model error, a runtime-environment problem or an operation guard do not count as good or bad (`SkillOutcomes.resultOf`). 「待确认」 states whether it is a supplement or a revision, and lists the lines added and removed; the one temporarily replaced by a trial revision is marked 「暂时由试用中的修订顶替」 (Temporarily replaced by a trial revision), and is not offered for archiving.

## 12. Memory and models

- **Thinking effort**: models whose provider states the tiers in the model list (`supported_reasoning_levels` / `capabilities.reasoning.effort` / DeepSeek's `effort.supported_levels`) can select it (when the OpenAI-compatible protocol's list does not write `none` but the preset's official documentation does, `none` is added so thinking cannot be left on), and each of the four protocols has its own way of sending it: `ResponsesModel` sends `reasoning: {effort: ...}`; `OpenAiCompatModel` sends `reasoning_effort`; `AnthropicModel` sends `thinking: {type: adaptive, display: summarized}` and `output_config: {effort: ...}` (when `none` is selected it sends `thinking: {type: disabled}`); `GeminiModel` sends `generationConfig.thinkingConfig` (`thinkingLevel`, using `thinkingBudget: 0` when `none` is selected, and `includeThoughts: true` when on). `ModelCatalog` keeps the tiers and their order, cached with `ListedModel.reasoningEfforts`; missing and an explicitly empty list are distinguished. The Anthropic list fills item by item according to `capabilities.effort.<level>.supported` and `capabilities.thinking.types.<mode>.supported`: when `adaptive` is accepted the tiers are those marked supported (shallow to deep), and `disabled` is also accepted with `none` in front; when `adaptive` is not accepted (only `enabled` thinking by budget) or tiers are not distinguished, it is an empty list; accepted thinking modes are stored separately in `ListedModel.thinkingTypes` and handed to `AnthropicModel` through `ClientSetup.thinkingTypes`, and an unaccepted one is not sent. The Gemini list has only one `thinking` boolean and gives no tiers. `ReasoningOptions` prefers the list; when nothing is reported only the Responses family (including ChatGPT and xAI sign-in) gets general manual tiers, while compatible interfaces, Messages and generateContent do not guess (each model's accepted tiers and notation differ, and a wrong guess is rejected on every request). Which protocol is actually used is decided in one place, `ProviderStore.adapterFor` (subscription sign-in always uses that provider's interface and does not follow another protocol written in the list), shared by building the model and giving tiers. `ReasoningControl` selects it under the use card, and `RoleChoices.reasoningEfforts` saves it per use in `uses.<role>.reasoningEffort`, so the same model can differ by use; 「用主模型」 (Use the main model) inherits the main model's effort, and switching that use's model clears its old choice. By default it is unspecified, and old configurations do not migrate to a new default; `ProviderStore.modelFor` passes it to the adapter through `ClientSetup`, and it is sent only when explicitly chosen. With thinking on, Claude's output limit is raised to 16K (thinking also counts in `max_tokens`); in turns with tool calls the thinking block's signature is stored together with the address it was received from in `Part.Thinking.opaque` (`SignedThinking`), and only returned to the same address (`redacted_thinking` is returned the same way), and when the address changes or thinking is turned off it is not returned. When the server rejects the chosen tier it reports an error as usual instead of quietly lowering it; when retrying without the unsupported `include` it still keeps the effort. After refreshing the list, a selected tier that is no longer supported is kept with a hint, and the default can be restored.

- **Memory** (`core/learn/memory/`): three kinds `MemoryKind`—facts, preferences, practices. Facts and preferences are used as soon as they are recorded and can be undone, while practices need the user's approval. It records only from what the user says themselves (`UserUtterances`, which when carrying the screen, the browser page's page notes, a quoted reply from Claire or attachment lines takes only what the user typed, and also takes his own quoted words, `UserWords.said`), not from screens and web content; passwords, verification codes, card numbers, ID numbers and the like are blocked by `SensitiveFilter`. A write not accepted under these rules is an answer to that item, and the result marks `counts_as_failure=false`, not counting toward consecutive operation failures. After the switch 「让 Claire 自己归纳着记」 (Let Claire summarize and remember on its own) (off by default) is turned on, when the user personally asks it to remember this turn (recognizing only Chinese and English phrasings) and the quote is that half of the sentence asking it to remember, content carrying specific values the user did not say is also accepted, with the source recorded as `inferred`: the opening injection, `memory_search` results and the memory page all state that it was not said by the user, and when handed to verification it counts as a fact the tool found, not a fact given by the user. Tools `memory_save`, `memory_search`, `memory_edit`; a saved quotation only recognizes this turn's user words, with the sole exception of content already discussed when the previous turn's user explicitly confirmed the immediately preceding assistant suggestion or question and this turn asks to save it; updates and deletions are not relaxed to the previous turn, and must use an explicit request this turn and a stable id from `memory_search`'s most recent result; with multiple candidates this turn's quotation must also contain that exact id, and when it was not searched, the id is not among the candidates, the id is duplicated or the target is unclear, it does not change it; changes go into the existing result card and can be undone. After the task ends `MemoryExtractor` extracts from the user's own words in the background (runs that read web pages do not extract; it also requires that this run was started from the conversation UI and handed over an answer, `RunLearning`). Memory is injected at the start (`MemoryContext`): when the total is within `FULL_MAX_TOKENS` every item is given without omission (pinned first, the rest in reverse update order), and only when it exceeds that does it fall back to carrying only pinned and retrieved relevant items (`MemoryIndex`'s BM25); in full mode practices are all given too, while in retrieval mode at most `MAX_PROCEDURES` practices are carried by relevance; the product path (`AgentLoop`) uses automatic mode, and `Mode.Relevant` keeps the old behavior. There is also a separate user profile (`ProfileStore`, tool `profile_edit`, with changes taking effect from the next task). Memory and profile are stored encrypted with a key from the Android Keystore (`app/memory/EncryptedMemoryFile.kt`). The switches 「使用记忆」 (Use memory) and 「自动记住我说过的事」 (Automatically remember things I say) are on by default, and 「让 Claire 自己归纳着记」 is off by default.
- **Models**: four interfaces—OpenAI-compatible (Chat Completions), OpenAI Responses, Anthropic, Gemini (`core/model/`); ChatGPT account sign-in with plan quota is also available (see "Responses and signing in with ChatGPT" below). Models are divided into three uses `ModelRole`: main model, vision model, lightweight model. Speech-to-text is a fourth use, but not in `ModelRole`, and is stored separately in the unified speech catalog (see "16. Voice input"). What each use selects is explicitly stated by the user (`RoleChoices`, in `app/settings/ProviderStore.kt`), with no default assignment inferred from capabilities: the main model is a specific model or not yet chosen; vision is a specific model, 「用主模型」 (Use the main model) or 「不用」 (Do not use) (not used by default on a new install); lightweight is a specific model or 「用主模型」 (the default on a new install). The choice is not blocked by capability flags (`ProviderStore.choose` does not refuse), and choosing a specific model records the corresponding flag: choosing as the main model records tool calling, and choosing as the vision model records vision, and at runtime these two flags decide whether to send tool definitions and whether to attach images; when vision is 「用主模型」 `configFor` gives the main model's configuration and takes the vision flag as true (the user said it can see images), while the main model doing tasks still follows the flag it stored. Capability labels are for reference only. Outcome judgement, memory extraction, intent judgement and route matching prefer the lightweight model; after turning on the speed switch 「简单步骤交给轻量模型」 (Give simple steps to the lightweight model) simple steps are handed to it too (`core/agent/ModelRouter.kt`, and when the lightweight model does not support tool calling it is not given phone steps). 「看图定位已验证」 (Visual locating verified) (`Capabilities.groundingVerified`) is changed in Settings › Developer options, and applies to the current vision model's configuration (`ProviderStore.setVisionGroundingVerified`), and is not shown when there is no vision model. API keys are stored encrypted with the Keystore (`app/settings/KeyCipher.kt`).
- **Provider presets** (`app/settings/ProviderPresets.kt`): prefill the interface type, address and initial capabilities, while the model name and Key are filled in by the user. In China: DeepSeek, Qwen, Kimi, Zhipu, SiliconFlow, Volcano Ark (Doubao, where the model name can be a model ID or an endpoint `ep-…`), MiniMax (China site `api.minimax.cn`), StepFun, Tencent Hunyuan (TokenHub `tokenhub.tencentmaas.com`), Baidu Qianfan (`qianfan.baidubce.com/v2`); abroad: OpenRouter, OrcaRouter, OpenCode Go, Anthropic, Gemini, OpenAI, xAI, Mistral, Groq, Cloudflare Workers AI; running on your own machine: Ollama, LM Studio; and finally 「自定义」 (Custom). 「OpenAI」's interface type is Responses (`ProviderConfig.Kind.OpenAiResponses`): the official docs state that new mainline models must use Responses to call tools, and Chat Completions with tools is rejected; listing models is likewise `GET /models`. The rest are all OpenAI-compatible. Cloudflare Workers AI's address contains an `{account_id}` placeholder (`https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/v1`), and `ProviderPreset.urlEditable` is true to allow the user to put the account ID into the address, with a prompt to change it when not replaced. When adding a 「自定义」 provider the interface type can be OpenAI-compatible, Anthropic, Gemini or OpenAI Responses (`ProviderConfig.Kind.withApiKey`, with Responses last), and ones choosing Responses call `{base}/responses` through `ResponsesModel`, while listing models is still `GET {base}/models`; custom Responses, like Anthropic and Gemini, must have a Key filled in (among custom providers only OpenAI-compatible can leave it empty, mostly local services, see `AddForm.keyRequired`). For `ProviderPreset.selfHosted` (Ollama, LM Studio) the address is prefilled with the local default port (`http://127.0.0.1:11434/v1`, `http://127.0.0.1:1234/v1`), can be changed in the form to the computer's LAN address (`AddForm.urlEditable`, with a line below hinting how to change it), and the Key can be left empty (`AddForm.keyRequired`), with the saved provider name still using the preset name. The preset list in the README is generated from this file by `./gradlew updateReadme` (see `ReadmeSections`).
- **Listing models and connecting providers**: `ModelCatalog` (`core/model/ModelCatalog.kt`) calls each provider's public model-listing interface (OpenAI-compatible `GET /models`, Anthropic `GET /v1/models`, Gemini `GET /v1beta/models`, the latter two paginated), returning model names and the capabilities the interface gives (tool calling, vision, context length, reasoning); what the interface does not give is empty, and `ModelOptions` (`app/settings/ModelOptions.kt`) uses the preset's initial values and marks them unconfirmed. Failures are classified by reason (invalid Key, network, listing not offered, etc.). A listing interface returning 404 / 405 / 501 is recorded as 「不提供列表」 (Does not offer a list), but that alone cannot tell whether the provider really does not offer a list or the address or interface type was filled in wrong; the test call below distinguishes them.
- **One provider, several protocols**: for some providers (such as subscription-based aggregators), models under one Key use different protocols, and each model in the list carries an `api` table whose keys are protocols (`chat-completions`, `messages`, `generate-content`, `responses`, …) and whose values hold that protocol's `base_url` (the compatible interface can also write `compatibility.reasoning_field`). `ModelCatalog` takes the first one it can speak in the order Chat Completions, Messages, generateContent, Responses, and records it as `ListedModel.endpoint` (`ModelEndpoint`: protocol, address, reasoning field); one that can speak none (such as `realtime`) has its protocol name recorded (`unsupportedApis`), `ListedModel.usable` is false, `ModelOptions.merge` does not list it and the provider's model count does not include it, so the user cannot select a model that is bound to fail. Capabilities in the same notation are recognized too: `capabilities.tools.supported`, `capabilities.reasoning.supported`, `limit.context`, `modalities.input` (`image/…` means it can see images). `endpoint` is stored along with the model list in `providers.json`'s `services[].models[].api` (`unsupportedApis` in the same place). When building a model, `ProviderStore.modelFor` looks up this model's `endpoint` in the provider's remembered list on the spot, and if present selects the adapter by protocol (`ProviderConfig.Kind.of`: Chat Completions → `OpenAiCompatModel`, Messages → `AnthropicModel`, generateContent → `GeminiModel`, Responses → `ResponsesModel`) and uses its address, otherwise it follows the provider's interface type and address as before; after relisting, if the address changed, the next model build uses the new one. The adapter appends the version path itself (Anthropic appends `/v1/messages`, Gemini appends `/v1beta/models/…`), and an existing `/v1`, `/v1beta` at the end of the list address is removed by `ModelEndpoint.adapterBaseUrl` so it is not duplicated. All use the provider's single Key. The compatible interface's thinking return (`OpenAiCompatModel`, not judged by provider name, address or model name): providers put thinking in `reasoning_content`, `reasoning`, or with `content` as a block array and thinking in `thinking` blocks (text blocks are the answer); received thinking records the address and position it was received from (`ReasoningVia`, stored in `Part.Thinking.opaque`), and in requests with tools it is put back in the same place as-is (same field name; the block-array provider is put back as a whole block array, with thinking blocks first). It only returns thinking received from the same address; thinking from another address or another adapter is not sent, and providers that do not recognize these fields will not receive it; bypass calls without tools do not return it. When the list states `reasoning_field` (`reasoning_content` or `reasoning`), thinking of unknown provenance (history stored by older versions) is also returned according to it. The preset 「OpenCode Go」 is like this: the list address is `https://opencode.ai/zen/go/v1` (the list needs no Key), and the OpenAI-compatible interface type is only the fallback when no protocol is written; models that only write `responses` (address such as `https://opencode.ai/inference/go/openai/v1`) are called by `ResponsesModel`.
- **Responses and signing in with ChatGPT**: `ResponsesModel` (`core/model/ResponsesModel.kt`) calls `POST {base}/responses`, always `stream:true` and `store:false`, putting the whole context into the `input` array each time: the system prompt goes in `instructions`, system messages in the conversation become developer messages, images are `input_image` (replaced with a placeholder sentence when the model cannot see images), tools are function tools (`strict:false`), and tool calls and results are `function_call` / `function_call_output` entries. By default it sends only `model`, `instructions`, `input`, `tools`, `store`, `stream` and `include`; when the user selects thinking effort it also sends `reasoning.effort`, and temperature and output limit are not sent (and are not accepted when using ChatGPT plan quota). For reasoning models it requests encrypted thinking content (`include: reasoning.encrypted_content`), stores it as-is into this turn's first tool call's `Part.ToolCall.opaque`, and puts it back before the tool call on replay (removing the `id` that only matters on the server); when the server says it does not accept `include` it removes it and sends again. It succeeds only on receiving `response.completed` (or `response.incomplete`: `max_output_tokens` is recorded as output truncated), `response.failed` / `error` is classified into `ModelError` by `error.code`, and a stream that disconnects before finishing is treated as a network failure (and is retried). The token is given by `BearerToken`: an API Key is fixed; one that can be renewed (ChatGPT) renews once and resends on HTTP 401. Usage is recorded from `response.usage` (`input_tokens`, `output_tokens`, `input_tokens_details.cached_tokens`) into token usage.
  「用 ChatGPT 登录」 (Sign in with ChatGPT) (`core/model/chatgpt/`, interface type `ProviderConfig.Kind.ChatGpt`) follows the path OpenAI offers to open-source Apps running locally: a public client, no secret, authorization code + PKCE (S256), with a new state, nonce and verifier generated on every sign-in. `LoopbackCallback` (`core/model/oauth/`, shared with OpenRouter) opens a system-chosen free port on `127.0.0.1` and accepts `GET /auth/callback` only once (other paths return 404, and a state mismatch returns 400 and keeps waiting); when the callback arrives it first finishes the sign-in—checking the callback, exchanging the token, verifying the ID token and checking plan permission, at most 20 seconds—then returns the result to the browser (which has been waiting on this connection all along): on success it writes 「登录成功，回到 Claire」 (Signed in; return to Claire), on failure it writes the same reason as the UI, and the page's button is an intent link that opens Claire; on timeout or cancellation it closes. The authorization page `https://auth.openai.com/api/accounts/authorize` is opened in the system browser: the first time it registers with `client_id=dynamic_agent_client`, carrying `agent_name_hint=Claire` and a local identifier `ext_agent_host_id` (`urn:uuid:…`, generated once per device); the callback gives this account's dedicated client_id, which is recorded before exchanging the token (`settings/chatgpt-host.json`, stored together with the local identifier, neither being a secret), and is used afterwards for token exchange, refresh and signing in again (signing in again carries the previous ID token and email as hints, and after signing out carries no ID token). `scope` is `openid profile email offline_access resource.invoke chatgpt.tokens.use.direct`, and `resource` is `https://api.openai.com/v1`. After exchanging the token (`/api/accounts/oauth/token`, form) it verifies the ID token: verifying the RS256 signature against `/.well-known/jwks.json`, checking the issuer, audience (= client_id), expiry and nonce; if the granted scopes do not include `chatgpt.tokens.use.direct` it does not count as a successful sign-in (`signInWithChatGpt` chains these together). Rejection reasons are classified by `ChatGptAuth.failureOf`, the UI and callback page say the same plain-language sentence, and the diagnostic info records the error code: a non-JSON 403 / 429 is being blocked by protection (`SignInFailure.Blocked`, change network or try later), a code or description containing `unsupported_country` / `region` / `territory` is a region not supported (`SignInFailure.Region`), `invalid_grant` means the sign-in code expired or was used (`SignInFailure.CodeExpired`), `access_denied` and the like mean the user did not agree (`SignInFailure.Denied`), a code or description mentioning plan, permission (`invalid_scope`, `plan`, `subscription`, `scope`) or the granted scopes lacking the plan item mentions Plus, Pro (`SignInFailure.NoPlanScope`), and the rest are 「ChatGPT 拒绝了这次登录(错误:代码)」 (ChatGPT rejected this sign-in (error: code)) (`SignInFailure.Exchange`); the `error` returned by the authorization page is classified the same way, with ones that cannot tell region or plan all counted as `SignInFailure.Denied`. During sign-in Claire is in the background while the user enters the password and two-step verification in the browser, and Android may freeze or reclaim the background process, leaving the local port open with nobody accepting, so the browser waits until timeout and the authorization code may expire: therefore sign-in does not run in the UI's scope but in the App's single `ChatGptSignIns` (`app/settings/ChatGptSignIns.kt`, uninterrupted by UI recreation or going to the background, with only one at a time), and at start it starts the foreground service `ChatGptSignInService` (`specialUse`, on the quiet 「任务进度」 (Task progress) channel: 「正在等你在浏览器里登录 ChatGPT」 (Waiting for you to sign in to ChatGPT in the browser), with 「取消」 (Cancel)), and if it cannot start it only records a line and sign-in proceeds as usual; the service watches `ChatGptSignIns.running` and stops itself as soon as sign-in ends (success, failure, cancellation, timeout). The most recent sign-in failure (time, category, error code, a short redacted description) is kept only in memory and written into 「复制诊断信息」 (Copy diagnostics). The whole sign-in (`ChatGptSession`: client_id, identity, token, expiry, granted scopes) is treated as this provider's "Key" and stored encrypted via the same `KeyCipher` in `provider-keys.json`. The access token expires in an hour: `ChatGptTokens` exchanges the refresh token for a new set when it is about to expire (less than 5 minutes) or is rejected, storing the new refresh token together with the access token, with only one exchange at a time; if the refresh token can no longer be used (`invalid_grant` etc.) it clears the tokens and reports 「登录已失效」 (Sign-in has expired), while on a temporary network or server error the tokens are kept. Signing out first revokes the refresh token on the server (`/api/accounts/oauth/revoke`), and if it cannot be confirmed it still clears the local tokens and explains; the provider, models and uses are all kept for use after signing in again. Deleting the ChatGPT provider forgets the client_id (registering anew next time, which allows switching accounts), while the local identifier is kept. The model list is `GET https://api.openai.com/v1/models` (with the access token), and of the returned `models` table it keeps only those whose `visibility` is `list`, in server order, taking the name from `slug` and the display name from `display_name`, and filling in capabilities from `input_modalities`, `context_window` and `supported_reasoning_levels` when given; all are called through `ResponsesModel` (`chatGptPlan`). Plan-quota errors: `subscription_sharing_usage_limit_exceeded` (or HTTP 429) is the quota reaching its limit (`ModelError.ChatGptLimitReached`), `subscription_sharing_user_not_eligible` (or HTTP 403) is the account not being allowed to use it this way (`ChatGptNotEligible`), neither is retried, and the task outcome states the reason and where to see usage (chatgpt.com/settings/usage); `subscription_sharing_usage_unavailable` and other temporary unavailability are retried as 503 later. UI: in the 「用账号登录」 (Sign in with an account) group at the top of Add provider, the ChatGPT row, and when opened, the panel has 「用你的 ChatGPT 套餐」 (Use your ChatGPT plan) and 「使用 ChatGPT 继续」 (Continue with ChatGPT) buttons (stating Plus and Pro are usable and Claire charges nothing extra), and after the first successful sign-in it explains once that usage goes through the ChatGPT plan; the provider details show the account (email), manage usage (opens chatgpt.com/settings/usage), sign out or sign in again, with no interface type, address or Key.
- **Signing in with an account (xAI, OpenRouter)** (`core/model/oauth/`): alongside ChatGPT, in the 「用账号登录 · 不用填 Key」 (Sign in with an account · no Key needed) group at the top of 「添加服务商」 (Add provider) (`settings/ui/models/AccountSignIn.kt`: three rows, ChatGPT, xAI / Grok, OpenRouter; signed-in ones say 「已登录」 (Signed in) and open details, unsigned ones open an explanation panel, and only tapping 「继续登录」 (Continue signing in) starts; xAI has a risk notice and 「改用 API Key」 (Use an API Key instead)). Sign-ins all run in `ChatGptSignIns` (`SignInTarget` recognizes which provider, and the foreground notification uses those two account-sign-in lines), and after success it lists models, saves them, selects one if there is no main model yet, and opens this provider's details (`ModelSetupUi.signedInProvider`); the details (`ModelsScreen.kt`) are the account, status, set as main model, open the provider's account page, sign out or sign in again, with signing out clearing only the local side. Failure categories and error codes are recorded in the diagnostic info. The local callback `LoopbackCallback` and `Pkce` are in `core/model/oauth/`, shared by ChatGPT and OpenRouter; `SignInBrowser` opens the browser, returns to Claire, and gives the result page after the callback.
  **xAI** (interface type `ProviderConfig.Kind.Xai`): sign-in, encrypted storage, refresh and calling xAI's own interface are four separate steps. It uses the device code flow (RFC 8628, `DeviceCodeClient`, `awaitDeviceGrant`): the user opens the verification page in the browser and checks the short code, and the App polls at the interval the server gives to exchange the token (adding 5 seconds on `slow_down`, and only 3 consecutive failures count as failure); the panel shows the same short code, its validity period and 「复制码并重新打开确认页」 (Copy the code and reopen the confirmation page); if the verification page's host is not in the allowlist it opens the fixed official page instead. Access tokens, refresh tokens and device codes do not go into logs. The whole sign-in (`AccountSession`) is stored encrypted the same way as an API Key in `provider-keys.json`; `AccountTokens` exchanges the refresh token for a new one when about to expire or rejected, and if the refresh token can no longer be used it clears it and reports 「xAI 登录已失效」 (xAI sign-in has expired) (`ModelError.SignInExpired.account`). `XaiAuth` first reads `https://auth.x.ai/.well-known/openid-configuration`, and the issuer and the device-code and token addresses must be https `auth.x.ai` (`OauthUrls`), otherwise it stops. The client reuses the public sign-in entry of xAI's official command-line tool (not registered for Claire), with scopes including `grok-cli:access` and `api:access`; the panel states the reuse risk before signing in. Calls are Responses at `https://api.x.ai/v1` (`ResponsesModel`, `accountLogin`), and HTTP 403 means the subscription tier cannot use this interface (`ModelError.AccountPlanNotAllowed`, not retried, explaining to switch to an xAI API Key).
  **OpenRouter** (`OpenRouterAuth`, `signInWithOpenRouter`): official OAuth PKCE. The authorization page `https://openrouter.ai/auth` carries the local callback (`http://localhost:<port>/auth/callback`, with the listener bound only to 127.0.0.1), S256 verification, `key_label=Claire` and state; a state mismatch returns 400 and keeps waiting, and no code and no state means the user declined; `POST /api/v1/auth/keys` (JSON: code, code_verifier, code_challenge_method) exchanges for an OpenRouter Key. It is stored as an OpenAI-compatible provider according to the OpenRouter preset, with the Key encrypted as usual, and `Provider.signIn` records `openrouter` (stored in `providers.json`'s `services[].signIn`); an authorized one and one with a user-filled Key are separate providers (`findOrAddProvider` separates by origin), authorization does not override the user's Key, and the UI writes it as 「OpenRouter（账号登录）」 (OpenRouter (account sign-in)). Signing out deletes the local Key (`ProviderStore.signOutOpenRouter`), with a hint to delete it on OpenRouter's Keys page. For details see `docs/dev/account-signin.md` (which also explains why Claude subscription, Google account and MiniMax account are not done).
- **Request headers and session id** (`core/model/ClientHeaders.kt`): every request sent to a model service (all four protocol adapters—Chat Completions, Messages, generateContent, Responses, both one-shot and streaming—and `ModelCatalog`'s model listing) carries the headers `ClientHeaders.of` gives, while the Key (or ChatGPT's access token) header is still added by the adapter itself; 「用 ChatGPT 登录」 also carries `User-Agent`, but it does not declare a session header, so no session id is sent. `User-Agent` is `Claire/<version>` (the App passes `BuildConfig.VERSION_NAME` to `ProviderStore`, and core does not write the version number). Some providers require each conversation to carry a fixed session id (used for routing and reusing prompt cache, and rejected without it): the preset declares the header name with `ProviderPreset.sessionHeader` (currently only 「OpenCode Go」's `x-opencode-session`), recorded on the provider when connected (`Provider.sessionHeader`, stored in `providers.json`'s `services[].sessionHeader`; ones stored by older versions lack this item, and it is filled in on read from the preset whose address matches). Providers without a declaration are not sent a session id, and the code does not judge by provider name. The session id is `ModelSession.of(conversation id)` (UUID v3, irreversible, not sending the conversation id itself): the three model factories of `TaskEnvironment` take one more `ModelSession` parameter, `TaskRun` builds the main, lightweight and vision models by its own conversation, verification, intent judgement, outcome judgement and the explanation after stopping all use these, and `TaskService` when starting a conversation title also takes it by the same conversation id; within one conversation every run and every bypass call has the same session id, and a different conversation differs. Requests that do not belong to any conversation (model listing, connection test) use a new id from `ModelSession.fresh()` each time.
- **Cleartext http** (`res/xml/network_security_config.xml`, referenced by `networkSecurityConfig` in the manifest): model services the user runs on this machine or the LAN mostly have only http, so the whole App allows cleartext (`base-config cleartextTrafficPermitted="true"`), and certificates trust only the system's. Nowhere else in the code rejects http: `ModelCatalog` and the adapters only require a valid http(s) address, and the add form only requires starting with `http://` or `https://`. When adding a provider, an address that is cleartext http and not on this machine or the LAN (`LocalHosts.isLocal`: localhost, 127/8, ::1, 10/8, 172.16/12, 192.168/16, 169.254/16, fc00::/7, fe80::/10, `.local`) gets a hint below the form (`AddForm.unencryptedWarning`), without blocking. The built-in browser can therefore also open http pages directly: previously the system first refused (`ERR_CLEARTEXT_NOT_PERMITTED`) and `WebScreen` reopened with https, but now it opens the original address, and that https-retry is only needed when the device policy or WebView still refuses cleartext; cleartext subresources in https pages are still refused under `MIXED_CONTENT_NEVER_ALLOW`.
- **Network proxy** (`core/net/NetProxy.kt`, `ProxyAddress.kt`, `LocalHosts.kt`; setting in `app/settings/NetProxyStore.kt`): Settings › Advanced and other settings › the 「网络代理」 (Network proxy) in the 「网络与连接」 (Network and connections) group (`settings/ui/NetProxySettings.kt`, changed only here), filled as `http://[user:password@]host:port`, also accepting socks5, socks5h, https (`ProxyAddress.parse` checks it, and a mistyped one is not saved), and empty means direct. The address may carry a username and password, and like a provider's Key it is stored encrypted via `KeyCipher` (Android Keystore) as `settings/net-proxy.bin`, not entering plaintext preferences and not written to logs, with the UI showing only protocol, host and port (`ProxyAddress.toString` also carries no username or password). Earlier it was only for the container and stored in `container-proxy.bin` (another key): on first read `NetProxyStore` decrypts it, saves it under the new one, and deletes the old file.
  - Who goes through it: OkHttp clients built by `NetProxy.shared.client(…)`—`ProviderStore`'s model clients (the four adapters one-shot and streaming, speech transcription, connection tests) and the clients for model listing and account sign-in token exchange, `UpdateChecker`, and the built-in browser's downloads (`WebStack`); sandbox commands go through environment variables (see §6 sandbox). What does not go through it: the remote relay (`RelayGateway`) and run-record export (`OtlpSender`).
  - How it goes through: the client is installed with `NetProxy.selector` (`ProxySelector`), which decides per request: `LocalHosts.bypassesProxy` (the `isLocal` ranges, plus dotless machine names, `.lan`/`.home.arpa`/`.internal`, 100.64/10) goes direct, and the rest go through the HTTP or SOCKS proxy; with SOCKS the domain is resolved by the proxy (socks5 and socks5h alike). An `https://` proxy (TLS handshake with the proxy first) is not supported by OkHttp, so `ProxyAddress.forApp` is false, Claire's own connections go direct, and the settings page states it is only for the container. Streaming replies are still read segment by segment, and the proxy does not change the reading. When the setting changes, `NetProxyStore` calls `NetProxy.changed()`: re-parsing and clearing each client's idle connections (in-flight requests still finish as usual).
  - Username and password: for HTTP proxies `NetProxy.authenticator` (OkHttp's `proxyAuthenticator`) adds `Proxy-Authorization: Basic` when the proxy returns 407 and before building the https tunnel; if it is still rejected after being sent once on the same request it is not retried. SOCKS proxies can only be given via the one-per-process `java.net.Authenticator`: `MikaApp` installs `NetProxy.socksAuthenticator` at startup, which answers only inquiries whose protocol is SOCKS and whose host and port match the current proxy, and answers nothing else.
  - Errors: when `HttpSupport` fails to connect, a request that went through the proxy is classified by `NetProxy.classify` as `ModelError.Proxy` (`ProxyFailure.Unreachable`: connection refused, proxy host not found, connect timeout, tunnel build failed, SOCKS handshake error; `ProxyFailure.AuthFailed`: the proxy rejected the username and password), with HTTP 407 also counting as the latter; a disconnect while reading the reply is still `Network`. `userReason`, the test call (`ModelSetupViewModel.proxyReason`) and model listing (`ListFailure.ProxyUnreachable` / `ListFailure.ProxyAuth`) all say it is a proxy problem, not that the Key or model is wrong; a failed connection can be retried, and a wrong username and password is not retried and does not disable the model.
  - Update downloads: the system download service (`DownloadManager`) does not go through the App's proxy, so when a proxy is set `ApkUpdater` instead downloads in-process through the proxy via `ProxiedApkDownload` (writing `.part` first, renaming when complete; a killed process counts as failure, and retrying is fine), and when installing it gives the system installer a read-only address through `UpdateFilesProvider`; verification is as before.
  - Built-in browser (`cap/web/WebProxy.kt`): when the WebView supports `PROXY_OVERRIDE`, it sets the same proxy for all WebViews in this process via androidx.webkit's `ProxyController`, with direct-access rules of `LocalHosts.BYPASS_RULES` plus simple host names; when the HTTP proxy needs a username and password, `WebTab.onReceivedHttpAuthRequest` only answers for the current proxy's host (at most 3 times per main-document load per tab, recounting on the next navigation or refresh). When the WebView does not support it, or the proxy is a SOCKS with a username and password (the kernel does not support SOCKS authentication), the browser goes direct, as stated on that line of the settings page. When no proxy is set, startup does not load a WebView for this.
- **Storage of provider and model configuration** (`app/settings/ProviderStore.kt`): a `Provider` is a connected provider (id, name, interface type, address, and the most recently listed models), and a `ProviderConfig` is a model hanging under it (recording `providerId`, with interface type and address copied from the provider, and the Key taken from the provider when building the model). The model configuration is a layer inside storage that the user does not see: it is created on the spot when a model is selected (`ProviderStore.use`), and deleted when no use uses it anymore (tidied each time uses are changed, a provider is deleted or state is read; the Key is stored per provider, so deleting a configuration does not touch the Key). In `providers.json`, `services` stores providers (including the remembered model list), `providers` stores model configurations, and `uses` stores the three use choices (`{"use":"model","config":<config id>}`, `{"use":"main"}` or `{"use":"none"}`); Keys are stored encrypted via `KeyCipher` in `provider-keys.json`, one per provider. Older versions had only model configurations with Keys stored by configuration id: on read they are grouped into providers by `ProviderConnection.keyOf` (interface type, address, name), the Key is taken from any one in the group, and the configuration-id-keyed ones are cleared. The old `roles` recorded only explicitly specified configuration ids: on read the assignment actually in effect then is written as `uses`—the main model takes the first configuration if unspecified, vision uses 「用主模型」 if the main model can see images and otherwise is not used, and lightweight uses 「用主模型」 if unspecified (all done only once, with migrated ones untouched and repeated execution having no side effect). Deleting a provider deletes its configurations and Key together, and uses that were using it fall back to the default (the main model becomes unselected, vision not used, lightweight use the main model).
- **Model configuration page** (`app/settings/ui/models/ModelSetupScreen.kt`, state in `ModelSetupViewModel`): the onboarding 「配置模型」 (Configure models) and Settings › 「模型」 (Models) (`app/settings/ui/models/ModelsScreen.kt` is just the same page without the guide) share the page and state, and the user only manages two blocks: uses (three cards, each stating what is selected: the model name, 「用主模型」 and who the main model is, 「不用」 or not set) and providers (one row each, stating which uses it works for). In onboarding the providers come first, the add form is spread directly on the page when there is no provider, and the bottom 「下一步」 (Next) can be tapped only after a main model is selected; in Settings the uses come first, there is no bottom button, and changes take effect on the spot. After adding a provider by choosing a preset or custom, filling in the Key, and tapping 「测试并保存」 (Test and save): it first lists models once, and after listing them (or the service not offering a list) it tries one real call—in the order of `ModelOptions.candidates` (this provider's own models first: model names or display names containing the preset's `ProviderPreset.familyTokens`, such as qwen for Qwen; then ones the list says can call tools; within the same family and tier newer versions by model name first (`settings/ModelOptions.kt`'s `ModelVersion`: version numbers like `x-3.1-pro`, `qwen3`, `claude-4-5`, `4o`, with parameter counts ending in b / k and context length not counting; for the same version the release comes before the `latest` alias, which comes before `preview` / `exp` / `beta` etc.; within the same tier ones without a date come first, then newer dates like `-2025-08-07`, `-0827` first; ones whose version cannot be read come after readable ones; it does not judge which of flash, pro, lite is better, and the same version follows list order; other providers' models are not sorted by version—provider lists often put old models first, and old models may be offline); the rest follow list order; ones that clearly do not call tools, and ones that look like embedding / reranking / speech / image generation, are not tried—the list's `type` and output modalities are followed when stated (`ListedModel.chat`), and when not stated the words in the model name are checked; when there is no candidate it tries the first) by giving the model a parameterless tool `get_time` and asking it to call it, with a reply limit of 1024 tokens (enough for one tool call plus the thinking of a model that thinks first; Messages and generateContent are given it; Chat Completions is not, since `max_tokens` and `max_completion_tokens` are accepted differently by each provider and a wrong one rejects the whole request; Responses is not given it either, as the ChatGPT plan path does not accept `max_output_tokens`), following the same model-building path as real tasks (`ProviderStore.probe` uses the same `modelFactory`, carrying headers and session id as usual, with a new session id), waiting at most 20 seconds (signing in with ChatGPT does not go through this form and is not tried: the sign-in itself already verified it); a wrong Key or a missing header the provider requires shows up here, and the server's error is displayed as-is and not saved. `ProviderStore.probe` returns `ProbeResult`: returning a tool call (`ToolCalled`) counts as passing; only returning text (`NoToolCall`) means the interface works but this model does not call tools. When it does not pass and it is that model's own problem (only returned text, or the adapter gives `ModelError.ModelNotAvailable`, meaning the account is not enabled or has no permission, `ModelNotFound`, `ToolsUnsupported`), it tries the next candidate, at most 3 (`ModelSetupViewModel.PROBE_CANDIDATES`): the one that passes is saved as the main model, and the page says below the provider list which ones were tried first and did not pass (`ModelSetupUi.probeNote`); if none pass it still saves the provider (the Key is proven correct), sets no main model, says why the first one did not pass and which were tried, with a 「选主模型」 (Choose main model) below, and records this provider in `ModelSetupUi.pickToProbe`, and when selecting a main model in it, it first tests the call (`ModelSetupUi.probeBeforePick` → `pickManual`), and if it does not pass it says why below that provider and does not select; testing again or selecting a main model collapses it. If the first fails for another reason (Key, network, address, timeout, server error) it is not saved; if a later candidate fails for another reason it stops trying and treats it as none passing. The adapter recognizes "this model does not work" with the same `core/model/ModelAccessErrors.kt`: when the content of an HTTP 400 / 403 / 404 error says tools are not supported ("does not support tools" …), the account cannot use it ("not activated", "not authorized to access this model", "does not have access to the model", "Model.AccessDenied", 「未开通」 (not activated), 「无权限」 (no permission) …, carrying the server's exact words), or the model does not exist ("model_not_found", "model not exist", "not found for API version" in 400 / 403 …, carrying the exact words from the JSON error), it gives `ToolsUnsupported`, `ModelNotAvailable`, `ModelNotFound` respectively, and a model being offline ("no longer available", "has been retired", "model … is deprecated", 「已下线」 (offline) …) also counts as `ModelNotAvailable`, with the exact words; HTTP 429 counts as `ModelNotAvailable` only when it says this account's quota on this model is zero ("limit: 0", "quotaValue": "0", "doesn't have a free quota tier") (waiting is useless and only switching models helps, so the test call tries the next), while other 429s are still rate limiting or quota exhausted; the rest follow each adapter's status-code handling, 401 is always a Key problem, and 404 gives `ModelNotFound`, likewise carrying the exact words from the JSON error (non-JSON ones carry none). When no models are listed (the listing interface does not exist, or the list is empty) it does not save directly: the form asks for a model name (`AddForm.noList`, with the input's example depending on the interface type, `ModelSetupCopy.modelExample`), and testing then uses it for the test call, and on passing saves it as a provider that does not offer a list and uses it as the main model, and on failing does not save. The form always has 「手动填写模型名」 (Enter the model name manually) (`AddForm.manual`, expanded automatically when model listing fails and nothing has been typed manually): when filled in (`AddForm.typedModel`) it tries only this one, and whether the list can list it, cannot list it, or gives another error (wrong Key, 5xx, non-JSON response) it still tries, and the test call's conclusion decides, and on passing saves it together with the listed models; ones not in the list are recorded in `Provider.typedModels` (stored with the provider, not lost on list refresh, still listed by `ModelOptions.ofProvider`, with `ModelOption.typed` marked 「手填」 (Manually entered)); when nothing is typed manually and model listing fails it still states the reason (a wrong Key says the Key is wrong) and does not save; when the test call returns 404 the adapter gives `ModelError.ModelNotFound(model)`, and the form states which model it is and roughly what a model name looks like, and for custom ones also that the address or interface type may be wrong. When a custom address's host name is the same as a preset's (`ProviderPresets.forHost`, except self-hosted services) it hints to switch to that preset, switching with one tap and keeping the Key; when the address is the preset's but the interface type differs it says so as well. The model name that the test call got a reply from is recorded in `Provider.verifiedModels` (stored with the provider; old files lack it, and providers that did not offer a list were then not test-called). Only when all succeed does it save this provider and the list via `ProviderStore.connect` (updating the original one with the same interface type, address and name), with the name being the preset name; a custom one can be named in the form (`AddForm.name`, at most `ModelSetupViewModel.MAX_NAME` characters (counted by code point, so emoji are not cut in half), and when empty it uses `AddForm.defaultName`: the address's host name, or the preset name when the address is a preset's, with the input hint stating this default name), and different names for the same address are saved as two providers (for example two Keys for the same relay), and when it cannot list it states the reason and does not save. When the first provider is connected and there is no main model yet, it automatically selects one of its models. On the use selection page (in `app/settings/ui/models/ModelsScreen.kt`), vision has 「用主模型」 「不用」 at the top and lightweight has 「用主模型」 at the top, below are all models grouped by provider (filterable by name when there are many), labels are reference only and do not filter or gray out, each provider can also take a manually entered model name (for providers that do not offer a list, or when the wanted one is not in the list), and a manually entered one is test-called first (`ModelSetupViewModel.pickManual`, and for the main model it must also call tools), and is selected only after passing and recorded as verified (ones not in the list are also recorded as manually entered), and when it does not pass it says why below that provider; the rest take effect with one tap and return. For a provider that does not offer a list, a model in use but not verified (`ModelSetupUi.unverified`) has the provider row say 「没测试通过」 (Did not pass the test), and the details page has 「重新测试」 (Test again) (`ModelSetupViewModel.retest`). When a model call in a task returns 404, the failure reason states which model does not exist and to check the model name in Settings › Models or switch to the corresponding preset; when the server's JSON error has exact words it does not conclude the model does not exist, but instead quotes the exact words (「服务端回复：…」 (Server reply: …)) and says the model name may be wrong or the service may be temporarily unavailable, then gives the same checking advice (a quote in the middle of a sentence drops one trailing period, and the same for the 「服务端说明」 (Server explanation) of the ChatGPT quota and subscription-tier kinds); for a model this account cannot use it states which one and to switch in Settings › Models or enable it in the provider's console; for one that does not support tools it states to switch to one that calls tools (`core/agent/StopRules.kt`'s `userReason`; when a lightweight model hits these, the rest of this task's steps use the main model). The provider details (same file) are the connection (status, interface, address, replaceable Key), at most three models (ones in use first, marked with which use they work for) and 「查看全部 N 个模型」 (View all N models), and delete (stating before deleting which uses need to be reselected); on the 「全部模型」 (All models) page the search box is fixed at the top, and refresh at the top right lists again. Tapping any model pops up 「用作」 (Use as) main model / vision model / lightweight model from the bottom, going through the same operation as the use selection page. The three uses' names, what they do and descriptions are written only once in `ModelsCopy`. When the use selection page or provider page is opened, a provider whose list has not been remembered yet (for example migrated from an older version) is listed once.
- **Token usage** (`core/model/usage/`): recorded at the source, not left to each caller. Models callable in the App are only obtained from `ProviderStore.modelFor` (`buildModel` is private to it), and before going out they are always wrapped for metering via `metered` (`MeteredModel.kt`): name and capabilities as before, exceptions thrown as-is, text callbacks as usual segment by segment; each call's end records an entry—provider id, the provider name at the time, model name, use (`UsagePurpose`, which is the `ModelRole` when the model was obtained: 「用主模型」's vision and lightweight calls are recorded under vision and lightweight), with usage recorded as input (including cache hits), output and cache-hit tokens, while ones reporting no usage and ones throwing (including cancellation) record only the count, without estimating. The main loop, outcome judgement, intent judgement, vision, memory extraction, route matching, skill and App knowledge drafting and other bypass calls are therefore all counted; model listing is not a conversation call and is not recorded. Anthropic streaming replies' usage follows the API docs' cumulative values: fields in `message_delta` that carry integer values (output, and possibly input and cache) override `message_start`'s, while ones not carried, null or non-integer carry over; some compatible interfaces have all zeros in `message_start`, with the real numbers only in `message_delta`. The ledger `UsageLedger` accumulates by UTC hour × provider × model × use (when local midnight falls in the middle of the hour, the part after midnight is recorded in a separate cell, and the daily token budget counts how much was used today by local date; the local time zone is taken fresh each time, and if the phone's time zone changes while the process has not exited it follows), stored only locally in `files/usage-v1.json` (JSON like other settings; one key table, with rows as compact arrays): accounting only adds in memory, is thread-safe, and about 2 seconds after a change a background thread atomically writes the whole thing, losing at most the last few seconds if the process is killed; it keeps only 400 days. The statistics `UsageQuery` is a pure function, with the local time zone converted at statistics time: 「24 小时」 (24 hours) is the rolling last 24 hours (including the hour of this moment) split by hour, 「7 / 30 / 90 天」 (7 / 30 / 90 days) are local calendar days including today, and 「自定义」 (Custom) is the local start and end dates (inclusive), split by day, and over 45 days split by week (one cell every 7 days from the first day, `UsageStep`); an hour bucket falls into the local day of its start time (correct even on a daylight-saving day). Each cell carries each provider's tokens, for stacking. Each provider has a fixed order (`ProviderUsage.order`: connected ones by connection order, deleted ones after, by earliest accounting time), and its color is taken from the theme's category colors (`MikaColors.series` three, the rest gray and grouped as 「其他」 (Other) in the trend chart), and changing the range or selecting a provider does not change the color; text always uses the ink color. A deleted provider's history remains, using the name at accounting time plus 「（已删除）」 ((deleted)). The use is only a storage dimension, and the UI does not split by use or show price. Settings › Models › 「Token 用量」 (Token usage) enters a separate page (`Route.Usage`, `app/settings/ui/UsageScreen.kt`, with no next level): time (24 hours / 7 days / 30 days / 90 days / custom, with the actual range written below, and custom ones with 「改日期」 (Change dates)), a total usage card (always all providers: a large number, input / output / cache hits / call count), then three charts—「用量趋势」 (Usage trend) (stacked bars by provider, with a legend, two dashed grid lines and a scale on the right, tapping a bar shows this cell's total and each provider's usage), 「按服务商」 (By provider) horizontal bar ranking (usage and share, tapping one selects it and tapping again deselects, with other providers dimmed when selected, and in the trend chart others dimmed to a quarter), and 「按模型」 (By model) horizontal bar ranking (the row of chips above is the same selection as the provider ranking; when selected it lists only this provider's models, the bars are its provider's color, and the share is computed within this row); the footer states the count of calls reporting no usage and 「数字以服务商返回的为准」 (Numbers are as returned by the provider).

## 13. Run records

The computer task console views the conversations and runs saved on the phone through the `RemoteHistory` read-only interface. `PhoneHistory` reads `ConversationStore`, `RunStore` and `TraceStore` directly, checking run ownership by conversation, and reads active tasks' state from the task center's own state. `McpSettings.historyEnabled` is off by default, authorized by the phone's 「连接电脑 → 高级设置」 (Connect computer → Advanced settings), and applies to USB and private networks. The new interface still goes through `RemoteAccess` first; after the owner authorizes, the model request and reply bodies are read paginated only when the task console explicitly expands them. The control interface still recognizes only tasks registered by `RemoteTaskHub`, and history reading does not expand the scope of task control. The task state carries the actual `"run_id"`, so the front end can merge a remote task with the same history turn; the task console updates recordings in the existing refresh scheduling of visible pages, keeping the selected turn and draft.

Each run writes a record (`app/record/RunStore.kt`): `run.json`, `events.jsonl` and screen screenshots under `files/runs/<time>-<id>/`, keeping the most recent 30. Event types are in `core/run/record/RunEvent.kt` (model replies and usage, tool results, observations, activity, confirmations, takeover, origin, compression, outcome judgement, etc.); before writing, `Redactor` masks input into password fields and key-like strings. In the UI 「查看过程」 (View process) opens the timeline (`app/task/ui/RunTimelineScreen.kt`): at the top are the goal, criteria, outcome and duration, with details such as model call count tucked into 「更多详情」 (More details), and below the steps are listed with a vertical line (`components/StepLine.kt`), and tapping a step with a screen shows the screen at that time. While a task is running, the conversation page has 「运行过程」 (Run process) right below the steps: the id is taken by the conversation the card is in (`TaskCenterState.run(conversation).runId`, from the same source as `endedRunIds` at the end, not the service's external displaying id); the outcome at the top says 「进行中」 (In progress), and it re-reads the record every second and the steps grow downward without auto-scrolling to the bottom; it stops when there is an end record or the task is no longer there (`RunTimelineViewModel`'s `alive`, the kind where the process was killed and the record was not finished).

The computer side uses the same persisted record for troubleshooting (`core/remote/RunRecordExport.kt`, `app/task/RemoteRunExport.kt`): `GET /api/v1/tasks/{id}/export` (CLI `mika task export`) exports by task id or run record id, writing `task_id`, `conversation_id`, run_id in the header, with `exportFormat` 1. During export strings go through `Redactor` again. It only recognizes tasks in `RemoteTaskHub`'s receipt index that belong to the current computer access token; the origin field in the run summary and a missing index cannot substitute for ownership verification, and runs started on the phone are not exported. A run in progress, or one whose task was handed over but whose record has not been opened, is marked `partial`. It does not read screenshot files and does not attach an OTLP Trace. When a run record is opened, `TaskRun` records the id on the corresponding receipt, and after a process restart it can still be exported by task id.

**Detailed Trace** is off by default. Debug and performance-test builds can turn it on in 「设置 → 开发者选项 → 运行记录」 (Settings → Developer options → Run records), collecting from the next task, and stopping on turning it off. Each main-loop request (including resends) and top-level tool call of the four model interfaces records one span each. In 「查看过程 → 详细 Trace」 (View process → Detailed Trace) you can compare the first changed block between adjacent requests of the same model, and unreported cache usage is displayed separately from zero hits.

- 「保存本次 Trace」 (Save this Trace) by default exports an OTLP Protobuf file containing only diagnostic metadata (`.pb`). Only when 「附带脱敏正文」 (Include redacted body) is checked does it save a ZIP containing the same `trace.pb` and redacted bodies named by span ID.
- In 「详细 Trace」 (Detailed trace) tap 「通过 OTLP/HTTP 发送」 (Send via OTLP/HTTP), fill in the full traces receiving address, and optionally fill in an authorization header. After confirmation it sends only the default `.pb` diagnostic metadata, and the authorization value is used only for that request. A public address must use HTTPS, while this machine, LAN IPs and `.local` names resolving to local addresses can use HTTP. The UI shows the receipt confirmation, the number of rejected spans or an HTTP error, and after a failed send you can still view or save the archive locally.
- When encountering 「部分记录」 (Partial record), first look at the root span's `mika.trace.partial_reasons`. To locate a truncated block, look at the `mika.block.path` and `mika.truncation.reason` of the `mika.trace.truncated` event on the model span. A single run's body budget is 8 MiB, recording at most 1,024 child spans.

The total capacity of the App-private archive is 100 MiB by default, adjustable in developer options. When space is insufficient it first clears the oldest finished archives, and archives being recorded or exported are kept.

**One summary per task** (`core/run/record/RunMetrics.kt`): `RunMetrics.of(events)` is a pure function that looks only at the events in the run record; all times count from the start event (loading knowledge and preparing the phone connection beforehand do not count).
- The total duration runs to the outcome event (for unfinished ones to the last event, with the outcome recorded as unfinished); the outcome also carries the failure category (the outcome event's `kind`, i.e. the lowercase name of `FailKind`) and the outcome judged after handing over the answer. Succeeded = reported success (including ones that could not be verified) and not judged as only partly done or impossible.
- **First feedback**: from the start to the moment the user first sees this run's actual progress—the moment the earliest genuinely executed model reply arrives (the reply event's `repliedAtMs`; a reply with tool calls is recorded only after execution, so the arrival time is recorded separately), when the UI shows its progress explanation, what it is about to do or the answer; or the earliest activity (the first step finishing when replay does not go through the model). A reply from a lightweight model that was rerouted does not count; when the answer is displayed segment by segment the first segment's text comes earlier but is not recorded, so it does not count.
- **Back and forth with the model**: the number of model reply events (main-loop requests, including replies from rerouted lightweight models); tokens are the sum of these replies' usage, with ones reporting no usage counted separately. Bypass calls (intent judgement, verification, vision, compression) and failed retries do not emit reply events: the run puts `RunUsageTally` into its own coroutine context, and each request on a model wrapped by `metered` adds an entry along the way, recorded at wrap-up as one `RunEvent.ModelCalls` (all requests, the count reporting no usage, and tokens). Outcome judgement and memory extraction after the answer is handed over are outside this context and only go into the Token usage page.
- **Where the time went**: model thinking is the sum of each reply's request time (failed requests before a retry and backoff are recorded separately); screen reading / operation is the execution time of top-level tool calls (model-called and replayed), split by the kind the single execution entry assigns to the activity (a tool whose declared risk is read-only counts as reading, the rest as operation), with no new timing points added. A batch of actions or a page script's outer call time already includes sub-steps: reads in sub-steps count as reading and the rest as operation, without double counting; control calls such as waiting, asking the user, asking for confirmation and handing to the user count as neither reading nor operation. Other = total duration minus these three: waiting for the user, retry backoff, control calls, verification and the remaining overhead.
- The run record's writer thread computes as it writes (`RunMetrics.Builder`, keeping only a few numbers per tool result), and at close hands the summary to `RunMetricsStore`: `files/run-metrics.jsonl`, one line each, keeping only the most recent 500, not cleaned up along with the 30-run run records; after the outcome is judged it is added in. Unreadable lines are skipped, and writing replaces the whole file. There is no extra read or write on the main loop.
- UI: the top of 「查看过程」 has a line 「共 2 分 13 秒 · 和模型来回 14 次 · 8.6 万 Token · 第一次反馈 3.2 秒」 (2 min 13 s total · 14 back-and-forths with the model · 86K tokens · first feedback in 3.2 s), and tapping it opens the time of model thinking / screen reading / operation / other and their shares, the input / output / cache-hit tokens, and the step count (`app/task/ui/RunMetricsUi.kt`; token formatting is the same as the Token usage page). ## 14. Prompts

The fixed text the model sees is all in `core/src/main/resources/prompts/`, with the layering and rules in its `README.md`: `system/` (identity and general guidelines), `capabilities/` (one paragraph per capability, spliced in only after that group of tools is expanded), `tools/` (each tool's description), `entries/` (short descriptions of entry tools while that group is withheld), `feedback/` (tool results and main-loop feedback), `roles/` (internal roles such as verification, outcome judgement, memory extraction and skill drafting). The system prompt is assembled by `SystemPrompt` (`core/agent/SystemPrompt.kt`) at task start, and reassembled only when a group of tools is expanded (paragraphs in a fixed order); all text has golden-sample tests, and the full picture and size of the four cases—withheld, phone only, web only, all on—are in `prompt-surface/layers/`.

The type comes first from the MIME given by the content provider, and when that cannot be told, from the extension (`ViewerKinds`, `app/ui/viewer/ViewerKind.kt`): a web page uses a newly created WebView (scripts on, zoomable, not going through the web capability's browser); Markdown uses the same parser and block styles as the conversation (`MarkdownText`), lazily loading by block so that even a large file is not laid out all at once; a PDF uses the system's `PdfRenderer` to draw page by page at screen width, drawing only the visible pages, zoomable with two fingers, with the page number at the bottom; images fill the space in proportion and can be zoomed and dragged; text types are shown in a monospace font and can be selected. Text and Markdown read at most the first 1 MB, and when there is more, a line at the top says "The file is large; only the beginning is shown". The top bar for text and Markdown also has "Find" and "Copy all": the find bar searches automatically for the typed characters and shows which match out of how many (counting only the first 1000 matches when there are too many, showing "1000+"), can jump to the previous and next match, and colors the matches with the current one darker; copy puts the whole text read so far on the clipboard, with a hint when it is too long to fit. On the right of the top bar are "Share" and "Open with another app"; when it cannot be read, it says so and offers "Open with another app". Other types do not enter this page and go straight to the system's chooser.
- **Picture-in-picture** (`app/chat/ui/AgentPip.kt`): a draggable floating window on the conversation page, usually parked at the bottom right, above the input bar, showing in real time the virtual screen or web page Claire is operating (view only, no operating); a thin green border means it is working, and an orange breathing glow means it needs you. It is an in-app overlay, not a system picture-in-picture. A web screen comes from the current tab attached to the web display; when a web page is read only in a temporary background tab (`web_read_page` with an address) the web display has no tab, `TaskRun` does not count it as being on the web (`webOpen` is false and no screen is put up), the small window does not appear because of it, the floating capsule shows the conversation card instead, and as soon as a visible page is opened it displays as usual. On the phone side, a created virtual screen does not mean there is a picture: the screen of a task that only uses system commands and event tools is empty, and `TaskRun` sets `appShown` (`TaskEnvironment.agentAppShown`) only when the target App is first opened onto the screen; the small window appears according to `TaskEnvironment.previewOpen` (an App has been opened or the built-in browser is in use), so the whole task is not a black rectangle. After expanding, the top left has "Do not show the small screen for this task" (`ChatViewModel.closePip`, `PipUi.closed`): until this task ends there is only a small "Show screen" button at the bottom right, and tapping it opens it again (`reopenPip`); it is cleared when switching to the next task or attaching to another task. When it is closed, it does not expand automatically when a takeover starts either; when it needs you the small button turns into an orange breathing "Waiting for you", and tapping it scrolls to the card that needs you. There is no settings switch; to see all screens go to the background screens page in the sidebar.
- **Floating capsule** (`app/capsule/`): when the user is in another App, a Claire icon floats at the top right of the screen, under the status bar, saying the most important thing in the background at that moment; normally it is just a dot (about 40dp), and only when there is something to tell you does it expand into a one-line capsule. The overlay is drawn by the accessibility service (`app/cap/phone/a11y/OverlayHost.kt`: an accessibility overlay window, with no "display over other apps" permission; a host that gives Compose a lifecycle, state saving and a ViewModel outside an Activity; normally it does not take focus, and when typing is needed it can switch to accepting the keyboard; when the service disconnects, `ScreenAccessibility` tears down the windows it added along with it; if it cannot be added it returns empty, without an error). What is shown is decided by the pure logic `CapsuleModel`: it is not shown when the switch is off, when the accessibility service is not there or the overlay cannot be drawn, when Claire's own UI is in the foreground (`AppForeground` counts visible Activities), or when the screen is off or locked (`DeviceStateWatcher`); otherwise it says only one thing by priority — you are handling it (the App has been moved to the main screen, with a bar at the top center "You handle it · Drop it · Handled", whose two buttons are cancel the task and hand back), needing you to take over / agree / answer, waiting for a condition, working, finished / failed / stopped. The states on the dot: while working, a blue arc runs around the outer ring (a full motionless ring with animations off); waiting for a condition, a gray ring; needing you, the whole dot turns orange and the outer ring breathes; with several things, the count is written in a corner; finished, a green check, and failed or stopped, gray badges; idle ("Always show" with no task), nothing at all; a change of step while working does not expand it. It expands into a capsule in only two cases: there is something needing you that you have not yet seen in the card (it stays put without shrinking or fading until the card is opened or that thing no longer needs you; the items seen when the card was opened — the same item, the same wait — are recorded as seen, and after collapsing it returns to an orange dot, expanding again only when something new arrives or another wait appears), and something just finished ("Finished · tap to see the result" and the like, expanding for 4 seconds before shrinking back to a dot with a result badge, staying a total of 10 seconds before disappearing, or returning to the icon under "Always show"; ones already seen in the card go straight to a dot; when a conversation has been deleted, the item that just ended disappears at once and the card no longer follows it). With several things, the capsule says "N items"; when something needs you it says "1 needs you · 2 in total"; the text uses `Running.narration` first, then `reason`, and replay and batch execution read "Following the route 3/7" (in a screen reader the dot says something from `CapsuleCopy.describe`, e.g. "Claire is working: …; tap to see details"). Within the same item and the same state each sentence stays at least 1.5 seconds (keeping only the last sentence during that time), the capsule only widens and never narrows, and its width is set afresh only when the state changes, or when it expands or shrinks; a line is at most 60% of the screen wide. The dot and the capsule share one base, the width changes slowly between the two, and the icon stays put against the edge it is docked to (it switches directly with animations off). `CapsuleContent` is the stateless capsule UI, and `CapsuleController` connects task state, the switch, the foreground, the screen and the service to the model, adding, moving and tearing down windows according to the result. Tapping either the dot or the capsule expands the card (`CapsuleCardContent.kt`, stateless; the content is decided by the pure logic `CapsuleCards`, see `app/capsule/CapsuleCardModel.kt`): the card says only one thing, has no list, and does not switch inside the card: first the task of the conversation that just had words sent from the card (so that the answer can be seen), otherwise the first by priority needing you (takeover, agreement, answer), in progress, just finished; if other things are going on too, go to Claire's conversation page to see them. The chosen item picks its card by its current state (not by its history): one that has not ended and is at this moment operating an App or a web page (it has its own virtual screen `TaskRun.displayId`, or is using the built-in browser `TaskRun.webOpen`) gets the task card, and anything else — pure chat, already ended (including ones that operated an App and then answered when done), and idle — gets the conversation card (`CapsuleCards.taskCard`). In the task card, working shows the most recent three steps (the same reduction as the conversation page's steps, `ChatViewModel.reduce`) and the elapsed time; while the task is still going (working, Claire asking you, waiting for a condition), stop is the same black stop key to the right of the input field as on the conversation page; needing you to take over says why (for a payment it lists the item, amount and address), "I'll handle it" (with this wait's id, the same as on the notification) and stop; when it is queued behind other takeovers it says "Finish the other takeover first, then this one" and gives no "I'll handle it"; when it is first and others are behind it says "After this one, N more are waiting" (the order is read from the `TakeoverQueue` shared by the several tasks and re-read whenever the queue changes; among equally urgent items the one ahead in the queue is mentioned first, and as soon as the one ahead is handed back the next immediately becomes the capsule's "needs you"); needing you to agree uses the same wording and declaration id as the conversation page's confirmation card, Agree / Do not agree, plus "Allow all for this task" and "Allow always", while a bottom-line operation is only offered "Agree only this time"; when Claire asks you and gives options they are listed as buttons (as the answer); waiting for a condition says why and offers continue when it can continue; at the bottom is "Back to Claire to see the whole process". The conversation card is that conversation's back-and-forth (arranged by `CapsuleThreads` in `app/capsule/CapsuleThread.kt`, drawn with `LazyColumn`): the same record as the conversation page (the turns `ConversationStore` saved, joined with ones not yet saved and with this conversation's current task, de-duplicated by run record id), the user's words as small bubbles on the right, Claire's answer as the full text with markers stripped (`CapsuleCards.answerText`), oldest at the top; a reply that an interjection interrupted is placed before that interjection as on the conversation page, in a pale color with a line underneath "Interrupted by your new message"; a reply already finished before the interjection is also placed before it, looking like an answer; an interjection not yet handed to the model is placed after the answer being written; a turn that operated an App or web page (reading its activity targets from that turn's run record, and treating it as pure chat if the record has been cleared) is collapsed into one line, "✓ Shopping · done", "12306 · failed", followed by the answer, without steps, screens or sources; for pure chat the text grows as it answers, with the stop key to the right of the input field, and when it needs you to answer or agree, that question is in the back-and-forth and the buttons are fixed below. The most recent 10 turns are laid out first, and scrolling to the top lays out 10 more before that (each keyed by run record id, with the list staying put); on opening, the latest sentence you said stays at the top of the visible area, and text growing downward follows only when you were already at the bottom (as on the conversation page). Below are the input field and "Back to Claire". The buttons all go through `TaskService`'s existing actions (cancel, continue, takeover, answer, agree, disagree), carrying that item's task id, and "Back to Claire" uses the same entry as tapping the notification, `TaskService.openAppIntent`. Tapping outside the card, the collapse button or back folds it into a dot (or a capsule when there is still something needing you that has not been seen); while it is expanded the model's clock stops, so a result the user is looking at is not taken away, and the remaining time continues after it is folded; when the App is handed to you the card folds and is replaced by the bar at the top. The dot and the card each live in an overlay window of their own, each at its own position (when folded, the card window is explicitly made invisible, and its empty content only handles layout, not relying on zero size to remove the system's stale frame): on expanding, the card scales up from the dot's position in its own window and fades in (about 240 ms; it waits for the card to lay out before starting, and the dot stays in place until then), and the dot's window empties out accordingly; on folding, the card shrinks back toward the dot's position and fades out while the dot emerges at the edge at the same time (both in the same animation in `app/capsule/CapsuleCardContent.kt`, moving only layers, and going straight to the final state with animations off). A single window is never moved back and forth between two places, because Android turns a plain window move into a sliding animation; nor is the window resized frame by frame (every change re-lays out and swaps the canvas, making it stutter). The width between the dot and the capsule also changes only while drawing: layout goes once to the wider of the two, and it shrinks only after drawing. While working, needing you to take over, or waiting for a condition, a small picture of the virtual screen goes on the left (the item's own `TaskRun.frames`: on the phone, virtual-screen frames, on the web, built-in browser frames, the same source as the in-app picture-in-picture; items without a picture get none), received only while the card is expanded and looking at that item, at most 5 per second, and one identical to the previous is not pushed (`previewFrames`, in `app/capsule/CapsulePreview.kt`); tap once to enlarge, and tap again or tap outside to go back. The capsule can be dragged (`OverlayHost`'s window is laid out over the whole screen but is only as large as its content, dragging is computed at the window root in screen coordinates, and only movement past the touch slop counts as a drag, cancelling the button being pressed so it is not taken as a tap), and on release it sticks to the nearest left or right edge (12dp from the edge, avoiding the status bar, notch and bottom gesture bar, with the range read from the system bars by `OverlayHost.area`); which side it is docked on and its height as a proportion of the area it can occupy are stored in `FeatureFlags`, and it is placed back by that proportion next time and after rotation; the "You handle it" bar is at the top center and can only be dragged up and down. The card's width is fixed and it is centered horizontally. The conversation card has a fixed height that does not change with content: 58% of the screen height, and when the input method appears it shrinks to above it (height and position are set from the tallest appearance after this round's input method appears, so that a pinyin candidate row more or less does not change them; the middle section gets shorter and the input field is still visible); the task card is as tall as its content with no empty space below, and its middle section takes whichever is taller of the small picture on the left (at the picture's aspect ratio) and the text on the right, or just the height of the text on the right when there is no picture, at most as tall as the conversation card, with longer text scrolling inside the right section. When the middle does not fit in either kind of card it scrolls inside, and the buttons and input field stay fixed below. The card's position is recorded by its top edge: the top's proportion of the area it can occupy (the area is computed for the tallest card, so cards of different heights align their top edges at the same proportion), and when the card changes (the task card and conversation card swapping) or the content grows taller or shorter the top edge stays put, moving in one go (the window follows the content size only once, not frame by frame), and when it does not fit downward (gesture bar, input method) it moves up to just fit. The card is dragged up and down by its title bar (`OverlayWindow.draggable` gives a handle, and only pressing inside it drags, while sliding up and down in the middle scrolls; here too only movement past the touch slop counts as a drag, so the collapse button is not hit), and on release it is clamped within the status bar, notch and gesture bar, with the top's proportion stored separately in `FeatureFlags` (the proportion previously stored for the fixed-height card is exactly its top proportion, and is still read), and it is placed back by it next time it expands and after rotation. The algorithms are the pure functions `CapsuleDocking` and `CardDocking` (in `app/capsule/CapsuleDock.kt`). In a screen reader the capsule has an extra "Move to the other side of the screen" in place of dragging, and the card's buttons, small picture, collapse and back all have descriptions. The card has an input field at the bottom (none when needing you to take over or agree): while running or waiting for a condition it says "Add to or change the request…" and hands the words to that item (the same path as an interjection while a task runs on the conversation page, `TaskService.start` carrying this sentence's id); when Claire asks you it says "Answer Claire…" (the option buttons stay); after finishing it says "Say more…" and continues in the same conversation; when there is no task (the switch is "Always show"), tapping the Claire icon gives the idle conversation card: it continues the conversation the user is in in the App at that moment (`ConversationStore.current`, announced by `ChatViewModel` when opening a new conversation, switching conversations, or speaking in a new conversation, with the choice in the pure logic `CapsuleIdle`: with no record it continues the most recent one, and a newly opened conversation with nothing said yet is a new conversation; the conversation it is in takes precedence over results that have ended in other conversations and are still attached); at the top is "Continue "<most recent conversation title>"" · New conversation", in the middle is that conversation's back-and-forth (empty for a new conversation), and the input field says "What would you like Claire to do?". The latter two open a task just as sending on the conversation page does (recorded into that conversation; queued rather than lost when another task is running), after which the card follows that conversation's task and the answer grows in the conversation card; once that item opens an App it switches to the task card. When the card folds or the capsule hides, unsent words stay in the input field (`CardInputUi.collapsed`; the captured screen is not kept, but a note written for it is), to be edited further on the next expand, with the cursor at the end, and only cleared when sent; they exist only in memory. The retained words do not follow the item they were originally addressed to, and on the next expand are sent to whatever the card is addressed to at that moment; sending a screen by double-tap, or long-pressing to speak and releasing to send directly, does not carry them, and they stay as before. Normally the input field is only a one-line hint (showing the unsent words when there are any), and only when tapped does the overlay accept the keyboard (`OverlayWindow.setFocusable`), giving it back immediately on sending, folding, tapping outside or pressing back; when the input method appears everything makes way for it (the input method window's position is read by `OverlayHost.imeTop` from the accessibility window list, re-read whenever the windows change, no matter which App the input method was raised for): the card, the dot and the expanded capsule all move above it, and return when the input method collapses. Untouched for 3 seconds, the dot fades to about 40% (the outer ring and badges stay solid), and touching it, dragging it, or a change of state or item count restores it at once; an expanded capsule, needing you, the "You handle it" bar and the card do not fade (the rule is the pure logic `CapsuleFade`). On rotation it is laid out again by the remembered side and height proportion; full-screen playback gets no special handling. The switch is in Settings › Floating capsule (in `app/settings/ui/SettingsSubPages.kt`): off / show when there is a task / always show (the default, so that the capsule can be double-tapped to send this screen at any time), stored in `FeatureFlags`; ones never chosen (including those upgraded from an older version) take the default. The × at the top right of the card only folds it; the card's bottom row (after "View process" in the task card and "Back to Claire" in the conversation card, and alone in an idle card with no conversation yet) has a gray "Turn off floating capsule" (`CardActions.hideCapsule`): the same place as choosing "Off" in Settings (`FeatureFlags.setCapsuleMode`), and as soon as the switch changes `CapsuleModel` stops showing it and the capsule and card are folded on the spot, while tasks keep running and notifying as usual; a toast then says "The floating capsule is off; you can turn it back on in Settings › Floating capsule" (the names come from those two in Settings, and follow the language).

- **The screen right now** (double-tap the capsule): double-tapping the dot or capsule sends the screen the user is looking at on the main screen right now to the conversation in the card that a single tap expands; afterwards it is exactly the same as sending a sentence in the card (an interjection while running, an answer when Claire asks you, continuing after finishing, continuing the most recent conversation or opening a new one when idle, the same `CapsuleController.submit`), then it expands the card to show the answer. A single tap waits for Android's double-tap timeout (`ViewConfiguration.getDoubleTapTimeout`) to pass before expanding, and the single/double tap decision is the pure logic `DoubleTap`; in screen readers there is also 「把此刻的屏幕发给 Claire」 (Send the screen right now to Claire). When that card has no input field (needing you to take over or agree) there is nowhere to send, so double-tapping is the same as a single tap. Whether it is shown still follows the floating capsule's switch, with no separate switch; when Claire itself is in the foreground or the screen is locked the capsule is not there anyway. To the left of the card's input field there is a screenshot button: the capture hangs above the input field (thumbnail, 「你此刻的屏幕」 (Your screen right now), App · time, × to remove), and you can add a sentence before sending; sending only it is the same as double-tapping.
   Capture: the overlay window is not torn down, only its content is hidden (`OverlayWindow.hiddenWhile`), and it waits for the hidden frame to be drawn and handed to the system (frame commit callback), then two more refreshes (the compositor swaps it in) before capturing; when the card's input field is open it is collapsed first and it waits for the keyboard to go down. The screenshot uses the accessibility service's `takeScreenshot` to capture the main screen (`ScreenAccessibility.takeMainScreenshot`, waiting a second before capturing when too fast), and right after capturing it shows the overlay again and flashes the dot, while at the same moment reading the accessibility tree of the App window on the main screen (the status bar, navigation bar, keyboard and overlay do not count). The tidying happens in the background (`MainScreenCapture.build`): on-screen text first uses elements with names in the tree, and when the tree is not enough (the same `TreeAdequacy` as task screen reading) it recognizes text on the image (`PhoneOcr`), only filling in what the tree lacks and removing misrecognized lines and the text in the status bar and navigation bar lines; an element that merely joins several text pieces inside it (a whole settings row) is not listed separately, leaving the pieces inside; each line carries a center point (0–999, with pixel centers of tree elements also converted), from top to bottom and left to right within a line (`core/screen/user/UserScreenText.kt`). Pages that block screenshots (the capture reports a secure window error, or the capture comes out almost entirely black while there is an App window on screen) do not keep the image, only recording which App it was and that it could not be captured. When the foreground is Claire itself, nothing is captured.
   Storage: it is kept with the conversation in that conversation's workspace (`/workspace/screens/<id>.jpg` and `.json`, `app/chat/UserScreenFiles.kt`, read and written through the workspace file gate, holding the tree lock's permit when writing), in the same place as attachments and gone together when the workspace is deleted; commands in the sandbox can read this image too. The message itself is an ordinary sentence: a separate line `[[screen:<id>]]`, with the rest being the note (`core/screen/user/UserScreenMessage.kt`), stored into the conversation as usual and used as an interjection or answer, while an image chosen from the gallery or files is still the attachment line, and the two do not mix. The conversation page and the card draw it as a screenshot bubble from this (`app/chat/ui/ScreenMessage.kt`: thumbnail, 「你此刻的屏幕 · App · 时刻」 (Your screen right now · App · time), with the note in its own bubble; ones that could not be captured are a line 「没截到」 (Not captured)), and the conversation title, sidebar and notification call it the note or 「你此刻的屏幕」 (`ScreenCopy.plain`).
   To the model (`core/agent/UserScreenTurns.kt`, text in `UserScreenPrompt` and `feedback/loop.md`'s `user_screen.*`): this sentence becomes "The user just captured the screen they are looking at (<App>, <time>), with no words" / "... with these words: …" (when capture was blocked it truthfully says it was not captured), and when the main model can see images the screenshot is attached to this sentence; immediately after comes a `user_screen` context block (not counting toward the budget, kept during compression): id, App and package name, time, and the text on screen (wrapped in an untrusted marker), and when there is no note it also carries the rule for guessing intent from the screen—if it is only answering, reading or looking something up, just do it; if it is to write or change something elsewhere (note it down, send, publish, book, pay, delete, change settings) first ask once with ask_user in one sentence and give options (buttons in the card), and do it only after agreement; when it is unclear which App the user uses for this kind of thing, ask that too, and remember it when memory is possible. Ones with a note are handled as usual without an extra rule; confirmation of irreversible operations stays as before. When only the screen is sent without words, intent judgement is not asked (there are no words to judge). Screens from previous turns keep only one line (App, time, the first few words on screen and the id), and to look again use `view_user_screen`: by id it gives the App, time and text, attaching the screenshot when the main model can see images, and when it cannot see images but a vision model is configured it asks the vision model that stored screenshot with the question (role prompt `user_screen`); it is offered only when this turn's words or previous turns carry a screen. The text on screen is recorded into the evidence ledger (answer sources); outcome judgement and memory extraction read the rewritten sentence; a sentence with a screen does not record an experience route.
- **Notifications**: task progress, needing takeover, needing an answer, and results all have notifications; the takeover button is on the notification. The 「需要你处理」 (Needs your attention) and 「任务结果」 (Task results) channels are created at high importance (heads-up), while 「任务进度」 (Task progress) stays quiet; when the capsule is showing on a lit screen, 「需要你」 (Needs you) is still sent but quietly into the notification shade (using the system's grouped-alert rule: putting this one into a group with no summary and letting only the summary alert means the system neither rings nor shows a heads-up banner, the same approach as the system's own silent notifications; the channel is not changed and no new channel is created), and when the screen is locked, the capsule is off, or the overlay cannot be drawn it pops up as before; the results channel has changed id (`task_result_v2`, with the old one deleted at startup), and everywhere channels are created through `TaskService.ensureChannels`. Status monitoring checks whether these two channels have been turned down, prompts when they have, and the fix button opens the system settings page for that channel directly, falling back to the App's notification overview page when it cannot open; after notifications are allowed during phone operation onboarding it checks once too. Settings › 「通知」 (Notifications) (in `app/settings/ui/SettingsSubPages.kt`) only shows status and goes to the system to change it, without putting notification switches in Claire: at the top is the master notification switch (「去打开」 (Turn on) when not allowed, requesting permission first from Android 13 and otherwise opening the App notification page), and below the three channels 「需要你处理」, 「任务结果」 and 「任务进度」 each have a row stating when it is sent and whether it is now 「会弹出」 (Pops up), 「只进通知栏」 (Only goes to the notification shade) or 「已关闭」 (Off), and tapping a row opens that channel's system settings page (with the same jumping and fallback as above). Status judgement is the pure function `NotificationOverview.of` (`app/settings/NotificationOverview.kt`): by channel importance, `IMPORTANCE_NONE` is off, not lower than `IMPORTANCE_HIGH` pops up, and the rest only go to the notification shade; if 「需要你处理」 or 「任务结果」 does not pop up it is flagged (progress being quiet or off is not abnormal), and when the master switch is off all three rows are off; the 「通知」 row in 「常用」 (Common) on the home page shows the overall status at the right (normal / N items will not pop up / off); the phone operation page no longer repeats the entry. Channel importance is read into `SystemStatus` by `SystemStatusMonitor`, and updated with `refresh` when returning from system settings.
- **Other pages**: Settings (`app/settings/ui/SettingsScreen.kt`) has the overall status card at the top (following `Prerequisites.check`, 「一切就绪」 (Everything ready) when all is well, turning into a prompt with a fix button when there is a problem), and the home page is divided into 「常用」 (Common) (models, phone operation, task running, floating capsule, language and appearance, notifications), 「我的数据」 (My data) (memory and data, app access) and 「其他」 (Other) (advanced and other, about Claire). Token usage belongs to the models page, opened via `Route.Usage`; autonomous mode belongs to task running; website sign-in and operation routes belong to memory and data, with internal back managed by MemoryDataScreen, and the original memory / skills / pending confirmation home page does not add a level. The models, usage, memory and data, and about pages go through `NavStack`, while the other settings subpages are still switched by the settings page itself. There is also a plan and phone assistant setup guide; on the sources page (`SourceScreen`) each source shows only the screenshot when it has one (tap to enlarge full screen) and the original text excerpt when it does not, sharing the same top bar, groups and rows as the licenses page (`LicensesScreen`) and those pages.
- **About and checking for updates**: the about page (`app/about/ui/AboutScreen.kt`, text in `AboutCopy`) is entered from the settings home page or 「关于 Claire」 (About Claire) at the very bottom of the sidebar (the bottom row of the sidebar has 「设置」 (Settings) on the left and 「关于 Claire」 on the right, going through `NavStack`'s `Route.About`). At the top are the version number, Beta mark (`BuildConfig.BETA`) and build number (`BuildConfig.GIT_HASH`, taking the current commit's short hash at compile time, or dev without git); below are check for updates and update history; report a problem (go to GitHub to file an issue, with the issue template prefilled with device model, Android version and Claire version in three lines; copy diagnostics); open-source repository and usage instructions; data explanation; the footer 「基于 Apache-2.0 开源许可发布」 (Released under the Apache-2.0 open-source license) leads to the licenses page (`Route.License`: the license text `assets/licenses/Apache-2.0.txt`, with third-party components listed below). External addresses are all in `app/about/MikaLinks.kt`. Check for updates (`app/about/UpdateChecker.kt`) accesses GitHub's releases/latest interface by default (no sign-in, short timeout), and being unable to connect, rate limiting or failing to understand all count as not found; in Settings › About › Update mirrors you can turn mirrors on and off and manage the list (order, add, delete, edit, `app/about/UpdateMirrors.kt`, file `files/update-mirrors.json`, presetting gh-proxy/ghfast/ghproxy.net measured usable in 2026-11), and once on, mirrors and the official site are queried in parallel: when a mirror finds a new version it is shown first, and after the official site responds the official version and verification info take precedence; when the official one fails, the newer version found by a mirror is kept; when a mirror does not proxy the API it falls back to the `/releases/latest` redirect (302 Location) or the tag in the page, and then reads the APK file name and sha256 from `/releases/expanded_assets/<tag>` (`app/about/UpdateProbe.kt`); every time the App opens (`MainActivity.onStart`) it quietly checks once, only blocking back-to-back ones (not checking if less than two minutes since the last automatic check, `UpdateSchedule.MIN_GAP_MS`; the time is recorded before starting the check, so ones arriving at the same time do not check twice), with no prompt and no banner on failure, and only tapping 「检查更新」 (Check for updates) manually prompts the result. The found version is stored in `files/update-v1.json`, and when it is newer than the current one the sidebar, settings home page and about page carry a red dot; when there is an APK attachment, 「下载更新」 (Download update) in the update panel is handed to the system DownloadManager to download in the background (`app/about/ApkUpdater.kt`): it accepts only HTTPS addresses under the official repository's `releases/download/` (`ApkIntegrity.requireOfficialUrl`), puts the file in this App's external dedicated directory `Download/updates/`, keeps only one at a time, keeps the task id so progress can be seen again after reopening, and can be deleted and retried on failure; the download notification is shown only while downloading (tapping a completion notification would bypass verification and open the package directly, so it is not kept). After the download completes, tapping 「安装更新」 (Install update) requires allowing installation from unknown apps the first time and continues after authorization returns; before opening the system installer it checks in order: the size and the release attachment's SHA-256 (the interface's `digest` field, verified only when present, rejected on mismatch), the package name, the version number being higher than the installed one, and the signing certificate matching the installed one (or the installed certificate being in the new package's signing history); ones that do not pass have the file deleted and the reason explained (`ApkRejected`). The system installer verifies the signature again and asks for confirmation. After the update is installed, the next startup clears the leftover package (`dropInstalled` in `MikaApp`). When there is no APK attachment it still opens the release page.
- **Diagnostics**: collected only when the user actively taps 「复制诊断信息」 (Copy diagnostics) (always at the bottom of the guide page, and also in the step that errored on failure; and in About › Report a problem); it is first shown in full to the user in a bottom panel (`app/ui/DiagnosticsSheet.kt`), enters the clipboard only after tapping 「复制」 (Copy), and is handed to the system share panel only after tapping 「分享」 (Share), with nothing sent automatically. Collection (`app/about/DiagnosticsCollector.kt`) only reads existing state: system status, the built-in assistant's status and the original text of the most recent pairing or connection failure (`BuiltinShellEngine.lastError`), how many candidates each source gave when looking for a connection port, how many ports were open and how many looked like adbd when scanning this machine, whether there is a user-filled port (`AdbConnectPort` reports to `BuiltinShellManager.lastConnectCandidates`, only counts, without addresses or port numbers), the automatic recovery items, model configuration, run summaries, and update checks; the guide page's steps use the guide page's own input (`setupInputs`, including steps the user confirmed) handed to the same `PhoneSetupFlow` for computation, not computed again separately. When written as text (`app/about/Diagnostics.kt`, pure functions) the section order is fixed and keys are English: App, Device, Phone control, Recovery, Models, Recent runs, Update; providers write only the interface type and host name, and runs write only relative time, outcome, failure category, step count and model, without Keys, sign-in, task goals, answers or screen content; finally the whole thing goes through sanitizing once (IP with port, port numbers, emails, credential-like "name=value", then to `Redactor`). The last paragraph of the GitHub issue template only tells the user where they can copy and paste it, and does not include it automatically.
- **Compatibility self-check** (Settings › Recovery and repair › Compatibility self-check, `app/selfcheck/ui/SelfCheckScreen.kt`): the user taps 「开始自检」 (Start self-check), and in about a minute it checks what works on this phone and produces a report that can be copied and pasted to GitHub. The pure logic is in `core/selfcheck/`: the items (`SelfCheck`: device, permissions, built-in assistant, virtual screen, opening Apps, screen reading, tapping and typing, continuous running, main screen undisturbed, built-in browser, sandbox, another App copy) run in order, each stating which items it must pass first, and if one fails or is skipped the ones depending on it are skipped with a note of which one is missing (partially available does not count as failed); each item has its own time limit (5–25 seconds), the whole run has a separate 90-second total limit, and what remains after it is used up is recorded as skipped; an error counts as a failure and does not interrupt later items; on cancellation the running and later items are recorded as skipped, and `SelfCheckPort.release` is always called once at the end (`SelfCheckRunner`). Each item's conclusion is "status + a line of English fact + one plain-language `Advice` for the UI"; the report (`SelfCheckReport`) has only version, device model, system version, processor architecture, memory, screen size, whether wireless debugging is available and one line per item, with English keys, and finally the whole thing goes through the same sanitizing as 「复制诊断信息」 (`Diagnostics.sanitize`), without accounts, App lists, user content or serial numbers. The Android side is implemented by `AndroidSelfCheck` (`app/selfcheck/`), and the phone items use the same set as tasks: the process-wide shared assistant connection (`SharedShell`), `AgentDisplay` creating screens, and `AndroidScreen` opening pages and `tapRef`, `typeText`, `scroll`, `back`, so the results reflect the Agent's real behavior. What is operated on the virtual screen is Claire's own test page `SelfCheckTargetActivity` (a counter button, an input field, a column of rows that scrolls, a number that keeps jumping and a bar that keeps changing color, marked as Claire's test page): like the service connected to the computer, it is open only to the shell level: exported in the manifest, but requiring the caller to hold INTERACT_ACROSS_USERS_FULL (which shell and the system have and ordinary Apps cannot get), with no intent-filter, in a task of its own that does not enter recents (`ManifestProvidersTest` guards it), and it closes itself at once when launched onto the main screen. `AndroidScreen.openOwnPage` hands its component to the assistant through `IMikaShell.startSystemAction`, and the assistant, recognizing this component (`SystemIntents.OWN_PAGE_CLASS`, with the package name still having to be Claire's), launches it directly onto Claire's screen as shell (the same path as opening an App: startActivityAsUser with the launch screen, falling back to `am start --display` when that fails); shell launching is not subject to Android's background activity launch restrictions, so it opens whether Claire is in the foreground or not. No new assistant interface was added. System settings are opened only through the ordinary `openApp`, checking that it opens on Claire's screen and not the main screen, then going back once to leave, without tapping anything inside. The continuous running item watches the test page for 15 seconds: if the virtual screen's live frame does not change for 3 seconds, or the jumping number in the view tree does not change for 3 seconds, it counts as stopped. The main screen item compares the topmost task on the main screen at the start and at each checkpoint. The built-in browser item builds a separate web display and tab pool (not giving a site list, and visits are not recorded into website sign-in), opens the local page `app/src/main/assets/selfcheck/page.html` bundled with the App (through WebViewAssetLoader, without networking), and goes through `WebScreen`'s page reading and tapping by id, then checks. The sandbox item runs `echo ok` and one line of Python only on arm64; a runtime environment not ready counts as partially available, and it is not installed just for the self-check. The another-App item only counts how many usable copies of another user there are (`appCopyUsers`, private space not counting), without listing Apps. Leaving this page cancels it, and the virtual screen, test page, web tab and assistant connection are released on the spot; it does not start while a task is running. After it finishes the whole report is shown on the page, and 「复制报告」 (Copy report) only copies; 「去 GitHub 反馈」 (Report on GitHub) copies the report and opens the new issue page, choosing the device feedback template `.github/ISSUE_TEMPLATE/device-report.yml` and prefilling only the title (`[Compatibility] <Android version> <model`), with the report pasted by the user and not put into the address (addresses have a length limit). The test that runs the whole set on a real device is `SelfCheckDeviceTest`.
- **First-time onboarding**: welcome (`app/setup/ui/WelcomeScreen.kt`) → configure models → phone operation (`PhoneSetupScreen`, a numbered checklist, skippable; after a successful connection the checklist is kept with everything ticked, the top says 「已经设置好了」 (It is already set up), and the bottom main button is 「开始使用」 (Start using), entering conversations only after tapping it, while entering from Settings shows 「完成」 (Done)). Which steps to take is decided by `Onboarding` (`app/setup/ui/Onboarding.kt`) by "seen or not": only when there is no main model yet and models have not been configured in onboarding does it take the first two steps (ones that have configured models skip them directly); phone operation follows the original judgement (the system is new enough, not ready yet, and the guide has not been seen).
- **UI language** (`app/i18n/`): UI text is all Android string resources, with 10 UI languages: English is the default (`res/values/`), Simplified Chinese in `res/values-zh/`, Traditional Chinese in `res/values-b+zh+Hant/` (Android matches by writing system, and `values-zh` does not take effect for Traditional systems), plus Arabic, Japanese, Korean, Spanish, Portuguese, Russian and Indonesian (`values-ar`, `values-ja`, `values-ko`, `values-es`, `values-pt`, `values-ru`, `values-in`; Indonesian keeps Android's old language code in). Each set of entries corresponds one-to-one with English (`StringResourcesTest` checks the entries, placeholders, the quantity words each language's plurals need, Traditional against Simplified, and that no Chinese is left in English and languages not using Chinese characters), so a system in these languages shows the corresponding translation and a system in other languages shows English. Settings › 「语言」 (Language) can be set to follow the system or one of them (`AppLanguage`; each name is written in its own language, and 「跟随系统」 (Follow system) in the current language; the language tags are zh-Hans, zh-Hant, ar, en, ja, ko, es, pt, ru, id, with non-Chinese recognized by language code regardless of region, and old codes such as in from Android Locale are first converted to current codes before comparing, and a Chinese tag without a writing system is filled in by ICU's `ULocale.addLikelySubtags`, with Hant being Traditional and other Chinese Simplified, and zh-Hans stored by choosing 「中文」 (Chinese) before being Simplified Chinese): from Android 13 it is handed to the system's 「应用语言」 (App languages) (`LocaleManager`, with `android:localeConfig` in the manifest listing these languages, and what can be changed in system settings being the same value, with the system responsible for remembering and recreating the UI); on Android 11 and 12 it is stored locally and applied via `AppLanguage.wrap` to each Activity's `attachBaseContext` and the floating capsule's Compose host, recreating the current UI after a change. Compose uses `stringResource` directly; places that count as text outside the UI (status copy, notifications, the task service, the capsule's data, tool wording) use `tr` / `trPlural` (`app/i18n/UiText.kt`), taking resources in the App language, replaced in JVM unit tests by `ResFileTexts`, which reads resource files directly (tests asserting Chinese install `ChineseTexts`, and device tests use `ChineseUi` to temporarily switch the App language to Simplified Chinese). Quantities use plural resources, and dates, weekdays and months are written by `uiLocale()`. Tool wording looks up resources keyed by the Chinese label in the tool declaration (`ToolLabels.TOOL_LABELS`). Only the UI is translated: the built-in App knowledge, skills and prompts remain Chinese as before; answers, questions and titles written by the model follow the language the user speaks.

## 16. Voice input

Native Doubao streaming speech recognition 2.0 can be configured separately on the speech-to-text page, uploading PCM in real time and returning intermediate full text; credentials are encrypted independently and do not go through the Ark chat model path. For the protocol, lifecycle and test limits see [doubao-asr.md](doubao-asr.md).

「千问实时语音识别」 (Qwen real-time speech recognition) is also configured in the same group (three tabs on the settings page: self-hosted service, Bailian · Beijing, Bailian · Singapore), sharing `LiveSpeech` (`voice/LiveAsr.kt`): text control messages plus binary PCM, producing text while uploading when held down, and after release waiting for the server's end event (`stopped` / `task-finished`) before handing over the final text, with disconnection or timeout counting as failure and intermediate results never sent to the model as final text. The self-hosted service only needs an address; Bailian's API Key is encrypted independently by region, with an optional workspace ID; it tries to connect once before saving, without sending audio. See [live-asr.md](live-asr.md).

Hold-to-talk has two entry points: the conversation page's input field and the floating capsule. Both get their session only through `VoiceSource` (`voice/VoiceInput.kt`, `VoiceInput` in the App), replaced by a fake in UI tests; the recognition and transcription logic is all in `app/voice/`, and the UI only handles gestures, visuals and wiring.

- **Unified voice catalog** (`app/voice/model/`): reading aloud, speech-to-text and real-time calls share one catalog, no longer each keeping their own selection. `VoiceCatalogStore` stores services (`VoiceService`, whose account is an existing provider, credentials managed by the catalog itself, or none), models (`VoiceModel`, one model can carry `stt`/`tts`/`realtime` bindings at the same time) and selections (`VoiceSelections`: transcription is `SttSelection.Auto`/`Off`/a model, reading aloud and real-time are `VoiceModelRef`), with one snapshot per JSON (`VoiceCatalogSnapshot`). The three selection controllers (`SttSelectionController`/`TtsSelectionController`/`RealtimeSelectionController`) share through `VoiceModelEnvironment`; `VoiceAdapterRegistry` maps resolved models (`ResolvedVoiceModel`) to the three families of typed adapters (`SttAdapter`/`TtsAdapter`/`RealtimeAdapter`, implementations in `adapters/`) by the bound protocol, and neither the UI nor runtime decides on its own who to use. Old selections (`SpeechChoice`/`VoiceChoice`/`CallVoiceProfile`, and the `ttsModels` field kept in serialization) are read only once during one-time migration (`LegacyVoiceMigration`, building the whole thing first, writing self-managed credentials, then taking effect atomically), after which `legacyMigrationComplete` closes the door; a failed migration goes down the old path as before and records the reason in `VoiceModelEnvironment.migrationError`, with old fields still readable and not rolled back or deleted.

- **The `voice/` package's responsibilities**: `SpeechChoice` is the user's choice (automatic, the phone's own, off, a model of some provider) and its storage in settings (`SpeechSettings`, one key per JSON, treated as automatic when unreadable). `SpeechResolver` matches the choice, the phone's capabilities (`SystemCapability`) and existing providers to arrive at this time's engine `SpeechEngineSpec`. `SpeechSession` is the interface of one session, emitting only `SpeechEvent` (volume, interim result, transcribing, final result, failure); there are two implementations: `SystemSpeech` (the phone's own recognition, producing text as you speak) and `ProviderSpeech` (recording with `PcmRecorder`, handing the whole `Wav` to `Transcriber` after release). `HoldToTalk` is the hold-to-talk state machine (press, swipe up to cancel, release, wrap up at the time limit), not touching the UI or gestures, shared by the input field and the capsule. When the session ends by itself while the finger is still down (the phone's own recognition finishes a segment without reopening, or errors midway but has heard words), the result is kept first and the UI shows the heard words as before, and when the finger leaves it is handled by the landing point at that time: if it stops on cancel it is dropped, otherwise it is handed over, so wanting to cancel does not fill in or send the words; an error while holding prompts without waiting for release, and only when stopped on cancel is it kept first and, if released on cancel, not prompted. `Segments` joins the segments that the recognition service ended and reopened, and `Restarts` decides whether to reopen after an empty segment and after how long.
- **The engine is chosen only in `SpeechResolver`**: the UI and `VoiceInput` do not decide on their own who to use. When 「自动」 (Automatic) is chosen (or never chosen), the phone's own recognition is used if usable; when the phone's own system says it is available but it has been tried on this phone and does not respond, it returns `Unavailable(SystemNoResponse)` so the UI can say so truthfully and point to Settings, and **never quietly switches to a provider model that costs money**. When a provider model is chosen it is used, and when the provider has been deleted it returns `Why.ProviderGone`. The various reasons for `Unavailable` are turned by the UI into an explanation that 「还不能语音输入」 (Voice input is not available yet), with a button going straight to the selection page in Settings.
- **Fallback when the phone's own recognition does not respond**: the system can only say whether this recognition service exists; whether it will answer takes a try. When `SystemSpeech` has received no callback 3 seconds after starting to listen (`NO_RESPONSE_MS`, leaving time for the recognition service process's cold start), this time it ends reporting 「没有响应」 (No response); if 2 seconds after release (`FINAL_WAIT_MS`) there is still no final result, it also wraps up the same way: if it has answered, use the words heard; if there is no callback at all, it is no response, and it does not stay hanging without ending; no response in the same session is recorded only once. Only two times in a row (`SpeechSettings.SILENT_STRIKES`) are recorded as 「没响应」 (Not responding) (`SpeechSettings.noteSystemSilent`, with the count also stored in settings, since one stuck time is most likely just a slow cold start), and any answer in between resets the count (`noteSystemAnswered`). After that is recorded, `SpeechResolver` no longer treats it as available, and the settings page's label shows 「没响应」. When the user chooses 「自动」 (Automatic) or 「手机自带」 (Built into the phone) in settings, both the mark and the count are cleared, and a phone with a changed recognition service or an updated system can try again.
- **On-device recognition's language spelling does not match**: each vendor's on-device recognition registers languages differently; Pixel registers Taiwanese Chinese as `zh-Hant-TW` and `cmn-Hant-TW`, and sending `zh-TW` makes it report an error (13) for "language pack not installed". When on-device recognition reports the language unusable (12, 13), `SystemSpeechSession` first asks which languages are installed with `checkRecognitionSupport` (from Android 13), and `SystemSpeech.installedTag` looks among them for the same language and same region spelling (ignoring the script subtag, treating `cmn` as `zh`), and if found it switches to that spelling and keeps using on-device recognition; only when it is not found, cannot be asked, or does not answer for 3 seconds does it switch to online recognition, sending the language in the original spelling. It asks only once per session.
- **Try another recognition service**: the system's default recognition service may be given only to the system's own voice assistant and give no callback at all to other Apps, and a registered service is usable by name even when it is not the default. `SystemSpeech.services` lists the registered services and also adds Google's known exported components (the Google app, Speech Recognition & Synthesis, Android System Intelligence) when package visibility hides them. When the system has a default entry, it is tried first; when `Settings.Secure` has none (or it cannot be read), the installed services are named directly, Google's first (`SystemSpeech.attempts`). If the default does not answer while the finger is still down, the next service is tried by name, ones open to other Apps first, up to `MAX_ATTEMPTS` at a time; the one that answers when tried by name is recorded (`SpeechSettings.systemService`) and tried first next time. When there is only one service and a default exists, only the default entry is tried. For build devices limited by `SystemSpeech.serviceCompatibility`, the named candidates are kept in compatibility mode; on every device, a client error while the finger is still down and no words heard switches to the next service, while release or existing text only wraps up and does not start a new recording. A client initialization failure says 「自带识别未能启动」 (Built-in recognition could not start), and is no longer classified as the microphone being occupied. The `[Speech]` section of diagnostics lists the selection, the state of built-in recognition and the recognition services registered on the phone (component name, whether open, permissions needed).
- **Provider transcription and how it is remembered**: `Transcriber` sends requests by `TranscribeMethod`, only by protocol and never special-casing by model name, with errors going through the same `ModelHttp` mapping as conversation models. Five forms: uploading a file to the audio transcription interface (`TranscribeMethod.AudioTranscriptions`), bare base64 `input_audio` in the chat interface plus a transcription instruction (`TranscribeMethod.ChatInputAudio`), the same but with `data` as a data URI (`TranscribeMethod.ChatInputAudioUri`), Gemini's inline data (`TranscribeMethod.GeminiInline`), and data-URI `input_audio` in the chat interface with only audio and no instruction (`TranscribeMethod.ChatInputAudioOnly`). The method (`method`) is part of the selection: `SpeechChoice.Provider.method` stored in old selections maps to `SttBinding` when migrated into the catalog (audio transcription / bare base64 / URI / Gemini each corresponding to one binding), and the runtime adapter derives `TranscribeMethod` from the binding (`ProviderSttAdapter.spec`), using it directly for each transcription and no longer guessing by model name. The enum can only be appended to, never renamed or deleted, so old settings can still be read. Choosing a model on the settings page triggers a trial transcription, and it is selected and returned only after passing; ones not in the list can have their model name entered manually.
- **Named service's foreground capability compatibility**: only on the named path of the above limited builds, `SpeechServiceLease` temporarily binds a public service the caller already has access to, carrying the foreground capability the caller already has; recognition still goes through `SpeechRecognizer`, without calling private Binder protocols and without changing the system default service or permissions. Listening starts only after the connection is established, and the connection is likewise limited to 3 seconds; if it is not connected yet on release it ends, while normal recognition waits for the final result / wrap-up timeout before unbinding. Switching, failure and cancellation all clear the connection, and late callbacks from an old recognizer or old connection cannot act on a new session.
- **The recognition service itself lacks recording permission**: the recognition service is another App with its own recording permission; if Claire's is granted but its is not, it still cannot record and reports "no permission". Telling the user to go to Claire's permission page at this point is pointing at the wrong place. When `SystemSpeechSession` receives this error it asks `SpeechServiceMic.missing`: Claire itself has recording permission, which service is used this time can be identified (the named one is it; if not named, look at the system's default recognition service; on-device recognition cannot be identified, and it does not guess by taking the first registered one), and that App requested recording permission but did not get it—only when all three are certain does it report `SpeechFailure.ServiceNoPermission`, carrying its package name and its name in the system; when any one is uncertain it uses the original `NoPermission`. The explanation popped up on the conversation page states which App lacks the permission, and 「去设置」 (Go to settings) opens its App details page (when it cannot open, prompting to find it in the system's app management); the floating capsule gives a prompt and returns to Claire when tapped. It only queries and does not request or grant permissions for other Apps; after returning it does not record again by itself, re-judging the next time it is held. The `[Speech]` section of diagnostics additionally writes the system's default recognition service and each registered service's own recording permission.

- **Conversation input field** (`voice/ui/VoiceHold.kt`): the gesture covers the **unfocused** input field, and tapping still focuses it and brings up the keyboard, while holding for about 300 ms starts listening; when the input field is already focused this gesture is not installed, and long-pressing is still the system's own text selection and paste; then there is an extra microphone between the input field and the send key, listening only when held, and tapping it only prompts 「按住说话」 (Hold to talk). The release landing point is decided by `voiceAim`: sliding a finger up into the 「在听」 (Listening) card (and sliding up more than 32dp, a slight thumb movement not counting) is 「松开 发送」 (Release to send), the input bar, card border and dots on the card turning green (the same style as cancel's red), and after release the words are appended after the existing text in the input field and sent directly (the same path as tapping the send key, an interjection while a task is running; when it cannot be sent it stays in the input field), or on the provider path sent after transcription; sliding past the card's top edge (where the small 「上滑 发送/取消」 (Swipe up to send/cancel) capsule is) is 「松开 取消」 (Release to cancel); when the card is not laid out yet, sliding up more than 80dp still counts as cancel as before. Releasing at other landing points **only fills the words into the input field without sending**, for the user to edit and send; on the provider path 「转文字…」 (Transcribing...) is shown right on release, filling in after transcription; transcription waits at most 30 seconds (`ProviderSpeech.TRANSCRIBE_TIMEOUT_MS`), and on timeout it prompts as a network failure, never spinning forever. If it is still transcribing after release (or built-in recognition is still wrapping up), holding again discards the previous segment and starts listening anew, and the capsule is the same. A press that is too short (less than 0.5 seconds from finger down) is treated as an accidental touch and not transcribed, to avoid wasting quota. Leaving the page, rotating, or the App going to the background all discard this segment.
- **Floating capsule** (`capsule/CapsuleVoice.kt`, `CapsuleController`'s `talkHold` and `CapsuleTalk`): long-pressing goes through `cap/phone/a11y/OverlayHost.kt`'s `OverlayHold`, counting as a long press only after the finger stays still for 400 ms (`HoldGesture` judges, and moving past the touch threshold first is a drag and no longer counts as a long press), with `start/move/end/cancel` callbacks to the controller. While holding, the whole screen dims and a panel with two landing points, 「取消」 (Cancel) and 「改一改」 (Edit), floats beside the capsule; releasing elsewhere sends directly to the thing it is addressing at the moment (the conversation being continued, a run waiting for an answer, etc.), dragging to 「改一改」 opens the card to continue editing (the words are appended after the unsent text in the input field, the same joining as the conversation page's `HoldToTalk.join`), and dragging to 「取消」 drops them. Screen-reader users use the 「说话」 (Speak) action: tap once to start and tap again to send, and having no finger they can only send. While the capsule is speaking it switches to the 「你来处理」 bar (or can no longer speak), and these words are dropped directly and the microphone released. Recording happens in the accessibility service's overlay window gesture, with the finger on screen while holding, without starting a separate foreground service. The speaking panel is a third overlay window: it covers the whole screen and appears while speaking, and when collapsing it is first explicitly set invisible and then shrunk to no size (the same set as the dot and the card: after the content is cleared no new frame may come out, and zero size still cannot remove the system canvas's old frame, so the panel would stay at 「转文字…」); if after release the engine's own wrap-up limit (2 seconds for built-in recognition, about 20 seconds for streaming, 30 seconds for whole-segment transcription) plus a little margin has passed with no result, it collapses the panel and treats it as not heard clearly, so a stuck session is not kept forever.
- **Too many words heard**: when they do not fit in the card while holding (6 lines for the input field, 5 for the capsule), it measures lines by the real layout, removes complete sentences already finished from the front (breaking after periods, question marks, etc.) and adds 「…」 at the front, keeping the latest words always visible; when even the one still being spoken does not fit, its end is kept (`VoiceCopy.fitHeard`; the displayed part is in `voice/ui/VoiceHold.kt`, shared by the input field and the capsule). Only the display changes; the text handed over does not.
- **60-second cap**: both the input field and the capsule listen at most 60 seconds per time (`MAX_MS`), treating reaching the limit as release and never holding back from sending; the input field counts down at the card's bottom right in the last 10 seconds. `HoldToTalk.tick` calls `release` at the limit, because recording stops by itself at the limit without a separate notification, and without wrapping up the words are lost. The exception is sessions that stream as they speak and do not accumulate a whole recording (`SpeechSession.unlimited`, currently the self-hosted and Bailian 「千问实时语音识别」): hold as long as you like, with no countdown and no wrap-up at the limit, and the recorder keeps no whole recording either (`PcmRecorder`'s `unbounded`); when there are too many words the preview removes finished sentences from the front as in the previous item.
- **Recording permission**: requested only when holding for the first time (`RECORD_AUDIO`). In the input field: with no permission it shows the system dialog; when it has been denied and the system will no longer show a dialog, it shows an explanation instead, with a button going straight to Claire's permission page in the system. When recording has been allowed but the recognition service still reports no permission, or reports a recording error (`ERROR_AUDIO`, `SpeechFailure.AudioError`), it shows another explanation instead: whether the master microphone switch in quick settings (from Android 12) is off, whether Claire's microphone has been separately turned off in the system's permission management, and that it may also be occupied by another App; the button still opens Claire's app details in the system. When the recognition service reports a client error, an error is thrown when starting to listen, or the provider path's recording cannot start, it still only prompts that the microphone may be occupied by another App. In the capsule: with no permission it does not start, popping a prompt that returns to Claire when tapped (`capsule_voice_need_mic`) to authorize. `VoiceInput.start` returns a session that emits only one `Failed` when there is no permission or the engine is unusable, and the UI handles it with the same failure path instead of each judging on its own.

The `content-transcribe` skill is the Agent transcribing **audio files**, a different matter from voice input here, and the two do not depend on each other.

## 17. App access

By package name, it restricts which Apps the standard phone tools can read and operate; see [`app-access.md`](app-access.md) for the rules and boundaries.

- **Policy** (`core/device/access/AppAccess.kt`): Apps with no setting are allowed by default, and classification does not decide permission. An empty block list does not reject because a package name is missing; when it is non-empty and ownership is unknown it waits briefly and re-reads once, and if still unknown returns `app_access_unverified`. An unavailable file returns `app_access_unavailable`, reset by the user in Settings.
- **Gate** (`core/screen/uistate/AppAccessScreenPort.kt`): wraps the task's phone port, protecting screen-reading results and explicit targets; `ActionExecutor` checks before and after actions, and rejections are returned to the model as tool results. Every member of `ScreenPort` is written out explicitly in the gate, without `by` delegation, and tests check member by member that it "is forwarded to the port inside" and that "except for a few that do not touch the App UI, all are checked", so a member added to the port later will not escape checking. The Android port provides only window ownership (`AndroidScreen.accessPackages`), and only looks at the list where the gate cannot see the target: who handles links and system actions with no App specified, and Apps opened onto the user's main screen; it does not downcast to read the settings implementation. `ScreenSession` clears old element references, screenshots and positioning caches by permission revision.
- **Cost**: when the list is empty nothing extra is done (no asking for windows, and the system prompt has no app access section). When the list is non-empty, screen reading checks directly against the window ownership in the screen it just read, without asking for windows separately; other reads' and actions' check results are reused for at most 1 second when the window has not changed (the accessibility window change count has not changed) and the list has not changed, so a screenshot right after the same screen reading and the task preview's frame-by-frame images do not have to ask for windows every time.
- **Prompt**: app access rules are in `prompts/capabilities/app-access.md`, appended after the phone section only when the list is non-empty (or the settings cannot be read); for ones disabled only while a task is running, the explanation carried by the rejection result still tells the model what to do next.
- **Storage and UI** (`app/settings/AppAccessStore.kt`, `app/settings/ui/AppAccessScreen.kt`): process-shared and atomically written; opening the settings page does not upload the list, and before refreshing classification it confirms sending App names and package names. `AppClassifier` reuses the existing model configuration, and failure does not change permissions. The page, classification and sharing copy support English, Simplified and Traditional Chinese.
- **Proactive sharing** (`app/cap/phone/a11y/ScreenShareConsent.kt`, `ShareChoice.kt`): the user can allow sharing the screen only, allow this App, or cancel; a separate sharing permission does not lift automatic operation restrictions, and the source and permission are rechecked before and after collection. Sensitive authorization screens can only be operated by the user.
- **Boundaries**: shell commands, the sandbox and computer access (MCP) are not restricted by this gate; calling standard phone tools inside scripts is still checked. On encountering a restricted App the model should re-evaluate its route and, when it really needs it, explain where to allow it in 「设置 › 应用访问」 (Settings › App access).

## Post-call summary and follow-up draft

`CallRuntime.summarizeCall` (`app/calls/CallRuntime.kt`) follows the call summary switch and the pre-send authorization check, and in the summary request after the call ends `CallSummaryGenerator` generates both the structured summary and a nullable `CallSummary.followUpDraft`. No extra model request is added; the draft stores at most 600 characters. A missing or incorrectly formatted optional draft does not affect the rest of the summary, and old records have no draft by default. `CallHistory.saveFollowUpDraft` saves edits through the existing mutex, encrypted file and publish-after-successful-write path, without overwriting the transcription, to-dos or processing state, and without reviving deleted records. `app/calls/ui/CallFollowUpDraft.kt` only provides edit, save and copy, keeping the edited content when saving fails; there is no contact lookup or sending capability.
