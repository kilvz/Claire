# User-controlled SMS auto-login (experimental)

Related to #606. Settings → SMS verification code login is off by default. After the user enables the Android RECEIVE_SMS permission once and configures a trusted service/account, a subsequent local main task that explicitly asks to log in to that app can automatically request the SMS, fill in the account/verification code, tap final login and verify the login result, without confirming each step or re-entering matching parameters. #609's old version only authorized filling the code each time; permission from the old version is not migrated to auto-submit permission, and you must re-read the explanation in Settings and turn it on.

## One-time configuration and authorization

The settings page can add, edit and delete local trusted configurations. One account per app; a configuration includes the installed app's package name, the exact SMS sender, the service signature, the account number and the account identifier in the SMS, the full resource IDs of the native account box / verification-code box / send button / final login button, and an explicit marker of the logged-in page, exact text and account display control. Saving the configuration authorizes the corresponding login flow; Android takes the signature certificate digest from the installed app automatically and it cannot be forged by the model or the configuration form. After the signature changes, the configuration must be verified again.

This version is a generic controlled native mapping entry point, and does not yet include any commercial app mapping verified on a real device. Initial configuration is an advanced setting and requires verified page rules; it will not guess buttons, substitute coordinates for missing controls, or classify a misconfiguration as a successful login. The account is a 4–11 digit number stored on the phone, and the SMS account identifier must correspond to it. If another account is already shown in the configuration's account input box, overwriting it is refused.

Permissions and configurations are encrypted with Android Keystore AES-GCM and saved atomically, and are not written into chat, tool arguments, model context or plaintext preferences. Only the matching rules and account the user explicitly configured are stored, never the SMS or verification code. Corrupted data, decryption failure and permissions from an older version are all treated as off. Turning off, editing or deleting a configuration changes the authorization version and cancels the current task; turning it back on does not restore the old authorization. The last native action and revocation share a lock, so after turning off returns, input or login taps under the old permission can no longer start; actions already handed to Android cannot be withdrawn.

## Automated task chain

1. The model only calls `phone_sms_login(app)`. The tool is limited to a local UI main task where the user explicitly asked to log in to the corresponding app, and is not provided to subtasks, unattended runs, channels, MCP or read-only checks. For an unknown configuration, an app signature mismatch, missing SMS permission, disabled app access or unclear profile identity, it returns the actual state and hands it to the user for manual handling.
2. The whole flow first turns on private-observation protection. It checks or fills in the configured account in the exact native account box, without going through the clipboard. It registers a temporary SMS_RECEIVED receiver constrained by the system signature-level BROADCAST_SMS send permission, then taps the exact request-verification-code button once; it does not read the inbox, does not use a persistent receiver, and does not change the default SMS role.
3. Within the 90-second new-SMS window, it requires the exact sender, `【service signature】` or `[service signature]` (service signature) at the start of the body, login semantics, the corresponding account identifier, and a uniquely and explicitly marked 4–8 digit verification code. Payment, transfer, registration, password change, recovery, binding, ambiguous and expired SMS are refused. The window can be consumed only once, and duplicate broadcasts cannot fill the code or submit again.
4. Before input, it re-checks the signature, the authorization version, the app, the primary user profile and the exact account box. It calls ACTION_SET_TEXT once on the unique verification-code box; there is no focus, coordinate or generic-paste fallback. If the app has already submitted automatically, it does not tap again. Otherwise it taps only the configured final native button whose text has explicit login semantics such as "Log in" once, and does not automatically agree to agreements, handle payment, registration, account recovery or risk control.
5. It waits on the phone for the actual login result. Success requires simultaneously seeing the configured logged-in marker and corresponding account, the verification-code box and login button having disappeared, and no residual verification code in the native tree, window content or local OCR; only when two consecutive observations meet the conditions does it return logged_in. Explicit errors return login_failed; timeout, OCR unavailable, identity/UI changes or missing evidence return states such as login_unverified. Input being accepted or a tap succeeding never equals being logged in.
6. After successful verification, native text screen reading and ordinary control operation are restored, and the task can continue; this is not a matter of forbidding all subsequent screen reading and then claiming login is complete. The task's images, previews and generic system commands remain on this phone, to prevent pixel or side-channel residue. Within the task only a non-exportable short-term verification-code fingerprint is kept, used to redact the same code (including variants with spaces, hyphens and full-width characters) in subsequent text trees, OCR, events and action hints, and it is zeroed when the task ends; the original code is not stored. When verification does not succeed, it keeps the observation protection and reports incomplete, leaving manual takeover available.

The state flow is in `SmsLoginAutomation`; rule and evidence checks are in `SmsLoginProfile`, `SmsLoginMatcher`, `SmsLoginWindow`, `SmsLoginEvidence`; Android broadcasts and permission checks are in `AndroidSmsLogin`; exact control input and local OCR are in `AndroidScreen`. Settings use `SmsLoginSettings`. The authorization UI and target teaching events remain protected by the existing sensitive UI protection, and authentication secret notifications are rejected before entering the inbox.

## Exact boundaries and items to be verified

- Android 10+, primary user profile, a single native verification-code box and explicit resource IDs. Missing resource IDs, WebView, grid-code CAPTCHA, work profile/clone, and unclear page mappings are not supported. When there is no trusted logged-in account marker or OCR cannot confirm there is no leftover code, success is not reported.
- The SMS must match the account safely. Scenarios where the service provides no account identifier at all, the sender/service is unclear, or the accounts do not match are not guessed and still need manual handling. The fallback here is insufficient identity or system capability, not the per-step-authorization flow.
- RECEIVE_SMS is an Android dangerous and strictly restricted permission; installer allowlists, vendor ROMs and distribution channels may block granting it; the shell will not be used to bypass this. See [Android permission documentation](https://developer.android.com/reference/android/Manifest.permission#RECEIVE_SMS). It does not depend on Google Play services.
- The SMS send time is checked against the system SMS's one-second precision; delayed, clock-inconsistent, abnormally segmented or out-of-window SMS may be refused. The whole automated flow takes at most 180 seconds. Cancel, permission/configuration revocation or task stop unregisters the receiver, clears the temporary code and does not retry the login tap.
- The system SMS app's own storage, user-initiated sharing, arbitrary code with the same UID, sandbox commands and external MCP are not data-isolation targets of this feature; the prompt forbids bypassing the refusal through these paths. This implementation is not a global security sandbox. Temporary immutable strings that Android must use cannot be zeroed in place, but they are not actively logged or kept for long.
- Synthetic tests cover automatic success, app auto-submit, wrong service/account, payment, duplicate/expired SMS, cancel, turning off/deleting a configuration, login error, no evidence of success, leftover verification code and restoration of text observation. A real account, number or SMS has not been used yet, nor has end-to-end acceptance on a commercial app on a real device been done. Installer authorization, vendor SMS broadcast/segmentation, configuration mapping, native controls, OCR, certificate changes and revocation timing still need synthetic-SMS verification on test devices; compiling and synthetic unit tests do not equal verification on all models/apps.
