# In-app realtime voice call · design (all in one go)

Date: 2026-11-22
Status: Pending approval
Research basis: in-session research notes (a close read of the whole PR chain of a reference implementation from the same source + a comparison with this repository's engine layer; the notes are not checked in, and all conclusions have already been folded into this spec)

## Intent and why

Talk to the assistant by realtime voice inside the app, **and get things done by voice**: full duplex, interruptible, hands-free, kept alive by a foreground service; what the user says goes through a strict safety gate into the existing task system, progress scrolls in the call panel, and the model restates the result; the call text is written back into the conversation.
The engine layer (`VolcRealtimeClient`/`CallPlaybackQueue`/`CallInputPacer`/`PcmRecorder`/`PlaybackTickets`/`CallVoiceProfileStore`) already exists in this repository and is newer than the reference implementation — **do not port the other client** (it is a fork of our old engine, so porting would be a downgrade); the additions are concentrated in the shell, the safety gate, routing and the UI, about 1,600–1,900 new lines of code + 600–800 lines of tests.
The user has already decided: no phasing, do it all at once; execute in worktree isolation.

## Acceptance (all are gates)

1. JVM all green: all safety-gate branches, state machine transitions, protocol frames (fake service), route decisions, transcript aggregation, echo guard, backpressure.
2. androidTest smoke: full call-page chain (connect→listen→play→interrupt→hang up→retry→limit) + permission-denied path + fake task execution routing.
3. **Real-device audio matrix (hard gate)**: speaker/earpiece/Bluetooth headset × interruption/echo; VOICE_COMMUNICATION availability and AEC; isSilenced; hot plugging; incoming-call interruption; focus stolen; lock-screen behavior; measured false blocks/misses of the echo guard.
4. **Full-chain real-device verification of getting things done by voice**: say one sentence→execute→status line→restatement; every anti-mis-execution measure (forged function_call, echo impersonating an instruction, cross-turn replay) does not take effect.

## Feature semantics (full UX chain)

- **Entry**: the earpiece button in the chat input bar (coexists with push-to-talk, enters call mode); the floating capsule menu "Voice chat" opens it directly via an explicit intent. Preconditions = realtime voice credentials configured (reusing the AI phone config) + microphone permission. The system digital assistant entry differs from our IA, so this spec does not cover it.
- **Permission flow**: in the call panel, RECORD_AUDIO is requested only when the user taps the button (no automatic prompt); after denial the button becomes "Go to settings" and opens the app details page, rechecking on ON_RESUME; when credentials are missing the button opens the realtime voice settings page.
- **Connecting**: Connecting (cancellable) → wait for the UI to be RESUMED (report "Please return to the foreground" if not back within 3 seconds) → the microphone-type foreground service takes its lease → request audio focus → microphone check (the first chunk within 3 seconds is non-empty and not silenced by the system) → start playback on the speaker → local two-tone prompt → play the greeting once per session → "Connected" green dot + mm:ss timer + red hang-up button.
- **Conversation**: the user speaks → server-side VAD produces a transcript → the model is constrained by the prompt: for each complete utterance it calls exactly one `mika_request` tool and stays silent → after strict validation on the app side, the request is handed to the existing chat/work entry point for execution → progress scrolls as short status lines (at most 12 lines, without details such as coordinates or schedule titles) → the result goes back to the model as a function result → the model restates the result only once. The panel has a text input field; typing and speaking take the same path.
- **Barge-in**: as soon as the user starts speaking (server-side speech_started) → invalidate the playback queue generation + AudioTrack pause/flush/play + cancel local tasks that have not finished (without claiming to undo operations that already took effect).
- **Speakerphone**: Android 12+ `setCommunicationDevice` (wired/Bluetooth headsets take priority over the earpiece; keep the speaker when there is no private listening device); older systems use the speakerphone toggle; the selected state reads the system's actual communication device, and hot plugging refreshes through AudioDeviceCallback; hanging up restores the original audio mode.
- **Ending**: hang-up button / hang up from the notification shade / incoming call (MODE_IN_CALL/RINGTONE or the phone function busy → busy error) / silent hang-up (when the configured number of minutes pass with no new content — nobody speaking, nobody typing, Claire not speaking, no task progress — hang up and show "No activity for X minutes; the call has ended", without automatic retry; "Call mode" offers 2 / 5 / 10 minutes, a custom 1–120 minutes, or no automatic hang-up, defaulting to 5 minutes; 30 seconds before the deadline Claire asks whether the user is still there, and that reminder itself does not count as new content; there is no overall duration limit, and AI phone calls are not governed by it) / collapse when the page hits ON_STOP and backgrounding is not allowed. Both sides' text is written back to the originating conversation in bulk under NonCancellable in finally.
- **Relationship between calls and conversation** (decided 2026-11-24): the conversation is the main path; a call is just a segment within it.
  - **The chat page** is the complete conversation: each finished turn in a call is saved into the current conversation (the turn carries a `callId`) and laid out sentence by sentence like typed turns; this segment is preceded and followed by a line of small light text, "📞 Voice call · 9:41" and "Call ended · 3:12" (silent hang-ups say "No one spoke for too long"). A call with nothing said leaves only one line, "Voice call · 0:05 · No one spoke", placed in the conversation by connection time.
  - **The call page** shows only this call: every open starts blank, with a line at the top, "Last call · 9:41 ›", that returns to that segment in the chat when tapped.
  - **Call history**: ⋯ in the top-right of the call page → "Call history" lists every call in this conversation (connection time, duration, a note when nobody spoke); tapping one returns to the start of that call in the chat and briefly highlights it, without opening a separate replay page; ⋯ also has "Call settings", which goes to "Call mode".
  - Records are stored next to the conversation in `<conversation>.json.calls` (write one entry on connection, then fill in the end time and reason on hang-up); deleting the conversation deletes them too.
  - **The call page is an ordinary page**: it enters the page stack; the back key / collapse button returns to the previous page and the call continues; while it is active, every other page has a green bar at the top, "In call · Return to call", with a timer, and tapping it returns to the call page. Tapping a task card on the call page opens the task timeline, and back returns to the call page.
- **Error UX**: auth, connection timeout, disconnection, rate limiting, provider error, no microphone input, audio focus failure and playback failure each get their own copy + in-place retry (attempt++ reruns the whole connection flow).

## Audio pipeline and full duplex (established facts, implement accordingly)

Microphone AudioRecord (16k mono PCM16, 320 samples/20ms chunk) → WebSocket (realtime duplex service, STT+LLM+TTS all server-side) → downlink 24k mono PCM16 → ring playback queue → AudioTrack (USAGE_VOICE_COMMUNICATION / CONTENT_TYPE_SPEECH, MODE_STREAM, non-blocking writes). VAD is entirely server-side; the client does no local VAD and no push-to-talk. Uplink and downlink run in independent coroutines; recording uses a `Channel<ShortArray>(100)` for backpressure, accumulating at most 5 seconds during connection setup, and overflow fails outright rather than silently dropping samples; uplink 20ms frames are paced to absolute deadlines; the playback queue is capped at 20 seconds (#695 lesson), and a single downlink packet is ≤1 second. Prompt tone: locally synthesized 720/960Hz sine, 65ms each with a fade-in/fade-out envelope, written directly to the playback track and not counted in the level meter.

## Component list

All new code follows generic AOSP design: public API capability detection + fallback chain, with no special cases for any device model; code/comments/docs/commit messages do not contain any external project names.

1. **`voice/PcmRecorder` (+~15, modified)**: `inputSource` (calls pass VOICE_COMMUNICATION to trigger the platform AEC/NS, falling back to MIC if initialization fails), `chunkSamples`, `isSilenced` reading (capability detection; always false when unsupported). The existing voice input path keeps its behavior.
2. **`calls/VolcRealtimeProtocol` (+~80, modified)**: `mikaActions` config item, `mika_request` tool registration frame, `functionResult` frame, `synthesize` frame (reused for read-aloud), `response.done` event parsing.
3. **`calls/VolcRealtimeClient` (+~60, modified)**: `VolcRealtimeConfig.agentTools`, `sendFunctionResult(callId, text)`, `synthesize(text)`, `VolcRealtimeEvent.ResponseDone`.
4. **`voicecall/VoiceCallSession` (~350, new)**: call orchestration, an **explicit enum state machine** (Connecting→MicCheck→Active→Ended/Error; no boolean composition, `ensureActive()` distinguishes external cancellation): RESUMED wait, focus, microphone check (3 s first chunk + isSilenced + VOICE_COMMUNICATION→MIC fallback), prompt tone, greeting once, playback writer (reusing CallPlaybackQueue), barge-in (queue invalidation + pause/flush/play + notification-route task cancellation), silent hang-up (see above), 8 error messages + in-place retry, echo guard (during playback, drop a "user transcript" that is a substring of the assistant's already-spoken content or contains it, within a 500-character ring buffer; the threshold is adjustable).
5. **`voicecall/VoiceCallRequest` (~120, new)**: the execution safety gate — only a "current-turn, final and complete" user transcript may feed execution; the `utterance` parameter is checked against the transcript with a normalized **one-way** containment check — the utterance must fall within the current-turn transcript, and anything longer than the transcript (the model added words the user did not say) is always rejected (on mismatch the transcript is not consumed); callId is single-use (including reconnection replay); assistant echo is removed; each turn's transcript is consumed once. Rewrite it from the semantics as needed.
6. **`voicecall/VoiceCallRoute` (~200, new)**: one-shot destination routing from voice requests to the existing chat/work task entry point (first come, first served); subscribes to TaskState to emit short status lines; when a task needs confirmation/takeover, prompts "Check the task page"; barge-in cancels tasks that have started but not finished; results go back through `sendFunctionResult`.
7. **`voicecall/VoiceCallTranscript` (~50, new)**: aggregates events into Turns (question/answer/time) and writes them back to the originating conversation at the end.
8. **`voicecall/VoiceCallService` (~130, new)**: microphone-type foreground service + CATEGORY_CALL ongoing notification (with a hang-up action); `select` races the call coroutine against the notification hang-up; on Android 14+ the mic FGS can start only from the foreground; the call page does not open on the lock screen.
9. **`voicecall/VoiceCallAudioRoute` (~120, new)**: two-path speakerphone routing + selected state read from the system's actual device + hot-plug refresh + hang-up restore; decisions are extracted into pure functions for JVM tests.
10. **`voicecall/ui/VoiceCallPage` (formerly VoiceCallOverlay)**: one page in the page stack (`Route.VoiceCall`; no longer a full-screen Dialog since 2026-11-24), opaque and dark; ⋯ in the top-right (call history / call settings, `VoiceCallRecords`); the green bar at the top of other pages lives in `VoiceCallBar`; a central breathing orb rises and falls with the bidirectional level (**drawn in-house**, reusing the VoiceWave/Breathing language and introducing no third-party particle engine); a status line scrolling area (≤12 lines) + mm:ss + hang up + speakerphone + collapse + text input field.
11. **Entry points (~30 each, modified)**: the earpiece button in the input bar enters call mode; the capsule menu "Voice chat" opens it directly.
12. **Prompt constraints**: the session instructions make the model call exactly one `mika_request` per complete utterance and stay silent, restating the result only once; goes into the prompts resources.
13. **Strings**: about 40 new keys × 12 directories (values + 11 locales), with the greeting localized, not hard-coded.

## Execution safety (the core a port must preserve)

The model can forge a `function_call` — **only a current-turn complete transcript may trigger execution**: final+complete validation, parameter-transcript compatibility check (on mismatch not even the transcript is consumed), single-use callId to prevent reconnection replay, echo removal to prevent the assistant's voice from impersonating an instruction, single consumption of each turn's transcript to prevent duplicate execution. Better to refuse execution than to execute wrongly.

## Risks and mitigations

- **Audio-path device differences (the biggest risk)**: AEC quality, AudioTrack freezing, isSilenced, setCommunicationDevice compatibility — capability detection + fallback chain; the device matrix is the acceptance gate.
- **Inherent residual echo self-excitation**: when platform AEC fails the guard is probabilistic (a ≥4-character substring heuristic, which may wrongly block a user repeating the assistant's words); prefer the conservative direction (reduce execution sensitivity during playback) and tune the threshold on real devices.
- **Permissions and policy**: RECORD_AUDIO runtime permission; continuous background recording must run under a microphone-type FGS (on Android 14+ it can start only from the foreground); backgrounding keeps the FGS alive + notification hang-up.
- **Power and heat**: continuous 16k capture + 24k playback + a long-lived connection; audio thread at `THREAD_PRIORITY_AUDIO`; silent hang-up as a backstop (it will not stay on forever when nobody is using it; default 5 minutes).
- **Server billing/rate limiting**: billed by duration; error copy distinguishes "retryable" from "go configure".
- **Credentials by purpose**: calls read the default realtime voice profile; the pitfall of audition/read-aloud credentials hitting the wrong API is already known, so they are stored and read separately by purpose.
- **Overlapping audio from multiple playback sources**: in-process mutual exclusion + generation tokens to block late callbacks (PlaybackTickets is already the right solution).
